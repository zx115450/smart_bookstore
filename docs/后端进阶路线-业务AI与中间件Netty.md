# 后端进阶路线：业务 / AI 作品集 vs 中间件 / Netty


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档  
> **关联**：`进阶分轨` — 业务 / AI / Netty  
> **索引**：[学习文档中心](./README.md)

> 适用：已有类似本仓库「智慧书城 + Spring AI」基础，想决定下一步学什么。  
> 对照本仓库缺口：[IMPROVEMENTS.md](../IMPROVEMENTS.md) · AI 学习：[AI模块学习文档](./AI模块学习文档.md)

两条路线都能走到「中高级」，差别在于**作品叙事与能力重心**。可以一条主修、另一条选修，不必同时深挖。

---

## 如何选型（先读这段）

| 你的目标 | 主修路线 | 暂时可以不做 |
| --- | --- | --- |
| 校招 / 业务研发 / AI 应用岗 / 作品集讲故事 | **路线 A：业务 / AI** | 先啃完整 Netty 源码 |
| 基础架构 / 中间件 / 网关 / 长连接高并发 | **路线 B：中间件 / Netty** | 再堆一个同质商城 Demo |

**判断口诀**：

- 面试主要讲「借阅、秒杀、Tool Calling、RAG 降级」→ 走 A  
- 面试主要讲「百万连接、协议编解码、零拷贝、Reactor」→ 走 B  

本仓库当前更适合先走 **路线 A**（测试、限流、MQ 幂等正好是文档里的 P0/P1），路线 B 作为选修或第二阶段。

---

## 路线 A：业务 / AI 作品集进阶

### A.1 目标画像

把现有项目从「功能很多的 Demo」提升为「能讲清稳定性与工程化的作品」：

- 核心链路有自动化测试  
- 关键接口有限流与失败保护  
- 消息消费可证明幂等  
- AI 能力可演示、可约束、可降级  

**不必先啃 Netty**：Spring MVC + Redis + RabbitMQ + Spring AI 已够支撑业务叙事；Netty 对这条路线是加分项而非门槛。

### A.2 为什么优先这三块

| 优先级 | 能力 | 作品集价值 | 本仓库对应 |
| --- | --- | --- | --- |
| P0 | **测试** | 证明你敢重构、懂回归 | IMPROVEMENTS P0-2 |
| P0 | **限流** | 证明你懂成本与滥用防护（尤其 AI） | IMPROVEMENTS P0-4、`ai.rate-limit` |
| P1 | **MQ 幂等** | 证明你懂异步下的「至少一次投递」陷阱 | IMPROVEMENTS P1-8、秒杀/订单超时消费 |

这三项比「再学一个新框架」更能拉开与普通 CRUD 作品的差距。

### A.3 12 周节奏（可压缩）

#### 第 1～3 周：测试地基

**做什么**：

1. 给 `AuthService`、借阅状态机、订单创建补单元测试  
2. 用 Testcontainers 拉起 MySQL / Redis，做 1～2 条集成测试  
3. AI：mock `ChatClient` 或只测 Tool / `BookRecommendService` 编排  

**验收**：

- `mvn test` 有真实断言，不再是空的 `contextLoads`  
- README 能写「如何跑测试」  

**推荐仓库**：

- [spring-petclinic](https://github.com/spring-projects/spring-petclinic)（看测试风格）  
- [testcontainers-java](https://github.com/testcontainers/testcontainers-java)  

#### 第 4～6 周：限流与安全配置

**做什么**：

1. 落地 `ai.rate-limit.per-user-hourly`（Redis 计数或令牌桶）  
2. 登录 / 发码限流已有则补文档与测试  
3. 密钥全部外置（`IMPROVEMENTS` P0-1），禁止默认 JWT Secret 上演示环境  

**验收**：

- 超限返回明确错误码，日志可追踪 user / IP  
- 压测或脚本证明限流生效  

#### 第 7～9 周：MQ 幂等

**做什么**：

1. 梳理本项目消费者：秒杀发券、订单超时取消、死信等  
2. 为每条消费链路设计幂等键（业务单号 / messageId + 去重表或 Redis SET）  
3. 模拟「同一消息投递两次」，结果仍正确  

**验收**：

- 文档画出「生产者 → 队列 → 消费者 → 幂等存储」  
- 有失败重试与死信处理说明  

#### 第 10～12 周：AI 作品集打磨

**做什么**：

1. 聊天 SSE / 流式（可选，体验加分）  
2. 固定问句评测集：断言是否调用了正确 Tool（查书 / FAQ / 推荐）  
3. 写一页「架构口述稿」：事实走 Tool、RAG 可选、会话隔离  

**验收**：

- 作品集 README 有架构图 + 3 分钟讲解提纲  
- 能主动说出测试与限流仍在演进的边界  

### A.4 本仓库落地清单（路线 A）

按顺序勾选即可：

1. 清理 `application.yaml` 敏感默认值  
2. 核心业务单测 + 至少一条 Testcontainers 集成测试  
3. 实现 AI 对话限流并写测试  
4. 秒杀 / 超时订单消费者幂等  
5. Actuator + 基础指标（可选但加分）  
6. AI 评测脚本或手工用例表  

细节见 [IMPROVEMENTS.md](../IMPROVEMENTS.md)。

### A.5 面试怎么讲（路线 A）

推荐结构：

1. 业务闭环：登录 → 借阅 / 购书 → 预约签到 → AI 客服  
2. AI 设计：Tool Calling 防幻觉；RAG 只召回，库存回查 MySQL  
3. 工程化：测试、限流、MQ 幂等各举一个真实例子  
4. 诚实边界：未上 K8s / 未自研协议，重点在业务正确性与可演进  

### A.6 路线 A 明确不做（前 3 个月）

- 完整阅读 Netty 源码并手写自定义协议服务器  
- 一上来拆十几微服务却无测试  
- 再克隆一个 mall 当「第二个主作品」

## 路线 B：中间件 / 基础架构 / 高并发网络（Netty 进阶必修）

### B.1 目标画像

面向网关、RPC、推送、IM、自研协议、中间件研发：

- 理解 Reactor、线程模型、零拷贝与背压  
- 能用 Netty 写清「编解码 + 粘包拆包 + 心跳 + 空闲检测」  
- 能阅读 Redis / MQ / gRPC 等组件与网络层的关系  

**Netty 是进阶必修**：这条路线的核心能力在「字节流与连接管理」，不是再堆业务表。

### B.2 前置条件（建议有了再深挖）

- 熟悉 TCP、HTTP 基础（三次握手、粘包、半包）  
- 写过或读过 NIO / 多路复用概念  
- 最好已有一个能跑的业务项目（例如本仓库），避免「只学框架不会落地」  

系统补前置：见 [Netty 前置基础](./learning/Netty前置基础.md)（网络 / NIO Demo / 协议帧 / Reactor 直觉与自检清单）。

若业务基础仍弱，建议先完成路线 A 的测试与幂等，再进 B，否则面试容易「概念很炫、项目很空」。

### B.3 学习地图

```text
Java I/O 演进（BIO → NIO → 多路复用）
        ↓
Netty 核心：EventLoop / Channel / Pipeline / ByteBuf
        ↓
实战：自定义协议 Echo → 长度字段解码 → 心跳
        ↓
对照：Redis 协议、HTTP 编解码、WebSocket
        ↓
进阶：内存泄漏排查、水位线、线程亲和、性能压测
        ↓
延伸：Reactor Netty / gRPC transport / 简易网关
```

### B.4 分阶段计划（约 16 周，可并行选修）

#### 阶段 1：网络与 NIO 基础（2～3 周）

**做什么**：

- 搞清阻塞 vs 非阻塞、select/epoll 直觉模型  
- 手写或跟写极简 NIO 服务端，体会 Buffer 与 Selector  

**验收**：能白板画出「一个 EventLoop 如何服务多个 Channel」。

#### 阶段 2：Netty 核心 API（4～5 周）

**必学概念**：

| 概念 | 你要能说清 |
| --- | --- |
| `EventLoopGroup` | Boss / Worker 分工 |
| `ChannelPipeline` | Inbound / Outbound 顺序 |
| `ByteBuf` | 引用计数、池化、为何比 `ByteBuffer` 好用 |
| `LengthFieldBasedFrameDecoder` | 解决粘包拆包 |
| `IdleStateHandler` | 心跳与踢掉死连接 |

**小项目建议**（二选一即可进作品集）：

1. **自定义长度协议的聊天室 / 推送 Demo**（Netty + 简单业务）  
2. **迷你 RPC**：序列化 + 请求响应关联 ID + 超时  

#### 阶段 3：对照真实中间件（3～4 周）

选读而非全啃：

- Redis 客户端如何管连接与命令流水线  
- RabbitMQ / Kafka 客户端网络线程模型（建立直觉）  
- gRPC / HTTP2 与 Netty 的关系（了解即可）  

**验收**：能讲「为什么业务项目用 Spring MVC 不必手写 Netty，而网关 / IM 常常要」。

#### 阶段 4：性能与生产问题（3～4 周）

- 背压与写缓冲区水位线  
- 常见内存泄漏（`ByteBuf` 未 release）  
- 简单压测（连接数、QPS、延迟分位）  
- 线程模型错误导致的业务错乱  

### B.5 推荐资源（路线 B）

| 类型 | 推荐 |
| --- | --- |
| 框架仓库 | [netty/netty](https://github.com/netty/netty)（先 examples 再源码） |
| 书籍（择一精读） | 《Netty 实战》或国内体系化 Netty 教程 |
| 对照 | Reactor Netty、Spring WebFlux 传输层（理解「响应式 Web 底层常是 Netty」） |
| 作品形态 | 独立小仓：`netty-im-demo` 或 `mini-rpc`，附压测数据与线程模型图 |

### B.6 面试怎么讲（路线 B）

推荐结构：

1. 为何不用阻塞 IO：连接模型与线程成本  
2. Netty 线程模型与 Pipeline 一次完整请求路径  
3. 粘包拆包与心跳的具体 Handler 设计  
4. 一次排障：内存泄漏或高延迟的定位过程  
5. 与业务项目的边界：书城用 Spring MVC；长连接推送才上 Netty  

### B.7 路线 B 常见坑

- 只背概念，没有可运行的协议 Demo  
- 在业务 Controller 里强行「用上 Netty」却无长连接场景（显得生硬）  
- 忽略引用计数导致线上泄漏  
- 把 Netty 学完却讲不清和 TCP、HTTP 的关系

## 两条路线对照总表

| 维度 | 路线 A 业务 / AI | 路线 B 中间件 / Netty |
| --- | --- | --- |
| 核心产出 | 可演示、可测试的业务 + AI 作品 | 协议 / 连接 / 高性能网络作品 |
| 必修技术 | 测试、限流、幂等、Spring AI 约束 | Netty、NIO、协议设计、压测 |
| 选修 | 简单了解 Netty 是什么即可 | 业务域知识保持「能读懂」 |
| 本仓库用法 | **主战场：直接在本仓补 P0/P1** | 旁路新仓练手，本仓继续当业务背景 |
| 岗位匹配 | 业务后端、应用 AI 工程 | 中间件、基础架构、音视频/IM 传输 |
| 3 个月 ROI | 通常更高（作品立刻变硬） | 更深但见效慢，适合明确志向 |

## 组合策略（推荐大多数人）

```text
现在 ──► 路线 A（8～12 周）：测试 + 限流 + MQ 幂等 + AI 讲述打磨
              │
              ▼
         作品可面试
              │
              ├── 继续业务岗：加深可观测、压测秒杀、SSE
              │
              └── 转向架构岗：启动路线 B（Netty 小项目独立仓库）
```

**一句话**：先把本仓库做成「工程可信的业务 / AI 作品」；确认要走网络与中间件方向后，再把 Netty 当必修，用独立小仓证明能力，而不是冲淡现有书城叙事。

## 自测题

### 路线 A

1. 为什么 AI 接口比普通查询更需要限流？  
2. MQ「至少一次投递」时，消费者怎样证明自己幂等？  
3. Tool Calling 与「直接让模型编库存」差在哪里？  

### 路线 B

1. Boss 与 Worker EventLoopGroup 各自负责什么？  
2. 粘包问题用哪个常见 Decoder 思路解决？  
3. 为什么 Spring MVC 书城项目通常不必直接依赖 Netty API？  

能答清本路线三题，说明阶段目标清楚；两条都答清，说明你已具备「选型意识」。
