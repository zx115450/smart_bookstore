## 导读
经典 Cache Aside（物理 TTL）在普通读多写下很好用：

```text
读：缓存 → miss → DB → 回填
写：更新 DB → 删缓存
```

但碰到 **热 Key 击穿** 就难受：

```text
爆款商品 detail:{id} 的 TTL 同一时刻到期
  → 上千请求同时 miss
  → 同时打 MySQL
  → 连接打满，全站变慢
```

互斥锁「单飞回源」能减并发，但持锁那个人查库时，其他人要么等、要么也打库。  
**逻辑过期**换一个思路：Key 在 Redis 里先别删光，只在 JSON 里记一个 `expireTime`——过期后 **先返回旧数据**，再让一个人去异步刷新。用户几乎无感，DB 只被轻轻点一下。

本文给出一套可直接落地的封装：逻辑过期 + 互斥锁 + 异步重建，并补上常见坑（线程池关闭、空值 TTL、自旋死等、异步过早解锁）。

---

## 一、三种「过期」分别防什么

| 问题 | 现象 | 典型手段 |
| --- | --- | --- |
| **穿透** | 查根本不存在的 id，每次打 DB | 布隆、空值短缓存 |
| **击穿** | **一个热点** Key 失效，并发打穿 DB | 互斥重建、**逻辑过期** |
| **雪崩** | **大量** Key 同时失效 | TTL 加抖动、多级缓存 |

逻辑过期主打 **击穿**；空值短 TTL 顺手挡一点穿透。它和布隆、物理 TTL Cache Aside **可以组合**，不是互斥。

## 二、核心思想

### 2.1 载荷长什么样

Redis 里不直接存业务 JSON，而是包一层：

```text
{
  "expireTime": "2026-07-26T22:00:00",  // 逻辑过期时间
  "data": { ... 业务对象 ... },
  "absent": false                         // true = DB 无此记录（空值缓存）
}
```

- **逻辑过期**：`now > expireTime`，但 Redis Key **还在**，仍可读出旧 `data`
- **物理 TTL**：给 Key 再设一个更长的 Redis 过期（如逻辑时长 + 1 小时），避免永久占内存；并保证逻辑过期后短时间内 Key 仍在，能返回旧值

### 2.2 读路径一句话

```text
GET Key
  ├─ 没有 → 抢锁回源（别人在建则短等）→ 写逻辑过期缓存
  ├─ absent=true → 当作不存在
  ├─ 未逻辑过期 → 返回 data
  └─ 已逻辑过期 → 返回旧 data；抢到锁则异步查库刷新
```

### 2.3 和「只加互斥锁」的差别

| | 仅互斥 miss 重建 | 逻辑过期 + 异步重建 |
| --- | --- | --- |
| 过期瞬间用户体验 | 可能排队等锁 / 变慢 | **立刻返回旧数据** |
| DB 压力 | 单飞，仍有人阻塞 | 单飞且在后台 |
| 一致性 | 较强 | **短暂脏读是设计内** |

接受「过期后几秒到几分钟可能读到旧值」，才适合上逻辑过期；订单状态、库存余额等强一致读不要用。

## 三、完整落地代码（可复制）

### 3.1 载荷 DTO

```java
public class RedisLogicalData {
    private LocalDateTime expireTime;
    private JsonNode data;
    private boolean absent;

    public RedisLogicalData() {}

    public RedisLogicalData(LocalDateTime expireTime, JsonNode data, boolean absent) {
        this.expireTime = expireTime;
        this.data = data;
        this.absent = absent;
    }
    // getter / setter 省略
}
```

### 3.2 客户端骨架（重点方法）

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class LogicalExpireCacheClient {

    private static final Duration LOCK_TTL = Duration.ofSeconds(30);
    private static final Duration NULL_CACHE_TTL = Duration.ofMinutes(2);
    private static final Duration WAIT_OTHERS_TIMEOUT = Duration.ofSeconds(3);

    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    // 不要 public static：避免容器关闭后任务无法结束
    private final ExecutorService rebuildExecutor = Executors.newFixedThreadPool(10, r -> {
        Thread t = new Thread(r, "logical-expire-rebuild");
        t.setDaemon(true);
        return t;
    });

    @PreDestroy
    public void destroy() {
        rebuildExecutor.shutdown();
        try {
            if (!rebuildExecutor.awaitTermination(60, TimeUnit.SECONDS)) {
                rebuildExecutor.shutdownNow();
            }
        } catch (InterruptedException e) {
            rebuildExecutor.shutdownNow();
            Thread.currentThread().interrupt();
        }
    }

    /** 逻辑过期写入；物理 TTL = 逻辑 + 1h，保证过期后仍能读到旧值一阵。 */
    public void saveWithLogicalExpire(String key, Object value, Duration logicalTtl) throws Exception {
        RedisLogicalData payload = new RedisLogicalData(
                LocalDateTime.now().plus(logicalTtl),
                objectMapper.valueToTree(value),
                false);
        Duration physicalTtl = logicalTtl.plus(Duration.ofHours(1));
        redisTemplate.opsForValue().set(
                key, objectMapper.writeValueAsString(payload), physicalTtl);
    }

    /** 空值短物理 TTL，防穿透；切勿只写死 Key 不设过期。 */
    public void saveAbsent(String key, Duration physicalTtl) throws Exception {
        RedisLogicalData payload = new RedisLogicalData(
                LocalDateTime.now().plus(physicalTtl), null, true);
        redisTemplate.opsForValue().set(
                key, objectMapper.writeValueAsString(payload), physicalTtl);
    }

    public <R, T> R queryWithLogicalExpire(String keyPrefix,
                                           String lockKeyPrefix,
                                           T id,
                                           Class<R> type,
                                           Duration logicalTtl,
                                           Function<T, R> dbLoader) {
        String key = keyPrefix + id;
        String lockKey = lockKeyPrefix + id;
        String json = redisTemplate.opsForValue().get(key);

        if (json == null) {
            return loadOnMiss(key, lockKey, id, type, logicalTtl, dbLoader);
        }

        RedisLogicalData payload = readPayload(json);
        if (payload.isAbsent()) {
            throw new CacheMissException("不存在该项");
        }
        R current = convert(payload.getData(), type);

        if (!LocalDateTime.now().isAfter(payload.getExpireTime())) {
            return current; // 未逻辑过期
        }

        // 已逻辑过期：抢锁异步重建；抢不到说明别人在刷，直接返回旧值
        if (!tryLock(lockKey)) {
            return current;
        }
        rebuildExecutor.execute(() -> {
            try {
                R fresh = dbLoader.apply(id);
                if (fresh != null) {
                    saveWithLogicalExpire(key, fresh, logicalTtl);
                } else {
                    saveAbsent(key, NULL_CACHE_TTL);
                }
            } catch (Exception e) {
                log.warn("rebuild failed, key={}, err={}", key, e.getMessage());
            } finally {
                unlock(lockKey); // 锁必须在异步任务里释放，不要 submit 后立刻 unlock
            }
        });
        return current;
    }

    private boolean tryLock(String lockKey) {
        Boolean ok = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", LOCK_TTL);
        return Boolean.TRUE.equals(ok);
    }

    private void unlock(String lockKey) {
        redisTemplate.delete(lockKey);
    }

    // loadOnMiss：抢锁失败则有限次等待；超时降级查库；成功则写缓存
    // readPayload / convert / CacheMissException 按项目习惯补全
}
```

`loadOnMiss` 建议逻辑（防死循环）：

```text
抢锁失败
  → 最多等 ~3 秒，每 100ms 再 GET
  → 等到数据 / 空值 → 返回或抛不存在
  → 超时再抢一次；仍失败 → 直接查库降级（可不写缓存）
抢锁成功
  → dbLoader
  → 有值 saveWithLogicalExpire；无值 saveAbsent(2min)
  → finally unlock
```

### 3.3 业务侧怎么用

```java
@Service
@RequiredArgsConstructor
public class ProductQueryService {

    private final LogicalExpireCacheClient cacheClient;
    private final ProductRepository productRepository;

    public ProductDetail getDetail(Long id) {
        return cacheClient.queryWithLogicalExpire(
                "product:logical:",
                "product:lock:",
                id,
                ProductDetail.class,
                Duration.ofMinutes(30),
                this::loadFromDb
        );
    }

    private ProductDetail loadFromDb(Long id) {
        return productRepository.findById(id).orElse(null);
    }
}
```

写后若要求尽快一致，可额外 `delete("product:logical:" + id)`，或缩短逻辑 TTL，并接受「未删前仍可能读旧值」。

## 四、时序图（逻辑过期命中）

```text
请求 A、B、C 同时到达（Key 已逻辑过期）
  │
  ├─ A 抢到锁 → 提交异步任务查 DB → 立刻返回旧 JSON
  ├─ B 抢锁失败 → 立刻返回旧 JSON
  └─ C 同上
        │
        └─ 异步线程：写新逻辑过期载荷 → unlock
下一波请求 → 读到新 data
```

对比物理 TTL 击穿：A/B/C 全 miss，可能三人一起查库。

## 五、必须避开的坑

| 坑 | 后果 | 做法 |
| --- | --- | --- |
| 线程池 `public static` 不关闭 | 关应用任务挂起、类加载器泄漏 | 实例字段 + `@PreDestroy shutdown` |
| 空值写入不设物理 TTL | 永久假「不存在」 | `absent` + 短 TTL（如 2 分钟） |
| miss 时 `while(true)` 死等 | 重建失败拖死线程 | 等待超时 + 降级查库 |
| `submit` 后立刻 `unlock` | 多人同时异步刷库 | **在异步 `finally` 里解锁** |
| 锁无 TTL | 进程崩溃死锁 | `SET NX` 带过期（如 30s） |
| 强一致业务用逻辑过期 | 脏读不可接受 | 改回 Cache Aside / 写后删 |

## 六、和 Cache Aside、布隆怎么搭配

推荐分层（电商详情常见）：

```text
① 参数校验
② 布隆 / 空值（挡穿透）
③ 可选：本地 Caffeine L1（降 Redis QPS）
④ 普通商品：物理 TTL Cache Aside
⑤ 已识别的超级热点：逻辑过期客户端
```

不必全站逻辑过期——复杂度和脏读面都会变大。用访问计数把 Top Key 导到逻辑过期路径即可。

| 方案 | 更适合 |
| --- | --- |
| Cache Aside + TTL 抖动 + 删缓存 | 大多数详情、写后要较快一致 |
| 逻辑过期 + 锁 + 异步重建 | 单 Key 极热、可接受短暂旧数据 |
| 秒杀库存 Lua | **写路径扣减**，不是这套读缓存模型 |

## 七、怎么验收

1. **未过期**：连打接口，DB 查询次数为 0（看日志 / 指标）  
2. **改库把 `expireTime` 调到过去**（或等过期）：接口仍 200 且先返回旧值；随后出现一条重建日志；再读变为新值  
3. **并发过期**：压测同一 id，DB QPS 约等于 1（单飞），而不是等于并发数  
4. **DB 无记录**：第二次起应打到空值缓存，短时间内不再打库；约 2 分钟后空值过期  

---

## 八、面试口述（约 1 分钟）

热点详情如果用物理 TTL，到期瞬间容易被打穿到数据库。我们用逻辑过期：Redis 里存数据和逻辑过期时间，物理 Key 多留一段时间。请求发现逻辑过期后先返回旧数据，用 Redis 互斥锁保证只有一个线程异步回源重建，其他人继续读旧值。完全 miss 时也用锁做单飞加载，空值写短 TTL 防穿透。线程池要能优雅关闭，锁要在异步任务结束再释放，等待不能死循环。强一致字段不用这套，普通商品仍用 Cache Aside 就够。

## 小结

| 项 | 建议 |
| --- | --- |
| 存储 | JSON 载荷：`expireTime` + `data` + `absent` |
| 过期 | 逻辑时间判断；物理 TTL 略长于逻辑 |
| 击穿 | 过期后返回旧值 + 锁内异步重建 |
| Miss | 锁 + 有限等待 + 超时降级 |
| 穿透 | 空值短 TTL（可再加布隆） |
| 运维 | 池子 `@PreDestroy`、锁带 TTL、监控重建失败 |

按本文封装后，你得到的是可复用的 **热点读缓存组件**，而不是散落在业务里的 `while(true)` + 裸线程。先在一个爆款详情接口试点，确认脏读可接受，再考虑扩大范围。
