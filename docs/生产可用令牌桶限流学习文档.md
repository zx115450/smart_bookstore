## 导读
秒杀接口最怕两件事叠在一起：

```text
同一时刻 10 万请求冲进来
  → 应用线程打满
  → Redis 库存脚本排队
  → MQ / DB 跟着抖
  → 真正能成交的人反而超时
```

库存 Lua 解决的是 **正确性**（不超卖、一人一单）。  
但它解决不了 **「太多无效请求也要进热路径」**：没抢到的人同样消耗 CPU、连接和脚本执行时间。

这时需要一道 **准入闸门**：先限流，再扣库存。

常见手段：

| 手段 | 特点 |
| --- | --- |
| 网关 `limit_req`（按 IP） | 粗粒度，挡外网扫；挡不住「合法用户海量并发」 |
| 固定窗口 `INCR` + TTL | 实现简单；窗口边界易突刺 |
| 滑动窗口 | 更平滑；实现与存储稍重 |
| **令牌桶** | **允许短时突发，又能把长期速率压在阈值** |

本文落地的是 **分布式令牌桶**：状态放 Redis，多实例共享；用 Lua 保证「读 → 补充 → 扣减 → 写回」原子完成。

## 一、令牌桶在说什么

把限流想成一个水桶：

```text
容量 capacity = 桶能装多少令牌（突发上限）
速率 rate     = 每秒往桶里倒多少令牌
请求          = 每次想拿走 1 个令牌；拿不到就拒绝
```

行为直觉：

- 桶满时，短时间可以「一口气」放行最多 `capacity` 个请求（突发）
- 之后只能按 `rate` 的速度持续放行（稳态 QPS）
- 空闲一段时间后，令牌会补满，再次允许突发

和漏桶对比（面试常问）：

| | 令牌桶 | 漏桶 |
| --- | --- | --- |
| 突发 | **允许**（桶里有存货就能放） | 通常更「匀速出水」 |
| 空闲后 | 可积攒令牌 | 队列被匀速消化 |
| 秒杀场景 | 更常见：活动开始允许一小波冲，再压住 | 更适合严格匀速出站 |

## 二、为什么必须用 Lua（不能 GET + 算 + SET）

错误写法（多实例下会「超发令牌」）：

```text
线程 A：GET tokens=1
线程 B：GET tokens=1
线程 A：算完 SET tokens=0，放行
线程 B：算完 SET tokens=0，也放行   ← 超卖了限流额度
```

正确做法：把「读状态 → 按时间补令牌 → 判断 → 写回」放进 **一条 Lua**，Redis 单线程执行，天然原子。

```text
多实例应用 ──► 同一 Redis Key（活动桶 / 用户桶）
                    ▲
                    │ 一次 EVAL：补令牌 + tryAcquire
```

单机 Guava `RateLimiter` 只护住本 JVM，秒杀多副本时 **必须上 Redis 桶**。

## 三、整体挂载位置（先限流，再扣库存）

推荐调用顺序：

```text
grab(activityId, userId)
  ① 校验活动是否进行中
  ② 幂等：已有结果则直接返回（不耗令牌）
  ③ 令牌桶：活动桶 → 用户桶
  ④ 库存 Lua：扣库存 / 记已抢
  ⑤ 发 MQ 异步落单
```

分层职责：

| 层 | 职责 |
| --- | --- |
| 令牌桶 | **准入**：太火爆则快速失败，保护下游 |
| 库存 Lua | **正确性**：不超卖 |
| DB 唯一键 | **最终**一人一单 |

被限流时返回友好文案即可，例如：「活动太火爆，请稍后再试」（业务错误码与库存售罄分开，便于监控）。

## 四、Redis 里怎么存

用 Hash 存两个字段即可：

```text
Key:   seckill:bucket:act:{activityId}              ← 活动总桶
       seckill:bucket:act:{activityId}:user:{userId} ← 单用户桶
Field: tokens    当前令牌数（浮点字符串也可）
       last_ms   上次更新的毫秒时间戳
```

并设置 TTL（如 2 小时），避免冷活动 Key 永久占内存。

**懒加载**：Key 不存在时，Lua 内视为「满桶」再扣，无需启动预热。

## 五、核心算法（补令牌 + try-acquire）

每次请求带上 `now_ms`（应用传入，避免脚本里取时带来的细微差异争议；也便于单测注入）：

```text
1. HMGET tokens, last_ms
2. 若缺失：tokens = capacity，last_ms = now
3. elapsed = max(0, now - last_ms)          // 时钟回拨当 0，不倒扣
4. tokens = min(capacity, tokens + elapsed * rate / 1000)
5. 若 tokens < acquire：写回 tokens/last_ms，返回 0（拒绝）
6. 否则 tokens -= acquire，写回，返回 1（通过）
```

完整 Lua（可直接放到 `classpath:lua/token_bucket.lua`）：

```lua
-- KEYS[1] = bucket key
-- ARGV[1] = capacity
-- ARGV[2] = refill_per_second
-- ARGV[3] = now_ms
-- ARGV[4] = acquire（通常 1）
-- ARGV[5] = ttl_seconds
-- 返回：1=通过  0=拒绝

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local acquire = tonumber(ARGV[4])
local ttl = tonumber(ARGV[5])

if capacity == nil or capacity <= 0 or rate == nil or rate < 0
        or now == nil or acquire == nil or acquire <= 0 or ttl == nil or ttl <= 0 then
    return 0
end

local data = redis.call('HMGET', key, 'tokens', 'last_ms')
local tokens = tonumber(data[1])
local last = tonumber(data[2])

if tokens == nil or last == nil then
    tokens = capacity
    last = now
end

local elapsed = now - last
if elapsed < 0 then
    elapsed = 0
end

local filled = tokens + (elapsed * rate / 1000.0)
if filled > capacity then
    filled = capacity
end

if filled < acquire then
    redis.call('HSET', key, 'tokens', filled, 'last_ms', now)
    redis.call('EXPIRE', key, ttl)
    return 0
end

filled = filled - acquire
redis.call('HSET', key, 'tokens', filled, 'last_ms', now)
redis.call('EXPIRE', key, ttl)
return 1
```

要点：

- **拒绝时也要写回**：把「已补充但不够扣」的 tokens 存住，否则下次又从旧值算，速率会偏
- **`elapsed < 0` 置 0**：NTP 回拨时不出现负补充
- **浮点 tokens**：亚秒级补充更平滑；若你更想整数，可改成按毫秒累计再整除

## 六、Spring 侧封装

### 6.1 配置项

```yaml
app:
  seckill:
    rate-limit:
      enabled: true
      activity-capacity: 2000          # 活动突发上限
      activity-refill-per-second: 2000 # 活动稳态约 2000 QPS
      user-capacity: 2                # 单用户最多攒 2 个令牌
      user-refill-per-second: 1       # 单用户约 1 QPS
      key-ttl-seconds: 7200
```

调参经验：

- **活动桶**：略高于「下游库存 Lua + MQ 能稳定扛住」的 QPS；过大等于没限流，过小误伤转化
- **用户桶**：保持很小，防脚本刷；正常用户连点两下通常还能过
- 压测库存逻辑时可临时 `enabled: false`

配置类示意：

```java
@ConfigurationProperties(prefix = "app.seckill.rate-limit")
public class SeckillRateLimitProperties {
    private boolean enabled = true;
    private int activityCapacity = 2000;
    private double activityRefillPerSecond = 2000;
    private int userCapacity = 2;
    private double userRefillPerSecond = 1;
    private long keyTtlSeconds = 7200;
    // getter / setter 省略
}
```

记得 `@EnableConfigurationProperties` 或用 `@ConfigurationPropertiesScan` 注册。

### 6.2 限流服务

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class SeckillRateLimitService {

    private static final String ACT_PREFIX = "seckill:bucket:act:";

    private final StringRedisTemplate redis;
    private final SeckillRateLimitProperties properties;
    private DefaultRedisScript<Long> script;

    @PostConstruct
    void init() {
        script = new DefaultRedisScript<>();
        script.setResultType(Long.class);
        script.setScriptSource(
                new ResourceScriptSource(new ClassPathResource("lua/token_bucket.lua")));
    }

    /** 先过活动桶，再过用户桶；任一失败则抛业务限流异常。 */
    public void assertAllowed(Long activityId, Long userId) {
        if (!properties.isEnabled()) {
            return;
        }
        if (activityId == null || userId == null) {
            throw rateLimited();
        }
        long now = System.currentTimeMillis();
        if (!tryAcquire(ACT_PREFIX + activityId,
                properties.getActivityCapacity(),
                properties.getActivityRefillPerSecond(),
                now)) {
            log.info("rate limited by activity bucket, activityId={}", activityId);
            throw rateLimited();
        }
        if (!tryAcquire(ACT_PREFIX + activityId + ":user:" + userId,
                properties.getUserCapacity(),
                properties.getUserRefillPerSecond(),
                now)) {
            log.info("rate limited by user bucket, activityId={}, userId={}", activityId, userId);
            throw rateLimited();
        }
    }

    boolean tryAcquire(String key, int capacity, double refillPerSecond, long nowMs) {
        if (capacity <= 0) {
            return false;
        }
        Long r = redis.execute(
                script,
                List.of(key),
                String.valueOf(capacity),
                String.valueOf(refillPerSecond),
                String.valueOf(nowMs),
                "1",
                String.valueOf(Math.max(60L, properties.getKeyTtlSeconds()))
        );
        return r != null && r == 1L;
    }

    private static RuntimeException rateLimited() {
        // 换成你项目的业务异常与错误码
        return new IllegalStateException("活动太火爆，请稍后再试");
    }
}
```

### 6.3 挂到秒杀入口

```java
public GrabResult grab(Long activityId, AuthPrincipal user) {
    Activity act = loadActive(activityId);           // ①
    Optional<GrabResult> existed = findIdempotent(...); // ②
    if (existed.isPresent()) {
        return existed.get(); // 已抢过：不耗令牌
    }

    rateLimitService.assertAllowed(activityId, user.userId()); // ③

    boolean ok = stockLua.tryGrab(activityId, user.userId());  // ④
    if (!ok) {
        return GrabResult.soldOut();
    }
    mq.sendOrder(...); // ⑤
    return GrabResult.processing();
}
```

**幂等放在限流之前**：重复查询结果不应被限流误伤。

## 七、和网关限流怎么叠加

```text
CDN / 网关（IP、路径 QPS）
    → 应用令牌桶（活动 + 用户）
        → 库存 Lua
            → MQ / DB
```

- 网关：挡扫描、挡整站过载  
- 应用桶：按 **活动**、**用户** 细控，和业务语义对齐  

两者不互斥；只做网关时，同一 NAT 出口下的正常用户可能误伤，只做用户桶时挡不住「百万新用户同时开抢」对库存脚本的冲击。

## 八、边界与坑（上线前必看）

1. **令牌花了但库存没了**  
   限流通过后库存 Lua 返回售罄：属于「占了限流名额但没抢到」。一般 **不要回滚令牌**（实现复杂，收益小）；用户看到售罄即可。

2. **多实例时钟**  
   `now_ms` 来自各应用节点。偏差大会让补充略不均匀，通常可接受；生产保证 NTP。Lua 内对负 `elapsed` 已兜底。

3. **Redis 故障**  
   需明确策略：fail-closed（限流失败则拒绝秒杀，保系统）或 fail-open（放行，保转化但更危险）。秒杀更常见 **fail-closed** 或快速失败降级页。上文示例是脚本执行异常直接向上抛，由统一异常处理。

4. **Key 设计**  
   用户桶带 `activityId`，避免用户参加活动 A 的限流状态污染活动 B。

5. **监控**  
   分开打点：`rate_limited_activity`、`rate_limited_user`、`grab_sold_out`、`grab_success`，调参才有依据。

## 九、怎么自测

### 9.1 单测思路（Mock Redis 或 Testcontainers）

- 连续 `capacity` 次 `tryAcquire` 应成功，第 `capacity+1` 次失败  
- 把 `nowMs` 推进 `1000 / rate` 量级后，应再次成功  
- `assertAllowed`：活动桶耗尽时抛限流；用户桶耗尽时抛限流  

### 9.2 手工用 redis-cli 验 Lua

```bash
redis-cli --eval token_bucket.lua seckill:bucket:act:1 \
  , 2 1 $(date +%s000) 1 3600
# 连打：前 2 次返回 1，随后返回 0；等约 1 秒再打应再出现 1
```

（`ARGV` 前的逗号是 `--eval` 分隔 KEYS/ARGV 的写法。）

### 9.3 压测关注点

- 限流开启后，库存 Lua 的 CPU / 耗时是否下降  
- 限流错误占比是否符合预期（不是全员 429）  
- 用户桶是否误伤正常连点（可适当把 `user-capacity` 调到 3～5）

## 十、面试怎么讲（约 1 分钟）

秒杀热路径上，库存脚本只能保证不超卖，挡不住瞬时洪水。我们在扣库存前加了 Redis 令牌桶：Hash 存当前令牌和上次更新时间，Lua 里按时间补令牌再 try-acquire，保证多实例原子。先过活动桶控总 QPS，再过用户桶防刷。容量决定突发，速率决定稳态。幂等查询放在限流前，避免重复查结果被误伤。和网关 IP 限流叠加，一个挡外网，一个对齐业务维度。

## 小结

| 项 | 建议 |
| --- | --- |
| 存储 | Redis Hash：`tokens` + `last_ms` |
| 原子性 | 一条 Lua 完成补充与扣减 |
| 维度 | 活动桶 + 用户桶 |
| 位置 | 幂等之后、库存 Lua 之前 |
| 突发 | `capacity`；稳态 | `refillPerSecond` |
| 运维 | TTL、开关、分项监控、可关限流做库存压测 |

按本文脚本 + Spring 封装接入后，你得到的是 **多实例共享、可调突发、可按用户防刷** 的秒杀准入层，而不是只能跑在单机内存里的 `RateLimiter` demo。
