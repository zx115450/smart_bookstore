# 向量检索策略与向量库存储单元


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档  
> **关联**：`com.zx.ai.rag` — Embedding / Milvus 策略  
> **索引**：[学习文档中心](./README.md)

向量检索（Vector Search）是把「文本 / 图片 / 音频」变成高维向量后，用相似度在向量库里找最相近的一批结果。本文说明业界常见的检索策略，以及向量库里「一条记录」通常长什么样。

---

## 一、整体链路长什么样

一次典型的语义检索可以拆成五步：

```text
用户问题
   ↓
① 查询理解（可选：改写、扩写、意图分类）
   ↓
② Embedding：query → 查询向量 q
   ↓
③ 向量库检索：在过滤条件下找 Top-K 近邻
   ↓
④ 重排 / 融合（可选：Rerank、关键词分、业务规则）
   ↓
⑤ 回查业务库补全实时字段 → 交给大模型或业务接口
```

要点：

- 向量库负责「语义上像不像」
- 业务库负责「现在库存多少、是否上架」等实时真相
- 二者通常通过 `id` / `metadata` 关联，而不是把全部业务字段塞进向量库

## 二、向量库存储的一个单元是什么

在 Milvus、Qdrant、Pinecone、pgvector 等系统里，**最小可检索单元一般叫一条 Entity / Point / Document / Row**。逻辑上可以看成：

```text
┌─────────────────────────────────────────────┐
│  一条向量记录（Entity）                        │
├──────────────┬──────────────────────────────┤
│ primary key  │ 唯一 ID（如 book:1001）        │
│ vector       │ float[]，维度固定（如 1024）    │
│ payload/meta │ 可过滤、可返回的结构化字段       │
│ text（可选）  │ 当时用于 Embedding 的原文摘要   │
└──────────────┴──────────────────────────────┘
```

### 1. 主键（ID）

- 稳定、可重复写入时覆盖或先删后写
- 常用业务前缀：`book:{id}`、`faq:{index}`、`chunk:{docId}:{n}`
- 作用：更新、删除、幂等重建索引

### 2. 向量（Embedding）

- 由 Embedding 模型输出，例如 `text-embedding-v3` → 1024 维
- **同一 collection 内维度必须一致**
- 检索时比较的是「查询向量」与「库内向量」的距离 / 相似度

常见相似度：

| 度量 | 含义 | 常见场景 |
| --- | --- | --- |
| COSINE | 夹角余弦，关注方向 | 文本语义检索最常用 |
| IP（内积） | 点积 | 已归一化向量时可等价于余弦 |
| L2 | 欧氏距离 | 部分图像 / 稠密特征 |

### 3. 元数据（Metadata / Payload）

不参与「语义远近」计算，但用于：

- **过滤**：只搜上架书、只搜 FAQ、只要某分类
- **回查**：拿到 `bookId` 再查 MySQL
- **分区**：同一 collection 用 `type=book|faq` 隔离业务

示例：

```json
{
  "id": "book:1001",
  "vector": [0.012, -0.088, "...共 1024 维"],
  "metadata": {
    "bookId": 1001,
    "categoryId": 3,
    "type": "book",
    "status": 1
  },
  "text": "深入理解计算机系统 | Randal E. Bryant | 分类:计算机 | 经典体系结构教材..."
}
```

### 4. 原文文本（可选）

很多框架会把「喂给 Embedding 的那段文本」一并存下，便于：

- 调试召回质量
- 直接拼进 Prompt（短文本场景）
- 重建索引时对照

长文档一般不存全书，只存 **chunk 摘要**；详情仍回查对象存储或业务库。

### 5. Collection / Index 层概念

| 概念 | 含义 |
| --- | --- |
| Collection | 一张「向量表」，固定维度与字段 schema |
| Index | 加速近邻搜索的结构（如 IVF_FLAT、HNSW） |
| Partition | 物理/逻辑分区，可按业务拆分（也可只用 metadata 过滤） |

一句话：**一个存储单元 = ID + 向量 + 元数据（+ 可选原文）**。

## 三、从业务对象到向量单元：怎么切

「一条业务数据」不一定对应「一条向量」。

| 策略 | 做法 | 适合 |
| --- | --- | --- |
| 一实体一向量 | 一本书 / 一条 FAQ → 一条向量 | 商品、书目、FAQ |
| 分块（Chunking） | 长文按段切，每段一条向量 | 手册、合同、知识库 |
| 多向量 | 标题一条、正文一条、图片一条 | 需要多路召回时 |
| 父子索引 | chunk 召回，返回父文档 | 长文问答 |

文本怎么写进 Embedding，会直接决定召回质量。常见做法是拼「可检索字段」，而不是 dump 全表：

```text
标题 | 作者 | 分类:xxx | 简介前 N 字
主题 | 答案摘要 | 关键词:a b c
```

原则：

1. 短而密：包含用户可能问到的语义
2. 稳定：同业务主键反复索引结果可覆盖
3. 可过滤字段放 metadata，不硬编码进不可解析的长字符串（除非确实要被语义匹配）

## 四、常见向量检索策略

### 1. 纯向量 Top-K（Dense Retrieval）

最基础：

```text
q = embed(query)
hits = search(q, topK=8, metric=COSINE)
```

再加相似度阈值，过滤过弱结果：

```text
score >= similarityThreshold（如 0.6）
```

优点：实现简单。  
缺点：专有名词、货号、精确短词可能不如关键词。

### 2. 过滤 + 向量（Filtered ANN）

先（或同时）用 metadata 收窄候选，再算近邻：

```text
filter: type == "book" AND status == 1 AND categoryId == 3
then:   vector Top-K
```

这是线上最常用的形态：既要语义，又要业务约束。

### 3. 混合检索（Hybrid：向量 + 关键词）

两路召回再融合：

| 路 | 擅长 |
| --- | --- |
| 稠密向量 | 同义改写、模糊意图 |
| 稀疏 / BM25 / 全文 | 精确词、型号、人名 |

融合方式常见：

- Reciprocal Rank Fusion（RRF）
- 加权分数：`α * dense + (1-α) * sparse`
- 先并集候选，再统一 Rerank

### 4. 多路召回 + 重排（Recall → Rerank）

```text
多路召回（向量 / 关键词 / 协同） → 合并去重 → Cross-Encoder / LLM Rerank → 截断 Top-N
```

适合：候选多、对排序精度要求高的问答与推荐。

### 5. 查询改写后再检索

用户话太短或口语化时：

1. LLM / 规则改写成检索友好句
2. 或多查询（Multi-Query）各搜一遍再合并

### 6. RAG 落地中的「检索策略组合」

企业应用很少只用一种，常见组合是：

```text
metadata 过滤
  → 稠密向量 Top-K
  →（可选）关键词补召
  → 阈值过滤
  → 回查业务库
  →（可选）Rerank
  → 注入 Prompt / 返回卡片
```

## 五、索引与性能策略（简表）

| 索引类型 | 特点 | 适用 |
| --- | --- | --- |
| FLAT | 精确、慢 | 小数据、基线 |
| IVF_FLAT | 聚类加速，可调召回 | 中等规模常用 |
| HNSW | 图索引，延迟低 | 低延迟在线检索 |
| DiskANN 等 | 大数据落盘 | 超大规模 |

工程上通常还要调：

- `topK`：召回宽度（常 5～20）
- `nprobe` / `ef`：精度与延迟权衡
- 相似度阈值：宁缺毋滥时提高阈值

## 六、写入与更新策略

向量不是「设一次永远对」：

| 场景 | 策略 |
| --- | --- |
| 全量重建 | 清空或按前缀删除 → 批量 embed → upsert |
| 增量更新 | 业务变更时按 ID 覆盖单条 |
| 软删除 | metadata 标 status，检索时过滤；定期物理删 |
| 模型升级 | 维度或模型变了 → 必须整库重嵌 |

批量写入时注意限流与批大小，避免 Embedding API 与向量库写入打满。

## 七、一张对照图：业务对象 vs 向量单元

```text
业务库（MySQL）                    向量库（Milvus 等）
─────────────────                  ─────────────────
book 表一行：                      entity 一条：
  id, title, author,                 id = "book:1001"
  stock, price, status...            vector = embed(摘要文本)
  （实时库存、价格）                  metadata = {bookId, type, status...}
                                     text = "书名 | 作者 | 简介..."

检索命中后：
  用 metadata.bookId 回查 MySQL → 补 stock / shelfLocation
```

**不要**指望向量库里的库存字段永远正确；向量库适合「语义索引」，不适合当交易真相源。

## 八、选型与落地检查清单

1. 一条向量对应什么业务粒度（实体 / chunk）？
2. Embedding 模型与维度是否固定、与 collection 一致？
3. 哪些条件必须走 metadata 过滤，而不是全靠语义？
4. Top-K、阈值、是否需要 hybrid / rerank？
5. 更新与删除是否按稳定 ID 可幂等操作？
6. 召回后是否回查业务库补实时字段？

---

## 小结

1. **存储单元** = 主键 + 向量 + 元数据（+ 可选原文），维度固定，靠 ID 更新删除  
2. **检索策略** 从「纯 Top-K」到「过滤 + 向量」「混合检索」「多路召回 + 重排」，按精度与成本递增  
3. **好策略** 通常是：合适的切块与文本拼装 + metadata 过滤 + 适度 Top-K/阈值 + 业务回查  

把「单元长什么样」和「怎么搜」想清楚，再选 Milvus / pgvector 等实现，会少走很多弯路。
