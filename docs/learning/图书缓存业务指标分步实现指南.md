## 零基础：Actuator / Micrometer / Prometheus 是什么

做业务指标时，你其实在串三条链路。先建立心智模型，再写代码。

```text
你的 Java 代码
  bookCacheMetrics.onL1Hit()     ← 业务里「打点」（+1）
        ↓
Micrometer（仪表盘抽象层）
  Counter / Timer / Gauge        ← 统一 API，不绑死某一种监控系统
  MeterRegistry                  ← Spring 注入的「注册表」，所有指标挂在这里
        ↓
Actuator（Spring Boot 运维端点）
  GET /actuator/prometheus       ← 把内存里的指标「打印成文本」给外面看
  GET /actuator/metrics          ← 人类可读的 JSON 列表（调试用）
        ↓
Prometheus（可选，独立进程）
  定时 HTTP 拉 /actuator/prometheus，存成时间序列
        ↓
Grafana（可选）
  画曲线、算命中率
```

三句话记住分工：

| 组件 | 一句话 | 本仓库状态 |
| --- | --- | --- |
| **Micrometer** | 在 Java 里记数 / 计时的库（像「仪表」） | 依赖已有；**业务 Counter 未写** |
| **Actuator** | 把健康检查、指标等挂成 HTTP 接口 | **已配置并放行** |
| **Prometheus** | 定期来拉指标文本并存历史 | 配置样例在 `observability/`；**先不装也能用 curl 验收** |

**关键结论**：C5-C 的验收最低标准是——启动应用后，浏览器打开 `/actuator/prometheus` 能看到你的指标行。不必先装 Prometheus / Grafana。

### 三种常见「仪表」类型

| 类型 | 像什么 | 典型用法 | 本课题 |
| --- | --- | --- | --- |
| **Counter** | 只增不减的计数器 | 请求次数、命中次数 | **必做** |
| **Timer** | 既记次数又记耗时分布 | 回源 DB 花了多久 | 可选 |
| **Gauge** | 可升可降的当前值 | 缓存里现在有多少条 | 可选 |

命中率（百分比）**不要**用业务代码算成 Gauge 再暴露；用两个 Counter，在查询时做除法（见后文 PromQL）。原因：Gauge 只是「某一瞬间的快照」，不好做「最近 5 分钟平均命中率」。

### 名称怎么变：Java → Prometheus

你在代码里写：

```text
bookstore.book.cache.l1.hits
```

Prometheus 文本里通常变成：

```text
bookstore_book_cache_l1_hits_total{application="smart_bookstore",...} 3.0
```

规则（不必死记，以实际 scrape 为准）：

- `.` → `_`
- Counter 常自动加后缀 `_total`
- `{...}` 里是 **标签（tag）**；本仓库全局已挂 `application=...`

## P0：动手摸一遍 Actuator（写代码前必做）

这一节不改任何业务代码。目标是建立「端点长什么样」的直觉。

### P0-1：依赖从哪来

`pom.xml` 里已有（不必复制，打开确认即可）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

- 第一个：提供 `/actuator/*` 这一套 HTTP 端点
- 第二个：把 Micrometer 指标 **翻译成 Prometheus 文本格式**，并注册 `prometheus` 这个端点

没有第二个依赖时，往往只有 `/actuator/metrics`，**没有** `/actuator/prometheus`。

### P0-2：配置在说什么

`application.yaml` 片段：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  endpoint:
    health:
      show-details: when_authorized
  metrics:
    tags:
      application: ${spring.application.name}
```

逐项人话：

| 配置 | 含义 |
| --- | --- |
| `exposure.include` | **允许通过 HTTP 访问**的端点名单。Actuator 默认只暴露很少几个；不写进 include 的端点浏览器打不开 |
| `health` | 活着吗（UP/DOWN） |
| `info` | 应用信息（可为空） |
| `metrics` | JSON 看指标名与当前值（调试友好） |
| `prometheus` | Prometheus 抓取用的纯文本 |
| `metrics.tags.application` | 给**所有**指标自动打上 `application=应用名` 标签，方便多服务区分 |

注意：还有一层 **Security**。本仓库在 `SecurityConfig` 里对下列路径 `permitAll()`（无需登录）：

- `/actuator/health`
- `/actuator/info`
- `/actuator/prometheus`
- `/actuator/metrics`
- `/actuator/metrics/**`

若你本地改过 Security 导致 401，先检查是否误删了这些 matcher。

### P0-6：`/actuator/metrics` 与 `/actuator/prometheus` 怎么选

| 端点 | 适合 | 不适合 |
| --- | --- | --- |
| `/actuator/metrics` | 人眼看、点某个指标名看当前值 | 给 Prometheus 当数据源（格式不对） |
| `/actuator/prometheus` | 给 Prometheus 抓取、用 `findstr`/`Select-String` 验收 | 当「漂亮 API 文档」读（太长） |

开发自测习惯：

1. 先 `metrics` 确认 **名字已出现**
2. 再 `prometheus` 确认 **文本行与标签** 正常
3. 需要历史曲线时再上 Prometheus + Grafana

### P0-7：常见踩坑（P0 阶段）

| 现象 | 排查 |
| --- | --- |
| 连接被拒绝 | 应用没起，或端口不是 8081 |
| 401 / 403 | Security 未放行；对照 `SecurityConfig` |
| 404 且路径像 `/prometheus` | 少了前缀，正确是 `/actuator/prometheus` |
| 有 metrics 无 prometheus | 检查是否缺 `micrometer-registry-prometheus`；或 `exposure.include` 没写 `prometheus` |
| 页面空白 / 极大 | 正常，用命令行 `Select-String` 过滤 |

P0 通过标准：你能在 prometheus 文本里用命令找到至少一行 `jvm_` 或 `http_server_requests`。

## C0：目标与指标清单

### 必做 Counter

| Java 名（Micrometer） | Prometheus 名（约） | 含义 |
| --- | --- | --- |
| `bookstore.book.cache.requests` | `bookstore_book_cache_requests_total` | 用户详情读进入次数 |
| `bookstore.book.cache.l1.hits` | `bookstore_book_cache_l1_hits_total` | Caffeine 命中 |
| `bookstore.book.cache.l2.hits` | `bookstore_book_cache_l2_hits_total` | Redis 命中 |
| `bookstore.book.cache.misses` | `bookstore_book_cache_misses_total` | 回源 MySQL 且查到书 |
| `bookstore.book.cache.bloom.rejects` | `bookstore_book_cache_bloom_rejects_total` | Bloom 判不存在（穿透被挡） |

### 可选

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `bookstore.book.cache.bloom.false.positives` | Counter | Bloom 放行但 DB 无上架书 |
| `bookstore.book.cache.load` | Timer | 仅 miss 回源耗时（DB + 组装 + put） |
| `bookstore.book.cache.l1.size` | Gauge | Caffeine `estimatedSize()` |

命中率用查询计算（先记住公式，C6 再练）：

```text
sum(rate(bookstore_book_cache_l1_hits_total[5m]))
  / sum(rate(bookstore_book_cache_requests_total[5m]))
```

含义：最近 5 分钟，「L1 命中速率 / 请求速率」。没有 Prometheus 时，也可以人工用两次 curl 的差值估算：`Δl1 / Δrequests`。

### 硬性约束

- Counter **禁止**带 `bookId` / `title` 等高基数标签（每个 id 一条时间序列，Prometheus 会爆）
- 区分环境用全局 `application` 标签即可（已配置）
- 一次请求至多记：**1 次 request + 1 次结果分支**（l1 / l2 / miss / bloom.reject 互斥）

## C2：实现 `BookCacheMetrics`

新建包与类：`com.zx.bookstore.catalog.metrics.BookCacheMetrics`。

### 为什么要单独一个类

- 读路径只调用 `onL1Hit()`，不关心 Micrometer API
- 单测里可以 `@Mock BookCacheMetrics`，不用起真实 Registry
- 指标名集中在一处，避免魔法字符串散落

### `MeterRegistry` 是什么

Spring Boot 启动时会创建一个（或多个）`MeterRegistry` Bean。  
你 `@Component` 构造器里写 `MeterRegistry registry`，框架会注入。

- **生产**：通常是复合注册表，其中包含 Prometheus 专用 registry → 数据出现在 `/actuator/prometheus`
- **单测**：可自己 `new SimpleMeterRegistry()`，不启 Spring 也能断言 `counter.count()`

你几乎不需要 `new Counter(...)` 裸构造；统一用 `Counter.builder(...).register(registry)`。

### C2-a：仅 Counter（推荐先做）

```java
package com.zx.bookstore.catalog.metrics;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Component;

@Component
public class BookCacheMetrics {

    private final Counter requests;
    private final Counter l1Hits;
    private final Counter l2Hits;
    private final Counter misses;
    private final Counter bloomRejects;
    private final Counter bloomFalsePositives;

    public BookCacheMetrics(MeterRegistry registry) {
        this.requests = Counter.builder("bookstore.book.cache.requests")
                .description("Book detail read requests")
                .register(registry);
        this.l1Hits = Counter.builder("bookstore.book.cache.l1.hits")
                .description("L1 Caffeine hits")
                .register(registry);
        this.l2Hits = Counter.builder("bookstore.book.cache.l2.hits")
                .description("L2 Redis hits")
                .register(registry);
        this.misses = Counter.builder("bookstore.book.cache.misses")
                .description("Cache miss, loaded from DB")
                .register(registry);
        this.bloomRejects = Counter.builder("bookstore.book.cache.bloom.rejects")
                .description("Bloom rejected (likely not exist)")
                .register(registry);
        this.bloomFalsePositives = Counter.builder("bookstore.book.cache.bloom.false.positives")
                .description("Bloom passed but DB miss")
                .register(registry);
    }

    public void onRequest() {
        requests.increment();
    }

    public void onL1Hit() {
        l1Hits.increment();
    }

    public void onL2Hit() {
        l2Hits.increment();
    }

    public void onMiss() {
        misses.increment();
    }

    public void onBloomReject() {
        bloomRejects.increment();
    }

    public void onBloomFalsePositive() {
        bloomFalsePositives.increment();
    }
}
```

说明：

- `@Component`：启动时就会注册指标；**即使还没人调用**，prometheus 里也可能出现值为 `0` 的行（取决于版本/惰性策略；有的要至少 `increment` 一次才出现——以你环境为准）
- `.description(...)`：会出现在 `# HELP` 注释里
- **不要**在 builder 上 `.tag("bookId", String.valueOf(id))`

写完类、启动应用后，可先搜名字（可能仍为 0）：

```powershell
curl.exe -s http://localhost:8081/actuator/prometheus | findstr bookstore_book_cache
```

若暂时没有行：先发一次图书详情请求（C3 埋点后），再搜。

### C2-b：可选 Timer（回源耗时）

```java
import io.micrometer.core.instrument.Timer;
import java.time.Duration;

private final Timer loadTimer;

// 构造里：
this.loadTimer = Timer.builder("bookstore.book.cache.load")
        .description("DB load + cache put on miss")
        .register(registry);

public void recordLoad(Runnable load) {
    loadTimer.record(load);
}

public void recordLoad(Duration duration) {
    loadTimer.record(duration);
}
```

只包住 **miss 分支**（查库 + `toResponse` + `put`）。  
不要包整段 `getBookDetail`，否则 L1 命中也会进 Timer，语义变成「接口延迟」而不是「回源成本」。

Timer 在 prometheus 里通常拆成多行，例如：

- `bookstore_book_cache_load_seconds_count`（次数）
- `bookstore_book_cache_load_seconds_sum`（总秒数）
- 以及 bucket 相关（若启用了 percentile histogram）

平均耗时可用：`sum / count`（有 Prometheus 时用 `rate(sum)/rate(count)`）。

## C3：埋入 `getBookDetail`

改 `BookCatalogService`：增加字段并注入 `BookCacheMetrics`（若类上已是 `@RequiredArgsConstructor`，加 `private final BookCacheMetrics bookCacheMetrics;` 即可）。

### 改造后伪代码

```java
public BookResponse getBookDetail(Long id) {
    bookCacheMetrics.onRequest();

    if (!bookBloomRedisService.mightContain(id)) {
        bookCacheMetrics.onBloomReject();
        throw BookstoreException.bookNotFound();
    }

    Optional<BookResponse> local = bookCacheFacade.getLocal(id);
    if (local.isPresent()) {
        bookCacheMetrics.onL1Hit();
        bookHotKeyService.recordAccess(id);
        return local.get();
    }

    Optional<BookResponse> redis = bookCacheFacade.getRedis(id);
    if (redis.isPresent()) {
        bookCacheFacade.fillLocal(redis.get());
        bookCacheMetrics.onL2Hit();
        bookHotKeyService.recordAccess(id);
        return redis.get();
    }

    // miss：可选 Timer 包住下面整段
    Optional<Book> bookOpt = bookRepository.findEnabledById(id);
    if (bookOpt.isEmpty()) {
        bookCacheMetrics.onBloomFalsePositive();
        throw BookstoreException.bookNotFound();
    }
    Book book = bookOpt.get();
    // ... toResponse ...
    bookCacheFacade.put(response);
    bookCacheMetrics.onMiss();
    bookHotKeyService.recordAccess(id);
    return response;
}
```

### 与现有代码的差异

当前是：

```java
Book book = bookRepository.findEnabledById(id)
        .orElseThrow(BookstoreException::bookNotFound);
```

要区分 **miss（有书）** 与 **Bloom 假阳性（无书）**，必须先拿 `Optional` 再分支；否则假阳性无法单独计数。

### 打点顺序建议

| 事件 | 建议顺序 |
| --- | --- |
| request | 方法入口最先 |
| bloom.reject | `throw` 之前 |
| l1 / l2 hit | `return` 之前；可与 `recordAccess` 相邻 |
| miss | `put` 成功之后（避免 put 失败却记 miss；若希望「进了 DB」就算 miss，团队统一即可） |
| false.positive | `throw` 之前 |

### 用 Timer 包 miss 的写法示意

```java
bookCacheMetrics.recordLoad(() -> {
    // findEnabledById + toResponse + put
});
bookCacheMetrics.onMiss();
```

假阳性不要放进 Timer 成功路径里和 `onMiss` 混在一起。

## C4：可选 —— 导出 Caffeine Gauge

`BookLocalCacheService` 已 `recordStats()`。若要看板辅助：

先暴露：

```java
public long estimatedSize() {
    return cache == null ? 0L : cache.estimatedSize();
}
```

在 `BookCacheMetrics` 构造（或注入 `BookLocalCacheService` 后）注册：

```java
import io.micrometer.core.instrument.Gauge;

Gauge.builder("bookstore.book.cache.l1.size", localCache, BookLocalCacheService::estimatedSize)
        .description("L1 estimated entry count")
        .register(registry);

Gauge.builder("bookstore.book.cache.l1.hit.rate", localCache,
                c -> c.stats().hitRate())
        .description("Caffeine internal hit rate (0~1)")
        .register(registry);
```

注意：Caffeine 内部 `hitRate` **不含** Bloom 短路；对外汇报命中率仍以业务 Counter 为准。

依赖关系：`BookLocalCacheService` 不要反向依赖 `BookCacheMetrics`，避免循环。

## C5：单测

### C5-a：Metrics 自身（不启 Spring）

```java
@Test
void counters_shouldIncrement() {
    SimpleMeterRegistry registry = new SimpleMeterRegistry();
    BookCacheMetrics metrics = new BookCacheMetrics(registry);

    metrics.onRequest();
    metrics.onL1Hit();

    assertEquals(1.0, registry.find("bookstore.book.cache.requests").counter().count());
    assertEquals(1.0, registry.find("bookstore.book.cache.l1.hits").counter().count());
}
```

`SimpleMeterRegistry` 来自 `micrometer-core`（经 actuator 传递依赖即可用）。

### C5-b：读路径分支（改 `BookCatalogServiceCacheTest`）

1. 增加 `@Mock BookCacheMetrics bookCacheMetrics`
2. 各用例 `verify`：

| 用例 | 期望 |
| --- | --- |
| Bloom 拒绝 | `onRequest` + `onBloomReject`；never `onMiss` / `onL1Hit` |
| L1 命中 | `onRequest` + `onL1Hit`；never `getRedis` |
| L2 命中 | `onRequest` + `onL2Hit` |
| DB miss 回源 | `onRequest` + `onMiss` |
| Bloom 假阳性 | `onRequest` + `onBloomFalsePositive`；never `onMiss` |

字段名需与 `BookCatalogService` 一致，否则 `@InjectMocks` 注不进去。

## C6：手工验收（结合 Actuator）

### C6-1：准备

1. 启动应用  
2. 另开一个终端，先看当前基线（可能没有 bookstore 行，或全是 0）：

```powershell
curl.exe -s http://localhost:8081/actuator/prometheus | findstr bookstore_book_cache
```

3. 准备一个**真实存在**的图书 id，以及一个**肯定不存在**的 id（且尽量让 Bloom 判不存在）

用户详情接口路径以你项目为准（常见需登录 Token）。也可用单测验证逻辑，HTTP 验收作补充。

### C6-2：对照表

| 操作 | 期望在 prometheus 中 |
| --- | --- |
| 访问不存在 id（Bloom 挡） | `...bloom_rejects_total` +1；`misses` 不涨 |
| 冷启动后首次真书 | `misses_total` +1；`requests_total` +1 |
| 同实例立刻再请求同一本 | `l1_hits_total` +1（L1 开启时） |
| 关闭 `local-enabled` 后再打 | 不应再涨 `l1_hits`；可能涨 `l2_hits` |
| 管理端详情 | **上述 Counter 不变** |

### C6-3：用 `/actuator/metrics/{name}` 看单个值

例如：

```text
http://localhost:8081/actuator/metrics/bookstore.book.cache.l1.hits
```

响应里 `measurements[0].value` 即当前累计次数。适合「发 1 次请求 → 刷新页面看是否 +1」。

### C6-4：没有 Grafana 时如何理解「命中率」

记两次采样：

1. 请求前：`requests=100`，`l1_hits=40`  
2. 压一段流量后：`requests=200`，`l1_hits=120`  

则这段增量命中率：

```text
(120 - 40) / (200 - 100) = 0.8
```

有 Prometheus 后，用 `rate()` 自动算滑动窗口，不必手算。

### C6-5：压测对比（有 L1 时）

```text
rate(l2_hits) / rate(requests)  应下降
rate(l1_hits) / rate(requests)  应上升
```

### C6-6：（选做）本仓库 Prometheus 配置在哪

`observability/prometheus/prometheus.yml` 里已有抓取本机 `8081` 的样例。  
**只有当你已经用 Docker / 本机装了 Prometheus 进程时才需要**；C5-C Demo 用 Actuator + curl 就够交差。

## C7：告警思路（选做）

| 症状 | 可能原因 |
| --- | --- |
| `bloom.rejects` 突增 | 扫库 / 爬虫乱 id |
| `misses` 占比长期很高 | TTL 过短、大面积 evict、缓存未写入、开关关了 |
| `l1`+`l2` hits 极低 | Key 错误、实例刚扩容、流量全是新 id |
| `bloom.false.positives` 升高 | 布隆未更新下架、误删 bitmap、预热不全 |

示例（有 Prometheus 时）：

```text
sum(rate(bookstore_book_cache_misses_total[5m]))
  / sum(rate(bookstore_book_cache_requests_total[5m])) > 0.5
```

Demo 不必上 Alertmanager；面试能解释「看占比而不是看绝对值」即可。

## 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 高基数标签 | 永不按 `bookId` 打标签 |
| 重复计数 | 结果分支互斥；`onRequest` 只调一次 |
| 测试变脆 | Metrics 用 Mock + verify，不解析 prometheus 全文 |
| Actuator 暴露面 | 本仓库已 permitAll；生产应内网或加鉴权（注释里已提示） |

回滚：去掉 `BookCacheMetrics` 注入与调用即可；不影响 health 等其它端点。
