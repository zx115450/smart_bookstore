# 学习路线：缓存


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档（加深分册）  
> **索引**：[加深方向](./README.md) · [学习文档中心](../README.md)

本路线围绕「穿透 / 击穿 / 雪崩、布隆过滤器、缓存与 DB 一致」，以本仓库书目 Bloom 与借阅到期 Redis 为锚点，目标是能设计缓存并说清一致性与失效策略。

---

## 学习目标

学完后应能：

1. 区分缓存穿透、击穿、雪崩，并各给出至少一种防护手段
2. 说明布隆过滤器的误判特性，以及本项目用它挡什么流量
3. 画出「读路径 / 写路径」上缓存与 MySQL 的更新顺序，指出不一致窗口
4. 针对图书详情或列表，设计一套可落地的缓存 Key、TTL、失效方案

预计投入：2～3 周。

### C2：吃透书目 Bloom（3～4 天）

详解文档：[布隆过滤器](./布隆过滤器.md)

回答：

1. `BloomFilterSpec.of(expectedElements, falsePositiveRate)` 如何影响误判率与内存？

   - `expectedElements`（`n`）与 `falsePositiveRate`（`p`）共同决定位图长度 `m` 与哈希个数 `k`：  
     `m ≈ −n·ln(p)/(ln2)²`，`k ≈ (m/n)·ln2`（本仓库再限制 `m≥64`、`k∈[1,16]`）
   - **`p` 更小**（更不容忍误判）→ `m` 更大 → **Redis Bitmap 更占内存**，假阳性更少
   - **`n` 更大**（书更多）→ `m` 更大 → 内存上升；若实际插入远超配置的 `n`，真实误判率会 **高于** 设定的 `p`
   - 粗算内存约 `⌈m/8⌉` 字节（另加 Redis 对象头）；改 `n`/`p` 后 `m`/`k` 变了，必须 `rebuild`，不能只改配置

2. 为何用 Redis Bitmap 自实现，而不是 RedisBloom 模块？

   - **零模块依赖**：标准 Redis 的 `SETBIT`/`GETBIT` 即可，云托管 / 裸 Redis 都能跑，不必装 Redis Stack
   - **多实例共享**同一 Key（`book:bloom:ids`），又不必每台 JVM 各维护一份 Guava Bloom
   - 书目规模下自研成本可控，参数与 fail-open、预热路径都在应用内，便于讲清原理；有 Stack 且想少写哈希细节时再上 `BF.ADD`/`BF.EXISTS` 即可

3. 启动 `rebuild` 与运行时 `add` 分别解决什么？漏加会怎样？

   - **`rebuild`（启动预热）**：`DEL` 位图后把 DB 里已有全部 bookId 灌进去，解决「历史数据 / Redis 被清空」后过滤器为空的问题
   - **`add`（运行时）**：`createBook` 成功后增量置位，解决「预热之后新上架的书」不在过滤器里的问题
   - **漏加**：真书 `mightContain=false` → 用户详情直接 404（**假阴性，比假阳性严重**）。预热失败或 create 后未 `add` 都会出现，需盯日志并保证写路径调用 `add`

4. 图书下架 / 删除时 Bloom **不能**可靠删除，业务上如何接受误判？

   - 经典布隆 **不能删**：清某个 bit 可能伤到其他 id，造成假阴性
   - **下架 / 删除后 id 仍占位**：用户再查该 id 时 Bloom 说「可能存在」→ 多打一次缓存 miss + DB → `findEnabledById` 仍 404，**结果正确，只是多一次查询**
   - 业务上接受「少量多余 DB」，换「绝不误杀仍在架的书」；管理端详情 **不走 Bloom**，以便排查下架书。若删除极频繁且必须回收位，再考虑 Counting Bloom / Cuckoo 等可删方案

产出：Bloom 读写时序图 + 「误判为存在」时的代码路径说明（见专题文 §7）。

### C3：缓存与 DB 一致性（4～5 天）

练习题（可在本项目图书详情上设计，哪怕尚未实现满血缓存）：

1. Cache Aside：先更新 DB 再删缓存，为何比「先更新缓存」更常见？

   - Cache Aside 读路径：先缓存，miss 再读 DB 并回填；写路径常见是 **先写 DB，再删缓存（或让其过期）**
   - **先改缓存再写 DB** 的问题：DB 写失败时缓存已是新值 → 脏缓存；或并发下缓存与 DB 长期不一致且难以回滚
   - **先写 DB 再删缓存**：DB 是权威；删缓存失败最多短暂读到旧值，下次写或 TTL 可收敛；读请求不会「写脏缓存当权威」
   - 仍有经典并发窗口（删缓存前另一线程把旧值回填），但比「缓存当写权威」好控；本仓库图书详情即 Cache Aside（`get` miss → DB → `put`；更新后应 `delete` 详情 Key）

2. 延迟双删适用什么场景？有什么坑？

   - **场景**：写库后立刻删缓存，但仍担心「并发读把旧值又 put 回去」——做法是：删一次 → 写 DB →（或写完再删）→ **sleep 一小段**（覆盖典型读回填耗时）→ **再删一次**
   - **适用**：读多写少、能接受写路径稍慢、并发读旧值回填概率需要压到更低的详情 / 配置类缓存
   - **坑**：
     - sleep 时长难定（太短无效，太长拖慢写、占线程）
     - 二次删除仍可能失败，需要重试 / 消息异步删
     - 不能从根上消灭所有竞态，只是降低窗口
     - 与「只删一次 + 合理 TTL」相比复杂度更高；流量一般时往往 **单次删缓存 + TTL 抖动** 就够

3. 秒杀库存为何倾向「Redis 为扣减权威、DB 异步对齐」，而不是经典 Cache Aside？

   - 秒杀是 **热点写 + 强并发扣减**，不是「读多写少的详情缓存」
   - Cache Aside 以 DB 为权威：每次扣减打 DB / 靠 DB 行锁，热 Key 会把数据库打爆，且难做超高 QPS 原子扣减
   - 本仓库做法：活动预热把库存打进 Redis；`grab` 用 **Lua 原子扣库存 + 记用户 Set**；成功后再 **MQ 异步落单 / 发券**，DB 做最终记录与唯一键兜底
   - Redis 是热路径权威，DB 是异步对齐与对账；MQ 失败要 **rollbackGrab**，死信要 reconcile——这是「缓存当库存」付出的补偿成本，换的是削峰与不超卖

产出：两种业务（书目只读缓存 vs 秒杀库存）的一致性策略对比短文。

**对比短文（参考）**

书目详情是典型读多写少：MySQL 存权威数据，Redis 只做加速。读走 Cache Aside（Bloom → 缓存 → DB → 回填）；写走「更新 DB 后删详情缓存」，短暂不一致可接受，靠 TTL 与删 Key 收敛。目标是少打库、最终读到正确书讯，不要求缓存参与扣减。

秒杀库存则相反：瞬时写压力极大，若仍以 DB 为扣减权威，行锁与连接扛不住。于是把「能否扣成功」前移到 Redis Lua，DB / 订单通过 MQ 异步对齐，并用唯一索引与回滚 / 对账修补「Redis 已扣、落库失败」等空洞。这里 Redis 不是旁路缓存，而是热路径库存状态机的一部分。

一句话：详情缓存怕的是脏读与穿透，用删缓存 + TTL；秒杀怕的是超卖与打爆 DB，用 Redis 原子扣减 + 异步落库 + 补偿。

## 能力自检

### 1. 能用业务语言解释穿透 / 击穿 / 雪崩

- [x] 见下

| 问题 | 业务说法（书城场景） | 典型防护（本仓库） |
| --- | --- | --- |
| **穿透** | 有人（或爬虫）疯狂查「根本不存在的 bookId」：缓存没有、DB 也没有，每次都打穿到 MySQL | 布隆先挡（`mightContain=false` → 404）；可选空值短 TTL |
| **击穿** | 一本超级热门书的缓存刚好过期，同一瞬间大量请求同时 miss，一起去打 DB | 热点加长 TTL（C5-B）；互斥重建 / 逻辑过期（可选）；TTL 抖动降低「刚好同时过期」 |
| **雪崩** | 大批 Key 用同一 TTL、同一时刻过期（或 Redis 宕机），流量瞬间全压到 DB | TTL + 抖动；多级缓存（L1+L2）；限流 / 降级；Redis 高可用 |

一句话区分：**穿透**打的是「不存在的数据」；**击穿**打的是「某一个热点刚过期」；**雪崩**打的是「一大片同时失效」。

### 2. 能说明 Bloom 误判为 true / false 时各有什么影响

- [x] 见下

布隆只有两种答案：`mightContain=true`（可能存在）、`false`（一定不存在）。**不会**对「一定存在」给出 100% 保证。

| 判定 | 实际 | 名称 | 业务影响（本仓库用户详情） |
| --- | --- | --- | --- |
| `false` | 确实没有 | 正确拒绝 | 直接 404，不打缓存 / DB — 防穿透成功 |
| `false` | 其实有这本书 | **假阴性** | 真书被当成不存在 → **误 404**，比假阳性严重；常见于漏 `add` / 预热失败 |
| `true` | 确实有 | 正确放行 | 继续走 L1 → L2 → DB |
| `true` | 其实没有（含已下架仍占位） | **假阳性** | 多走一次缓存 miss + DB，`findEnabledById` 仍 404；**结果对，多一次查询** |

本仓库策略：宁可接受假阳性多打库，也要避免假阴性误杀在架书；下架不能从经典 Bloom 可靠删除，管理端详情不走 Bloom。

### 3. 能画出书目 Bloom 预热与增量 `add` 的生命周期

- [x] 见下

```text
应用启动
  → BookBloomWarmupRunner
  → BookBloomRedisService.rebuild()
       DEL book:bloom:ids
       扫描 DB 全部 bookId → 逐个 SETBIT
  → 过滤器就绪（历史书可查）

运行中 createBook 成功
  → bookBloomRedisService.add(newId)   ← 增量置位
  → 新书立刻能通过 mightContain

用户 getBookDetail(id)
  → mightContain(id)?
       false → 404（穿透被挡）
       true  → L1 / L2 / DB …

下架 / 删除
  → 位图通常不删该 id（经典 Bloom 不能可靠删除）
  → 再查：Bloom 仍可能 true → DB 查无上架书 → 404
  → 位图膨胀或误判升高时：择机全量 rebuild
```

漏加后果：真书 `mightContain=false` → 用户侧直接 404（假阴性）。预热失败或 create 后未 `add` 都要盯日志。

### 4. 能对比秒杀库存缓存与只读书目缓存的一致性模型差异

- [x] 见下（与上文 C3「对比短文」同旨）

| 维度 | 书目详情（只读加速） | 秒杀库存 |
| --- | --- | --- |
| 业务形态 | 读多写少 | 瞬时热点写、强并发扣减 |
| 权威数据 | **MySQL** | 热路径 **Redis**（Lua 扣减）；DB 异步落单 / 对账 |
| 读路径 | Cache Aside：Bloom → 缓存 → DB → 回填 | 抢购读的是 Redis 库存状态，不是「详情缓存」 |
| 写路径 | 先写 DB，再 **删缓存** | Redis 原子扣成功后再 MQ 写 DB；失败要 rollback / 对账 |
| 不一致容忍 | 短暂脏读可接受，TTL + 删 Key 收敛 | 不能超卖；用 Lua + 唯一键 + 补偿换正确性 |
| 缓存角色 | **旁路加速** | **热路径状态机的一部分** |

一句话：详情怕脏读与穿透，用删缓存 + TTL；秒杀怕超卖与打爆 DB，用 Redis 原子扣减 + 异步落库 + 补偿。

### 5. 知道缓存不是银弹：哪些数据不该缓存

- [x] 见下

适合缓存：读多写少、可接受短暂不一致、体量可控、Key 稳定的数据（如图书详情、分类名、配置项）。

**不宜或要谨慎缓存：**

| 类型 | 原因 |
| --- | --- |
| 强一致余额 / 库存扣减（若仍以 DB 为准且写极热） | 缓存易脏；要么别当旁路缓存，要么改成 Redis 权威 + 补偿（秒杀那套） |
| 个性化实时结果（每人每页都不同） | Key 爆炸、命中率低，可能更慢 |
| 大对象 / 大列表整页硬塞 | BigKey、网络与序列化成本高；宜分页或拆字段 |
| 权限 / 敏感令牌若 TTL 过长 | 撤销不及时有安全风险（会话黑名单要另设计） |
| 写入极频繁且读很少的数据 | 写放大，收益为负 |
| 必须「读己之写」且窗口为零的场景 | 单靠 Cache Aside 很难，需要同步方案或绕过缓存 |

经验法则：先问「脏了多久能接受」「QPS 是否值得」「失效是否好做」；答不上来就先别加缓存。
