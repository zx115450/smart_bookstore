# C5：缓存增强分步实现指南


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档（加深分册）  
> **索引**：[加深方向](./README.md) · [学习文档中心](../README.md)

对应 [缓存学习路线](./缓存.md) 的 C5 扩展课题。把三件事拆成可落地的小步：**本地 Caffeine + Redis 二级缓存**、**热点 Key 探测与加长 TTL**、**命中率 / 穿透指标接入 Prometheus**。

本文是实现指南，不要求一次全做完；建议按 A → B → C 顺序，每阶段可独立联调与回滚。

读路径（C5-A 已落地）：

```text
getBookDetail
  → Bloom.mightContain（false → 404）
  → L1 Caffeine（hit → 返回）
  → L2 Redis（hit → 回填 L1 → 返回）
  → MySQL → put L2+L1 → 返回
```

目标读路径（做完 B+C 后还可叠加热点 TTL 与指标）：

```text
getBookDetail
  → 指标：请求计数
  → Bloom（false → 穿透拦截计数 → 404）
  → L1 Caffeine（hit → L1 命中计数 → 返回）
  → L2 Redis（hit → 回填 L1 → L2 命中计数 → 返回）
  → MySQL → 写 L2（热点则长 TTL）→ 写 L1 → miss 计数 → 返回
```

## C5-A：Caffeine + Redis 二级缓存

### A0：目标与验收

- 读路径：先 L1，再 L2，再 DB；L2 命中时回填 L1
- 写路径：`evict` 时 **同时清 L1 + L2**（本机至少清掉自己的 L1）
- 开关：`bookstore.cache.local-enabled`，默认可先 `false`，联调再开
- 验收：连续两次查同一本书，第二次不再打 Redis（可用日志或 metrics 验证）

### A1：加依赖

`pom.xml`：

```xml
<dependency>
    <groupId>com.github.ben-manes.caffeine</groupId>
    <artifactId>caffeine</artifactId>
</dependency>
```

Spring Boot 会管理版本；若用 `spring-boot-starter-cache` 亦可，本指南偏向 **手写 Cache 实例**，便于和现有 `BookRedisService` 并列，不强绑 `@Cacheable`。

### A2：扩展配置

在 `BookstoreCacheProperties` / `application.yaml` 增加例如：

```yaml
bookstore:
  cache:
    enabled: true
    local-enabled: true
    local-max-size: 2000
    local-expire-seconds: 60          # L1 宜短，降低多实例脏读窗口
    detail-ttl-seconds: 1800
    detail-ttl-jitter-seconds: 300
```

含义：

| 项 | 建议 |
| --- | --- |
| `local-max-size` | 按实例内存定，先 1k～5k |
| `local-expire-seconds` | **远短于** Redis TTL（如 30～120s），多实例无广播时靠短 TTL 收敛 |

### A3：实现 `BookLocalCacheService`（示例骨架）

新建 `com.zx.bookstore.catalog.service.BookLocalCacheService`：

```java
@Service
public class BookLocalCacheService {

    private final BookstoreCacheProperties props;
    private Cache<Long, BookResponse> cache;

    @PostConstruct
    void init() {
        cache = Caffeine.newBuilder()
                .maximumSize(Math.max(100, props.getLocalMaxSize()))
                .expireAfterWrite(Duration.ofSeconds(Math.max(5, props.getLocalExpireSeconds())))
                .recordStats() // 便于 C5-C 导出
                .build();
    }

    public Optional<BookResponse> get(Long id) {
        if (!props.isLocalEnabled() || id == null) {
            return Optional.empty();
        }
        return Optional.ofNullable(cache.getIfPresent(id));
    }

    public void put(BookResponse response) {
        if (!props.isLocalEnabled() || response == null || response.getId() == null) {
            return;
        }
        cache.put(response.getId(), response);
    }

    public void evict(Long id) {
        if (id != null) {
            cache.invalidate(id);
        }
    }

    public CacheStats stats() {
        return cache.stats();
    }
}
```

注意：`BookResponse` 若会被调用方修改，应放入不可变副本或保证 DTO 只读，避免污染缓存。

### A4：改造读路径 `getBookDetail`

伪代码顺序（Bloom 仍最前）：

```text
if !bloom.mightContain(id) → 404

local = localCache.get(id)
if local.isPresent → return local

redis = bookRedis.get(id)
if redis.isPresent:
    localCache.put(redis.get())
    return redis.get()

load DB → toResponse
bookRedis.put(response)
localCache.put(response)
return response
```

### A5：改造写路径失效

凡调用 `bookRedisService.evict(id)` 处（`updateBook`、下架等）**同步**：

```java
bookRedisService.evict(id);
bookLocalCacheService.evict(id);
```

可抽一个 `BookCacheFacade.evict(id)`，避免漏清。

### A6：多实例脏读（必读）

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| **短 L1 TTL**（推荐先做） | L1 60s 内可能脏，之后自动过期 | 实现简单 |
| Redis Pub/Sub 失效广播 | 写后 publish `book:evict`，各实例 invalidate | 稍复杂 |
| 不放会变字段 | L1 只缓存极少变字段 | 模型要拆 |

Demo 阶段用短 TTL 即可；面试要能说出 Pub/Sub 方案。

### A7：自测清单

- [x] `local-enabled=false` 行为与改造前一致（单测 `BookLocalCacheServiceTest`）
- [x] 开启后：L1 / L2 / miss 分支（单测 `BookCatalogServiceCacheTest`）
- [x] 更新 / 下架走 `BookCacheFacade.evict`（L1+L2）
- [ ] 另一实例在 L1 TTL 内可能旧，TTL 后变新（接受或再做广播；手工多实例验证）

**已实现入口**：`bookstore.cache.local-enabled`（默认 `true`）；关闭即退回仅 Redis。

### 可选工具：逻辑过期客户端（未挂到图书详情默认读路径）

封装类：`com.zx.bookstore.cache.logical.LogicalExpireCacheClient`

对外实战叙述：[生产可用逻辑过期缓存学习文档](../生产可用逻辑过期缓存学习文档.md)

- 逻辑过期 + Redis 互斥锁 + 异步重建
- 空值短物理 TTL；线程池 `@PreDestroy` 关闭；miss 等待带超时
- 适用超级热点读；图书详情默认仍用 Cache Aside（A 已落地）。挂载示例：

```java
logicalExpireCacheClient.queryWithLogicalExpire(
    "book:logical:", "book:lock:", id, BookResponse.class,
    Duration.ofMinutes(30), this::loadBookFromDb);
```

## C5-B：热点书 Key 自动探测与加长 TTL

### B0：目标与验收

- 访问频繁的 `bookId` 被识别为热点
- 热点写入 Redis 时使用 **更长 TTL**（可另加更小 jitter）
- 非热点仍走原 `detail-ttl-seconds`
- 验收：压一个 id 超过阈值后，Redis 上该 Key 的 TTL 明显大于普通书

### B1：配置

```yaml
bookstore:
  cache:
    hot-key:
      enabled: true
      window-seconds: 60           # 滑动/固定窗口长度
      threshold: 50                # 窗口内访问次数 ≥ 此值视为热点
      detail-ttl-seconds: 7200     # 热点 Redis TTL（如 2h）
      detail-ttl-jitter-seconds: 600
      max-tracked-keys: 5000       # 防计数器本身爆内存
```

### B2：选探测方案（三选一，由易到难）

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| **B2-a 本机窗口计数** | Caffeine/ConcurrentHashMap：`id → 窗口计数` | 单机或热点在各实例均匀时够用 |
| **B2-b Redis 计数** | `INCR book:hot:cnt:{id}` + `EXPIRE` 窗口 | 多实例汇总真实热度 |
| **B2-c Top-K 近似** | Redis + 定时扫 / Count-Min | 书目极大时再上 |

推荐 Demo 先做 **B2-a**，生产多副本再升级 **B2-b**。

### B3：实现 `BookHotKeyService`（B2-a 骨架）

```java
@Service
public class BookHotKeyService {

    // key=bookId, value=当前窗口计数；也可用 Caffeine expireAfterWrite(window)
    private final ConcurrentHashMap<Long, AtomicLong> counters = new ConcurrentHashMap<>();
    private final AtomicLong windowStartMs = new AtomicLong(System.currentTimeMillis());

    public void recordAccess(Long bookId) { /* 窗口滚动 + incr */ }

    public boolean isHot(Long bookId) {
        // count >= threshold
        return false;
    }
}
```

窗口滚动要点：

- 固定窗口：`now - windowStart >= windowSeconds` 则 `counters.clear()` 并重置起点（简单，边界有突刺）
- 或每个 key 自带过期时间戳（更平滑，实现稍繁）

### B4：接到读路径与 `put`

在 `getBookDetail` **每次成功准备返回前**（含 L1/L2/DB 任一命中）调用：

```java
bookHotKeyService.recordAccess(id);
```

改造 `BookRedisService.put`（或增加重载）：

```java
public void put(BookResponse response) {
    Duration ttl = bookHotKeyService.isHot(response.getId())
            ? hotTtlWithJitter()
            : ttlWithJitter();
    redis.opsForValue().set(key(response.getId()), json, ttl);
}
```

L2 miss 回源写入时用长 TTL；若希望「已是短 TTL 的 Key 变热后立刻变长」，可在判定热点后 `EXPIRE` 续期（可选一步）：

```text
if isHot(id) && redis.exists(key):
    redis.expire(key, hotTtl)
```

### B5：与击穿防护的关系

加长 TTL **降低**热点同时过期概率，但不能替代：

- 互斥重建（单飞加载）
- 逻辑过期 + 异步刷新

若只做 B，至少保证：热点 TTL ≫ 普通 TTL，且 jitter 足够。

### B6：自测清单

- [x] 冷门书：`TTL` 约在 `detail-ttl ± jitter`（默认 `1800 + 0~300`）
- [x] 对单 id 压过 `threshold`：HotKeyService 判定为 hot，下次 `put` 使用 `hot-detail-ttl`（单测 `BookHotKeyServiceTest`、`BookRedisServiceHotTtlTest`）
- [x] `hot-key-enabled=false` 时全员普通 TTL（`BookHotKeyService` 空操作）
- [x] `hot-max-tracked-keys` 通过外层 Caffeine `maximumSize` 控制；`expireAfterAccess` 自动淘汰冷 key

**已实现入口**：`bookstore.cache.hot-key-enabled`（默认 `true`）。关闭后仅使用普通 `detail-ttl-seconds`。

## C5-C：命中率 / 穿透次数接入 Prometheus

**完整步骤（骨架代码、Timer、单测、PromQL、假阳性分支）见专项文档：**

→ [图书缓存业务指标分步实现指南](./图书缓存业务指标分步实现指南.md)

### 摘要

在 `/actuator/prometheus` 暴露业务 Counter（禁止按 `bookId` 打标签）：

| 指标（Prometheus 约） | 含义 |
| --- | --- |
| `bookstore_book_cache_requests_total` | 详情读总次数 |
| `bookstore_book_cache_l1_hits_total` | Caffeine 命中 |
| `bookstore_book_cache_l2_hits_total` | Redis 命中 |
| `bookstore_book_cache_misses_total` | 回源 DB |
| `bookstore_book_cache_bloom_rejects_total` | Bloom 穿透被挡 |

打点位：

```text
进入 → onRequest
Bloom false → onBloomReject → 404
L1 hit → onL1Hit
L2 hit → onL2Hit
DB 有 → onMiss
DB 无 → onBloomFalsePositive（可选）
```

管理端 `getBookDetailAdmin` 不打点。命中率用 PromQL，不必再做百分比 Gauge。

### 自测清单（摘要）

- [ ] 不存在 id：`bloom.rejects` +1，无 miss
- [ ] 首次真书：`misses` +1；同实例再请求：`l1` / `l2` hits +1
- [ ] prometheus 能搜到 `bookstore_book_cache`
- [ ] 开 L1 后 `l2.hits` 占比下降

## 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| L1 脏数据 | 短 TTL；写路径必 evict；问题期间 `local-enabled=false` |
| 热点误判 | 提高 `threshold`；热点 TTL 别无限 |
| 指标基数爆炸 | Counter **不要**带 `bookId` 标签 |
| 计数器占内存 | `max-tracked-keys`、窗口清理 |

回滚：三个功能均应有独立开关，关掉即回到「仅 Redis + Bloom」。
