# 学习路线：消息队列


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档（加深分册）  
> **索引**：[加深方向](./README.md) · [学习文档中心](../README.md)

本路线围绕「可靠投递、死信、幂等消费、顺序消息」，以本仓库秒杀发券与订单超时为锚点，目标是能设计异步链路并处理重复与失败。

---

## 学习目标

学完后应能：

1. 说明 Producer 确认、Broker 持久化、Consumer ACK 各自防什么丢消息
2. 设计幂等消费：业务唯一键 + 状态判断，并指出仅靠「防重表」不够的情况
3. 讲清死信队列（DLQ）何时进入、如何人工 / 自动对账
4. 判断本项目哪些场景需要顺序消息，哪些只需要最终一致

预计投入：2～4 周。

---

## 与本项目的映射 

| 概念 | 本仓库落点 |
| --- | --- |
| 秒杀异步发券 | `SeckillMqProducer` → `SeckillOrderConsumer` |
| 秒杀死信对账 | `SeckillService.reconcileDeadLetter`（及对应 DLQ 消费者，若有） |
| 订单超时 | `TradeMqConfig`、`TradeMqProducer`、超时队列 |
| 超时死信 | `TradeOrderTimeoutDeadLetterConsumer`；仍失败写入 `trade_order_timeout_fail` 后 Ack；管理端 `GET /api/admin/trade/timeout-fails` |
| 消费幂等 | 秒杀落库前查重；订单超时按状态机取消 |
| 事务后发消息 | `TradeService` 中 `TransactionSynchronization`（提交后再发，避免脏消息） |
| 消费本地重试 | 默认 `strategy: queue`（`*.retry` TTL 回主队列）；可选 `local`；见 [MQ 重试文档](./MQ本地重试与Spring-Template学习文档.md) |

建议先读项目实操指南：[RabbitMQ 使用指南](../RabbitMQ使用指南学习文档.md)，再对照源码：

- `bookstore/seckill/config/RabbitMqConfig.java`（或同包 MQ 配置）
- `bookstore/trade/config/TradeMqConfig.java`
- `SeckillOrderConsumer`、`TradeOrderTimeoutDeadLetterConsumer`
- `com.zx.config.mq`（重试：默认 QUEUE，可选 LOCAL）

## 阶段规划

### M1：消息模型与投递语义（2～3 天）

- 队列、交换机、路由键、绑定
- at-most-once / at-least-once / exactly-once（实务中多为 at-least-once + 幂等）
- 持久化消息、持久化队列、Publisher Confirm、Consumer ACK / NACK / 重入队

详解文档：[消息模型与投递语义](./消息模型与投递语义.md)

产出：一张「丢消息可能发生在哪一层」的图（见该文档第 6 节）。

### M2：吃透秒杀异步链路（3～5 天）

```text
Lua 成功 → 发 MQ → Consumer 写订单 + 发券
         ↘ 失败：回滚 Redis / 进 DLQ / 对账
```

回答：

1. 为何不在 grab 请求线程里同步写 DB？
2. 消息体需要哪些字段才能幂等？（activityId、userId、idempotencyKey…）
3. Consumer 重复消费两次，第二次应如何表现？
4. 「Lua 已扣、消息永久丢失」如何发现与修复？

产出：秒杀 MQ 故障矩阵（重复、丢失、乱序、积压）。

### M3：吃透订单超时与 DLQ（3～5 天）

- 延迟实现方式：TTL + DLX、延迟插件、还是定时扫表？本项目用哪一种？
- 消息到期后谁负责取消订单、回库存 / 回券？
- `TradeOrderTimeoutDeadLetterConsumer` 与「正常超时队列」职责如何划分？
- 为何强调「事务提交后再发超时消息」？

产出：从 `createOrder` 到超时取消的时序图。

### M4：幂等与顺序（3～4 天）

| 主题 | 练习 |
| --- | --- |
| 幂等 | 为 Consumer 补「先查后写 / 唯一索引 catch」测试 |
| 顺序 | 说明秒杀发券是否要求全局顺序；若多实例消费如何分片 |
| 积压 | 观察队列深度指标；设计降级（暂停活动、扩容消费者） |
| 毒消息 | 重试次数耗尽进 DLQ，避免死循环打爆 DB |

### M5：扩展课题（选做）

- 本地消息表 / 事务消息（对比 RocketMQ）与当前「Confirm + 回滚 Redis」
- Outbox 模式与 Spring 事务同步的取舍
- 将关键指标挂到 Prometheus：发送失败率、消费延迟、DLQ 深度

## 推荐阅读与练习顺序

1. RabbitMQ 官方：ACK、DLX、TTL
2. 精读本仓库 `TradeMqConfig` 与秒杀 MQ 配置
3. 对照 `SeckillService`：发送失败回滚与 `reconcileDeadLetter`
4. 写集成测：投递一条超时消息，断言订单变为取消态
5. 口述：「至少一次投递下如何保证只发一张券」

## 面试口述提纲（示例）

1. 秒杀要削峰：Lua 占库存后发 MQ，接口立即返回排队中  
2. 投递：关注发送失败时回滚 Redis；消费侧用唯一约束与状态幂等  
3. 订单超时：延迟消息 + DLQ，取消时校验仍为待支付  
4. 监控 DLQ 与积压；对账补发或回滚库存  
5. 不做全局顺序，按活动 / 订单维度保证业务正确即可
