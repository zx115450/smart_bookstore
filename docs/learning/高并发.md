# 学习路线：高并发


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档（加深分册）  
> **索引**：[加深方向](./README.md) · [学习文档中心](../README.md)

本路线围绕「库存一致性、超卖、削峰、延迟队列、对账」，以本仓库秒杀与订单超时为锚点，目标是能讲清设计、失败兜底与验证手段。

## 学习目标

学完后应能：

1. 画出秒杀从请求到发券的时序图，标出每一步的一致性责任方
2. 说明为何「Redis 扣库存 + MQ 异步落库」仍可能超卖或少卖，以及本项目如何防
3. 用压测或集成测给出「一人一单 / 库存不为负」的证据
4. 对比同步下单与削峰异步两种模型的适用场景

预计投入：2～4 周（有基础可压缩）。

## 阶段规划

### H1：概念对齐（2～3 天）

- 什么是超卖、少卖、重复下单
- 单机锁 / DB 行锁 / Redis 原子操作 / Lua 的边界
- 同步链路 vs 异步削峰：延迟、一致性、用户体验
- 幂等：业务键、唯一索引、状态机

产出：一页笔记，用自己的话定义上述名词（下方保留个人理解，并附标准表述对照）。

#### 超卖

- **我的理解**：本来有 50 stock 但是创建了 52 订单。
- **标准表述**：卖出数量超过可售库存（成功单 / 已占名额 `> stock`）。常见原因是「读库存 → 判断 → 扣减」非原子，并发下多人同时看到「还有货」。本项目用 Redis Lua 原子扣减，并用 DB 唯一约束兜底一人一单，避免「库存维度 + 用户维度」双重超卖。

#### 少卖

- **我的理解**：MQ 里面失败，Redis 的 stock 没有恢复。
- **标准表述**：名额已被扣减（或用户已进已抢 Set），但最终没有形成有效成功单，库存又未回滚，导致可售量被「吃掉」。典型路径：Lua 已成功 → MQ 丢失 / 消费失败未回滚 → 用户既没拿到券，别人也用不了这个名额。本项目在「发 MQ 失败」时 `rollbackGrab`；发券失败标 `FAILED` 并回滚；死信 `reconcileDeadLetter` 处理卡住与泄漏。

#### 重复下单

- **我的理解**：优惠券限制一号一个，Redis 的 Set 存 id 限制，MQ 里面查数据库检验，前端传 `IdempotencyKey` 做幂等（防止网络抖动）。
- **标准表述**：同一用户对同一活动（或同一业务意图）产生多笔有效单。防护分层：
  1. Redis Set：热路径快速拦截「已参与」
  2. DB `uk_seckill_user_activity`：最终一人一单
  3. `idempotencyKey`：客户端重试（超时、重复点击）不重复占名额 / 不重复落库
  三者缺一可能在某一层被打穿，所以要叠着用。

#### 单机锁

- **我的理解**：Java JVM 的锁。
- **标准表述**：进程内互斥（`synchronized` / `ReentrantLock` 等），只对**同一 JVM** 内线程有效。多实例部署时锁不住别的机器，秒杀场景通常不够，需要 Redis / DB 等分布式手段。

#### DB 行锁

- **我的理解**：MySQL InnoDB 的行级锁，`FOR UPDATE`。
- **标准表述**：在事务中锁定特定行，串行化对该行的修改，一致性强，但秒杀热点行会成为瓶颈（排队、锁等待、把压力打到 DB）。适合库存不大、QPS 可控的场景；高并发秒杀更常见「Redis 扣减 + DB 异步落库」。

#### Redis 原子操作

- **我的理解**：Lua 脚本查询和修改作为一次任务执行。
- **标准表述**：单条 Redis 命令（如 `INCR`/`DECR`）本身原子；复杂「先查后改」要用 Lua 或 `MULTI/EXEC`（事务）把多步合成在服务端一次执行，避免客户端两次往返之间被别的请求插入。本项目抢券用 Lua，而不是应用里 `GET` 再 `DECR`。

#### Lua 的边界

- **我的理解**：不懂，可能是根据返回值做不同逻辑处理。
- **标准表述**：Lua 保证的是 **Redis 单实例内脚本执行期间不被其他命令打断**，不是分布式事务。边界包括：
  1. 不覆盖「脚本成功之后」的事（发 MQ、写 MySQL 仍可能失败）
  2. 脚本宜短、勿做重计算或访问外部服务
  3. 集群模式下 Key 一般要在同一 slot（本项目库存 Key + 用户 Set 需注意设计）
  4. 返回码（本项目 `0/1/2`）只表达 Redis 侧结果，业务还要用 MQ / DB / 回滚补齐

  「根据返回值分支」是应用层用法，不是 Lua 原子性本身的定义。

#### 同步链路

- **我的理解**：一次业务一个线程同步跑完，响应慢，高峰期容易导致服务卡死。
- **标准表述**：请求线程内顺序完成扣库存、写订单、发券等全部步骤再返回。一致性好讲、实现直观，但延迟高、线程被占满，流量尖峰时容易把应用和 DB 一起打满。适合低并发、强同步结果的场景。

#### 异步削峰

- **我的理解**：马上返回 `PROCESSING` 的状态，任务以消息形式进入消费者，横向扩展容易。
- **标准表述**：热路径只做轻量决策（本项目：Lua + 发 MQ），立即返回「排队中」；落库发券由消费者消化。用队列缓冲尖峰，消费者可水平扩展。代价是最终一致、需要轮询 / 回调、以及消息丢失与重复的治理（ACK、幂等、死信、对账）。注意：grab 返回的 `PROCESSING` 时 MySQL 可能尚未有行，以 Redis 占名额为准。

#### 幂等

- **我的理解**：任务多次执行效果一样。
- **标准表述**：同一请求（或同一业务键）执行一次与执行多次，业务终态相同。手段包括：业务幂等键、唯一索引、状态机（已 `SUCCESS` 再消费直接 return）。MQ **至少一次投递** 下，幂等是逼近「业务恰好一次」的核心手段，不只是防前端抖一下。

### H2：吃透本仓库秒杀路径（3～5 天）

按调用链做笔记：

```text
grab → 幂等查询 → Lua(库存+已抢用户) → 发 MQ → 返回 PROCESSING
     → Consumer：写 seckill_order + 发券
```

逐项回答：

#### 1. Lua 返回 `0/1/2` 各代表什么？接口如何响应？

- **我的理解**：
  - `0`：库存不足，直接返回异常
  - `1`：成功，发消息给队列
  - `2`：已经参与，直接返回异常
- **标准表述**（见 `seckill_grab.lua` / `SeckillService.grab`）：
  | 返回值 | Redis 侧含义 | 接口响应 |
  | --- | --- | --- |
  | `0` | 售罄（库存不存在或 `≤ 0`） | 抛 `soldOut`，不发 MQ |
  | `1` | 抢中：已 `DECR` 库存且 `SADD` 用户 | 发 MQ，返回 `PROCESSING`（排队中） |
  | `2` | 用户已在已抢 Set 中 | 抛 `alreadyParticipated`，不发 MQ |

  注意：`1` 时接口返回的是异步中间态，不是最终发券成功。

#### 2. 「已参与」靠 Redis Set 还是 DB？两者缺一会怎样？

- **我的理解**：Redis Set 提供了高效，DB 保证了最终一人一单。
- **标准表述**：两者都要，职责不同。
  - **Redis Set**（`seckill:users:{activityId}`）：热路径快速判重，和扣库存在同一 Lua 里完成，扛并发。
  - **DB 唯一约束**（`uk_seckill_user_activity` + 幂等键）：Consumer 落库时的最终兜底；并发双消费时靠 `DuplicateKeyException` 忽略。

  缺一后果：
  - **只有 Redis、无 DB 唯一键**：Set 过期 / 被误删 / 多实例逻辑漏洞时，可能落出多单。
  - **只有 DB、无 Redis Set**：每次抢券都要打 DB 判重，削峰失效，DB 易被打满；且 Lua 无法在扣库存同时做高效防重。
  - **Redis 有、DB 尚无行**：属正常空窗（消息未消费完），`getResult` 用 Set 仍报 `PROCESSING`。

#### 3. MQ 丢了或 Consumer 挂了，用户轮询 result 会看到什么？

- **我的理解**：轮询是 `PROCESSING`。
- **标准表述**：分阶段看。
  1. **Lua 已成功、消息未消费完 / Consumer 暂时挂起**：DB 可能无单，但 Redis Set 仍有该用户 → `getResult` 返回 **`PROCESSING`**（你的理解正确，这是主路径现象）。
  2. **消息永久丢失且无人回滚**：会**长时间**停在「Redis 已占 + 无终态单」→ 轮询一直像 `PROCESSING`，实际是少卖/名额泄漏，需死信或对账 `rollbackGrab` / 标 `FAILED`。
  3. **Consumer 已落库后挂在发券途中**：DB 为 `PROCESSING` → 轮询仍是 `PROCESSING`；对账可把卡住单改为 `FAILED` 并回滚 Redis。
  4. **已 `SUCCESS` / `FAILED`**：轮询返回对应终态。

  因此：看到 `PROCESSING` 只表示「名额已占、结果未揭晓」，不保证消息一定还在路上。

#### 4. 活动库存变更时，Redis 与 DB 如何再对齐？

- **我的理解**：先删 Redis，再改 DB，再删 Redis，延迟双删策略。
- **标准表述**：
  - **延迟双删**是经典 Cache Aside（先更新 DB、删缓存，延迟再删一次）思路，适合「DB 为权威、缓存可丢」的读多写少模型。
  - **本仓库秒杀路径并不是延迟双删**：扣减权威在 Redis，DB 活动表存的是配置库存；对齐方式是管理端 **`warmUpStock` 预热**：
    - 创建活动 / 非进行中修改库存且活动启用时：`SET seckill:stock:{id}`，并 **清空** `seckill:users:{id}`
    - **活动进行中禁止改库存**（`updateActivity` 直接拒绝），避免热卖中改数导致与已抢人数对不齐
  - 运行期不一致更多靠 **`rollbackGrab`（库存 +1、Set 移除用户）** 和死信对账，而不是双删。
对照：你的「双删」知识可留作书目缓存等场景；秒杀库存要对齐，优先记「预热覆盖 + 禁热改 + 失败回滚」。



#### 产出：时序图 + 故障矩阵

##### 我的理解（一例）

RabbitMQ 抖动，发送的消息没有收到，没有兜底能力，导致 Redis Set 里有该用户，但一直 `PROCESSING`。

##### 标准补充

- **发 MQ 时抛异常**（连接失败等）：本项目**有**兜底——`catch` 里 `rollbackGrab` 并返回系统繁忙，不会留下「Set 有人 + 永久 PROCESSING」。
- **你描述的更危险的情况**是：`publish` **看似成功**（或半成功），消息实际未入队 / Broker 弄丢，且**没有进主队列也就进不了 DLQ**。此时死信对账触发不了，确实会「Redis Set 有人 + 轮询一直 `PROCESSING`」→ 少卖。这是「先扣 Redis、后发 MQ」模型的经典缺口，需要 **Publisher Confirm + 本地消息表 / 定时对账扫 Set** 才能补强（见 H4）。

##### 故障矩阵（失败点 × 现象 × 现有兜底）

| 失败点 | 现象 | 现有兜底 | 缺口 / 备注 |
| --- | --- | --- | --- |
| Lua 返回 `0` | 售罄异常 | 不发 MQ、不占 Set | 无 |
| Lua 返回 `2` | 已参与异常 | Set 已有用户 | 无 |
| **发 MQ 抛异常** | 用户看到系统繁忙 | **`rollbackGrab`**（库存 +1、Set 移除） | 有兜底 |
| **发 MQ「成功」但消息丢失**（Broker 抖动等） | Set 有人，DB 无单，轮询一直 `PROCESSING` | **无自动兜底**（进不了 DLQ） | 正是你指出的缺口；需 Confirm / 对账任务 |
| 消息积压 / Consumer 暂挂 | 同上，但通常短暂 | 恢复后继续消费 | 正常空窗 |
| Consumer 早期异常（参数坏、活动不存在） | Nack → DLQ | `reconcileDeadLetter`：无单则 `rollbackGrab` | 有 |
| 并发双消费 | 第二次 insert 撞唯一键 | `DuplicateKeyException` 忽略 | 有 |
| 发券失败 | DB=`FAILED`，券未发 | 标失败 + `rollbackGrab`，**Ack**（不进 DLQ） | 有 |
| 落库后卡在 `PROCESSING`（进程挂死等） | DB=`PROCESSING`，轮询处理中 | 仅当消息最终 Nack 进 DLQ 时，对账改为 `FAILED`+回滚 | 若消息已 Ack 则靠人工/定时任务 |
| 死信对账失败 | DLQ 内 Nack 且不 requeue | 日志告警，需人工 | 避免死循环 |

##### 和「我的理解」对齐的一句话

你的场景成立：**消息没进队列时，死信帮不上忙**，会表现为 Redis Set 有记录却长期 `PROCESSING`。  
要区分：本项目只保证「**publish 抛错**」会回滚；不保证「**publish 无异常但消息消失**」会自动恢复——后者正是后续要对账 / 本地消息表补的点。

## 能力自检（参考答案）

### 1. 能默画秒杀主路径与至少 3 个失败分支

**主路径：**

```text
grab → 校验活动窗口 / 幂等键
    → Lua（判库存、判 Set、DECR、SADD）返回 1
    → 发 MQ → 返回 PROCESSING
    → Consumer：insert PROCESSING → 发券 → update SUCCESS → Ack
    → 用户 getResult → SUCCESS
```

**失败分支（至少掌握 3 个）：**

| 分支 | 现象 | 处理 |
| --- | --- | --- |
| Lua=`0` | 售罄 | 抛 `soldOut`，不发 MQ |
| Lua=`2` | 已在 Set | 抛 `alreadyParticipated` |
| 发 MQ 抛异常 | 系统繁忙 | `rollbackGrab`（库存+1、Set 移除） |
| 发券失败 | DB=`FAILED` | 标失败 + `rollbackGrab`，Consumer **Ack**（不进 DLQ） |
| Consumer 早期异常 | Nack | 进 DLQ → `reconcileDeadLetter` 回滚或标失败 |
| publish「成功」但消息丢 | 长期 PROCESSING | **缺口**：死信进不来，需对账/Confirm（见 H2 故障矩阵） |

### 2. 能说明 Redis 与 DB 双重防重各自防什么

| 层 | 手段 | 防什么 | 防不了什么 |
| --- | --- | --- | --- |
| Redis Set | Lua 里 `SISMEMBER` + `SADD` | 热路径重复抢、与扣库存原子完成 | Set 过期/误删、脚本之后的重复消费 |
| DB | `uk_seckill_user_activity`、`uk_seckill_idempotency` | 最终一人一单；MQ 重复投递；并发双 Consumer | 单独扛秒杀峰值（所以前面要 Redis） |

互补：**Redis 扛并发快速拒绝；DB 做最终正确性。**  
另：`idempotencyKey` 防客户端重试重复占名额/重复发 MQ。

---

### 3. 有自动化或压测证据证明库存不为负

本仓库已有：

- **单测** `SeckillServiceTest`：售罄/已参与/幂等/MQ 失败回滚等分支
- **集成测** `SeckillRedisGrabIT`：库存 `N=20`，并发 `80` 用户，断言成功数 `= N`、剩余库存 `0`、二次抢无新增成功（需 Docker）
- **压测草稿** `scripts/perf/README.md`：HTTP 链路记录模板

口述时可说：「用 Testcontainers 对 Lua 做并发断言；HTTP 全链路用多用户压测看 SUCCESS ≤ N。」

---

### 4. 能说清「PROCESSING」中间态对前端轮询的含义

`PROCESSING` = **名额已占（Redis 已扣），发券结果尚未揭晓**，不是第三种业务终态。

对前端：

1. `grab` 立刻可能返回 `PROCESSING` → 应轮询 `getResult`，不要当成失败去换 key 狂重试
2. `getResult`：有 DB 单则看状态；无单但 Set 有人 → 仍报 `PROCESSING`（MQ 未落库的空窗）
3. 终态只有 `SUCCESS` / `FAILED`；长时间 PROCESSING 可能是积压或消息丢失，需运维/对账，不是「再点一次 grab」就能好

---

### 5. 知道何时不该用纯异步秒杀

| 更适合同步 / 别用这套的场景 | 原因 |
| --- | --- |
| 极低 QPS、强同步要券 ID | 异步空窗与轮询成本不值 |
| 必须实时展示「还剩精确 N 件」且不允许最终一致 | Redis 与 DB 有窗口；MQ 延迟会让展示不准 |
| 发券必须与扣减同事务强一致、不能接受少卖窗口 | 「先扣后发」在消息丢失时有缺口 |
| 监管/资金类强一致下单 | 应同步落库或本地消息表等更强方案 |

异步秒杀适合：**瞬时高峰、允许短暂排队、可用轮询、可对账补偿** 的营销抢券。

## 面试口述提纲（完整示例约 3 分钟）

### 1. 背景

我们书城有优惠券秒杀：瞬时流量大，要求不超卖、一人一单，又不能把下单发券全堆在请求线程里把 DB 打挂。

### 2. 方案

活动创建时把库存预热到 Redis。用户 `grab` 时用 Lua 原子完成：判库存、判是否已参与、扣库存、写入已抢用户 Set。成功后发 RabbitMQ，接口马上返回 `PROCESSING`。消费者异步写 `seckill_order`、调用发券，再更新为 `SUCCESS` 或 `FAILED`。

### 3. 一致性与兜底

- 热路径正确性靠 Lua；最终一人一单靠 DB 唯一索引，重复消息撞键直接忽略
- 发 MQ 失败会 `rollbackGrab`，避免少卖
- 发券失败落 `FAILED` 并回滚 Redis，Consumer Ack，避免 FAILED 被事务回滚冲掉
- 早期消费失败进死信，由 `reconcileDeadLetter` 按「有单/无单/卡住 PROCESSING」补偿回滚
- 已知缺口：publish 看似成功但消息未入队时，死信帮不上，需要 Confirm 或定时对账（可主动提，显得有思考）

### 4. 验证

单测覆盖售罄、已参与、幂等、MQ 失败回滚；集成测用 Testcontainers 跑并发 Lua，断言成功数不超过库存。必要时再对 HTTP 做压测看终态。

### 5. 权衡

换来的是吞吐和削峰，代价是最终一致、前端要轮询、运维要盯 MQ 积压与 DLQ。库存展示和「抢到是否立刻有券」都有空窗；极低并发或强一致场景不必上这套，同步落库更简单。
