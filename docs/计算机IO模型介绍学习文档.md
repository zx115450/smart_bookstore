## 导读
写 Web 服务、连数据库、调第三方 API，底层几乎都在做一件事：**I/O（输入/输出）**。  
磁盘读写、网络收发、键盘输入……进程要跟「外部世界」交换数据，就绕不开 I/O。

很多人第一次听到「阻塞 I/O」「epoll」「异步 I/O」会混在一起。其实 **I/O 模型**讨论的核心就一件事：

> 进程在等待 I/O 数据时，**怎么等、谁来等、等的时候能不能干别的事**。

本文从一次完整的 I/O 过程讲起，把五种经典模型、两组易混概念、以及 Java / Linux 里的常见落地方式串起来。

---

## 一、一次 I/O 到底发生了什么

以「从网卡读一段数据」为例，一次完整 I/O 通常分两步：

```text
① 等待数据就绪（Waiting for data）
   数据从网卡 → 内核缓冲区（Kernel Buffer）

② 数据拷贝（Copy data）
   内核缓冲区 → 用户进程缓冲区（User Buffer）
```

```text
┌──────────────┐     ① 就绪等待      ┌──────────────────┐
│  用户进程     │ ─────────────────► │  内核空间         │
│  User Buffer │ ◄───────────────── │  Kernel Buffer    │
└──────────────┘     ② 数据拷贝      └──────────────────┘
                                              ▲
                                              │ 网卡 / 磁盘
```

不同 I/O 模型的差异，主要体现在：

- **第 ① 步**：进程是挂起等待，还是立刻返回、稍后再问？
- **第 ② 步**：拷贝由谁发起、完成后怎么通知应用？

## 二、两组必须分清的概念

### 2.1 阻塞 vs 非阻塞

看的是：**发起 I/O 调用时，进程会不会被挂起**。

| | 阻塞（Blocking） | 非阻塞（Non-blocking） |
|--|------------------|------------------------|
| 调用行为 | 一直等到有结果才返回 | 立刻返回 |
| 没数据时 | 进程休眠，让出 CPU | 返回错误码（如 `EAGAIN`） |
| 典型 API | 默认的 `read` / `recv` | `fcntl` 设 `O_NONBLOCK` 后再 `read` |

### 2.2 同步 vs 异步

看的是：**数据从内核拷到用户态，谁负责、完成后怎么通知**。

| | 同步（Synchronous） | 异步（Asynchronous） |
|--|---------------------|----------------------|
| 拷贝谁做 | 应用自己调 `read` 完成拷贝 | 内核完成后直接通知应用 |
| 应用感知 | 「我主动去取数据」 | 「数据好了你告诉我」 |
| 典型代表 | 阻塞 I/O、非阻塞 I/O、多路复用 | Linux AIO、Windows IOCP |

**一句话：**

- **阻塞/非阻塞** → 调用时「等不等」  
- **同步/异步** → 拷贝时「谁干完、怎么通知」

所以：**非阻塞 ≠ 异步**。非阻塞只是「先问问有没有」，真正读数据往往还是同步的。

## 三、五种经典 I/O 模型

POSIX / Unix 网络编程里，通常讲这五种（以网络读为例）。

### 3.1 阻塞 I/O（Blocking I/O）

最简单、也是默认模型。

```text
应用                  内核
  │
  │── recv() ─────────────────────►
  │         （进程阻塞挂起）
  │                    等待数据就绪
  │                    拷贝到用户态
  │◄──── 返回数据 ─────────────────
  │
  │  继续处理业务
```

**特点：**

- 调用直到「就绪 + 拷贝」都完成才返回  
- 编程简单，逻辑清晰  
- 一个连接占一个线程时，高并发下线程数爆炸（上下文切换、内存开销）

**日常对应：** 传统 `ServerSocket` + 一连接一线程；同步 JDBC 读库。

---

### 3.2 非阻塞 I/O（Non-blocking I/O）

把 socket 设成非阻塞后，`recv` 立刻返回。

```text
应用                  内核
  │── recv() ──► 没数据，返回 EAGAIN
  │── recv() ──► 没数据，返回 EAGAIN
  │── recv() ──► 没数据，返回 EAGAIN   ← 轮询空转
  │── recv() ──► 有数据，开始拷贝
  │◄── 返回数据
```

**特点：**

- 不等待，但应用要自己反复问「好了没」  
- 轮询浪费 CPU，几乎不会单独用于生产  
- 通常和 **I/O 多路复用** 搭配使用

---

### 3.3 I/O 多路复用（I/O Multiplexing）

一个线程同时「盯」多个文件描述符（fd），哪个就绪处理哪个。

```text
应用                         内核
  │
  │── select/poll/epoll ──►  同时监听 fd1, fd2, ... fdN
  │         （阻塞在「有没有人就绪」上）
  │◄── 告诉你：fd3、fd7 可读
  │
  │── recv(fd3) ──► 拷贝数据
  │── recv(fd7) ──► 拷贝数据
```

**特点：**

- 仍是 **同步 I/O**：就绪后还要自己 `read`  
- 一个线程管成千上万连接，是高并发网络服务的主流方案  
- Linux 上演进：`select` → `poll` → **`epoll`**

#### select / poll / epoll 对比

| | select | poll | epoll |
|--|--------|------|-------|
| fd 上限 | 默认约 1024 | 无硬编码上限 | 很大，受系统限制 |
| 传参方式 | 每次拷贝 fd 集合 | 类似，用链表 | 内核里维护兴趣列表 |
| 就绪检测 | 遍历全部 fd | 遍历全部 fd | 事件驱动，只返回就绪的 |
| 适用 | 连接少、教学 | 中等规模 | C10K / C100K 级 |

```text
epoll 核心三板斧：
  epoll_create  → 创建 epoll 实例
  epoll_ctl     → 增删改要监听的 fd
  epoll_wait    → 阻塞等待就绪事件
```

**日常对应：** Nginx、Redis、Netty（Linux 下用 epoll）、Java NIO 的 `Selector`。

---

### 3.4 信号驱动 I/O（Signal-driven I/O）

内核数据就绪时，用信号（如 `SIGIO`）通知进程，进程再去 `read`。

```text
应用                     内核
  │── 注册 SIGIO 处理函数
  │── 继续干别的事
  │
  │◄════════ SIGIO（数据就绪）
  │── recv() ──► 拷贝数据
```

**特点：**

- 少了轮询，但仍是同步拷贝  
- 信号处理复杂（可重入、信号丢失等），实际网络服务里用得很少  

---

### 3.5 异步 I/O（Asynchronous I/O / AIO）

真正的「发起后几乎不用管」：内核负责 **等就绪 + 拷贝**，全部完成后通知应用。

```text
应用                         内核
  │── aio_read() ──►  立即发起
  │◄── 立刻返回
  │
  │   （应用可继续干别的）
  │              等待数据就绪
  │              拷贝到用户缓冲区
  │◄════════ 完成通知（回调 / 完成队列）
  │
  │   直接使用已拷好的数据
```

**特点：**

- **异步 + 非阻塞** 的完整形态  
- Windows 上 IOCP 很成熟；Linux 早期 POSIX AIO 不理想，后来有 `io_uring`  
- 编程模型更复杂，但吞吐潜力大

## 四、五种模型一张图对比

```text
          阻塞 I/O          非阻塞 I/O         多路复用           信号驱动           异步 I/O
        ┌─────────┐       ┌─────────┐       ┌─────────┐       ┌─────────┐       ┌─────────┐
等待就绪 │  阻塞   │       │  轮询   │       │ 阻塞在  │       │ 信号通知 │       │         │
        │         │       │         │       │ select  │       │         │       │  内核做  │
数据拷贝 │  阻塞   │       │  阻塞   │       │  阻塞   │       │  阻塞   │       │         │
        └─────────┘       └─────────┘       └─────────┘       └─────────┘       └─────────┘
         同步阻塞          同步非阻塞        同步阻塞*         同步非阻塞         异步非阻塞

* 多路复用：阻塞点从「等某一个 fd」变成「等一批 fd 里谁就绪」
```

| 模型 | 第 ① 步（等就绪） | 第 ② 步（拷贝） | 同步/异步 |
|------|-------------------|-----------------|-----------|
| 阻塞 I/O | 阻塞 | 阻塞 | 同步 |
| 非阻塞 I/O | 不阻塞（轮询） | 阻塞 | 同步 |
| I/O 多路复用 | 阻塞在 select/epoll | 阻塞 | 同步 |
| 信号驱动 I/O | 不阻塞（信号） | 阻塞 | 同步 |
| 异步 I/O | 不阻塞 | 不阻塞（内核完成） | 异步 |

## 五、和 Java 开发的对应关系

Java 后端日常接触的，大多能映射到上面的模型。

### 5.1 BIO（Blocking I/O）

```java
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept(); // 阻塞等连接
    new Thread(() -> {
        InputStream in = socket.getInputStream();
        in.read(buf); // 阻塞等数据
    }).start();
}
```

- 模型：阻塞 I/O  
- 问题：连接多 → 线程多 → 扛不住  

### 5.2 NIO（New I/O / Non-blocking I/O）

```text
Selector（多路复用器）
   │
   ├── Channel 1  (非阻塞)
   ├── Channel 2
   └── Channel N
```

- 核心：`Channel` + `Buffer` + `Selector`  
- Linux 下 `Selector` 底层常是 **epoll**  
- 模型：非阻塞 + I/O 多路复用  

### 5.3 AIO（NIO.2 Asynchronous I/O）

```java
AsynchronousServerSocketChannel.open()
    .accept(null, new CompletionHandler<>() {
        @Override
        public void completed(...) { /* 连接完成回调 */ }
        @Override
        public void failed(...) { }
    });
```

- 模型：异步 I/O（回调 / Future）  
- Linux 上早期实现一般，生产里更常见的是 **Netty 基于 epoll 的多路复用**  

### 5.4 业务里常见的「伪异步」

线程池 + 阻塞调用（如同步 HTTP 客户端、同步 JDBC）：

```text
请求进来 → 线程池取一个线程 → 阻塞调下游 → 返回
```

这能缓解「无限建线程」，但 **每个任务仍占用一个线程卡在 I/O 上**，本质还是同步阻塞，只是把资源池化了。真正要吃满 CPU、撑高连接数，还是要往 **事件驱动 / 多路复用 / 异步** 靠。

## 六、怎么选型（实用视角）

| 场景 | 更合适的模型 | 原因 |
|------|--------------|------|
| 连接少、逻辑简单 | 阻塞 I/O | 代码直观，够用 |
| C10K / 长连接 / 网关 | 多路复用（epoll） | 单线程管大量连接 |
| 磁盘随机读、批量提交 | 异步 I/O / io_uring | 减少线程空等 |
| 业务接口调 DB / RPC | 线程池 + 同步调用 或 响应式 | 先看延迟与线程成本 |
| 学习理解内核行为 | 从阻塞 → 非阻塞 → epoll | 概念递进清晰 |

经验法则：

1. **先分清瓶颈**：是连接数，还是单次 I/O 延迟，还是 CPU。  
2. **网络高并发**优先多路复用，而不是盲目上异步。  
3. **异步不是银弹**：调试、背压、错误处理都更难，有收益再上。

## 七、几个高频面试追问

**Q：为什么说 epoll 比 select 高效？**  
A：select 每次要把 fd 集合拷进内核并线性扫描；epoll 在内核维护红黑树/就绪链表，只返回就绪事件，连接数上去后差距明显。

**Q：多路复用是异步吗？**  
A：不是。它只是「同时等很多 fd」，就绪后仍由应用同步 `read`，属于同步 I/O。

**Q：Redis 单线程为什么快？**  
A：网络部分用 I/O 多路复用，避免多线程锁竞争；瓶颈常在内存操作而非多核并行。

**Q：同步非阻塞和异步有什么本质区别？**  
A：同步非阻塞：应用反复问 + 自己拷贝；异步：内核做完拷贝再通知，应用拿到的往往是「已经就绪的用户态数据」。

## 八、小结

| 要点 | 记住什么 |
|------|----------|
| I/O 两阶段 | 等数据就绪 → 拷到用户态 |
| 阻塞/非阻塞 | 调用时会不会挂起 |
| 同步/异步 | 拷贝谁做、如何通知 |
| 五种模型 | 阻塞、非阻塞、多路复用、信号驱动、异步 |
| 高并发主力 | Linux epoll 类多路复用 |
| Java 对应 | BIO / NIO(Selector) / AIO；Netty ≈ 多路复用增强版 |

**最后一句话：**  
I/O 模型不是玄学名词，而是「进程怎么跟内核配合拿数据」。把 **两阶段** 和 **同步/异步、阻塞/非阻塞** 两根轴钉牢，再看 Nginx、Redis、Netty，会清晰很多。
