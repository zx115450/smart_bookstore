# 登录鉴权实现流程

> **项目**：smart_bookstore（智慧书城）  
> **文档类型**：实现流程说明 · 对照本仓库代码  
> **关联包**：`com.zx.auth` · `com.zx.config.SecurityConfig`  
> **加深阅读**：[登录流程学习文档](./登录流程学习文档.md) · [双 Token 登录学习文档](./双Token登录学习文档.md) · [JWT-Refresh-Token 完整链路](./JWT-Refresh-Token完整链路.md) · [QQ 扫码登录学习文档](./QQ扫码登录学习文档.md)

本文按「一次完整生命周期」描述本仓库的登录与鉴权：**发码 / 登录签发 → 请求鉴权 → 刷新 → 登出**。读完应能画出双 Token + Session 的协作关系，并知道每一步查 Redis / MySQL 还是只验 JWT。

---

## 1. 设计总览

### 1.1 采用什么方案

| 组件 | 形态 | 作用 |
| --- | --- | --- |
| Access Token | 短寿命 JWT（默认 7200 秒） | 业务请求 `Authorization: Bearer ...` |
| Refresh Token | 长寿命不透明串（`jti:随机串`） | 仅 `/api/auth/refresh` 换票 |
| Session | 服务端有状态（MySQL + Redis 缓存） | 会话总开关：吊销、绝对过期 |
| Access 黑名单 | Redis（按 Access 的 `jti`） | 登出后 Access 未过期也能立刻失效 |

Spring Security 为 **无状态 Session**（`SessionCreationPolicy.STATELESS`）：不靠服务端 HttpSession，靠每次请求带 Token + 过滤器校验。

### 1.2 为什么双 Token 还要 Session

- Access 短 → 减少泄露窗口；JWT 自带 `userId` / `roles` / `sid`
- Refresh 长 → 少反复登录；很少出现在业务请求里
- Session → 登出、踢人、绝对过期（默认 90 天）时服务端能一刀切

有状态补的是 **可吊销**；双 Token 补的是 **短票跑业务、长票只续期**。二者正交。

### 1.3 生命周期总图

```text
发码(可选) → 登录
              ├─ 写 auth_session
              ├─ 签发 Access JWT（含 jti、sid、roles）
              └─ 签发 Refresh（jti:secret，库中只存 hash）
                    │
业务请求 ──Bearer Access──► JwtAuthenticationFilter
              ├─ 验签 / 过期
              ├─ Redis：Access jti 黑名单？
              ├─ Session：存在且未吊销、未绝对过期？
              ├─ 用户 status 正常？
              └─ 写入 SecurityContext → Controller
                    │
Access 过期 ──Refresh──► /api/auth/refresh
              ├─ 校验 jti + hash + 过期
              ├─ 吊销旧 Session，签发新一对 Token（轮换）
              └─ absolute_expires_at 继承，不因 refresh 无限延长
                    │
登出 ──Access + Refresh──► /api/auth/logout
              ├─ Access jti 进 Redis 黑名单（TTL=剩余有效期）
              └─ 吊销对应 Session
```

## 3. 登录签发流程

### 3.1 接口

`POST /api/auth/login`（公开，Filter 不强制 Token）

支持多种 `loginType`（工厂路由），例如：

- `password`：账号密码
- `qq_email_code` / `phone_code`：验证码（先 `POST /api/auth/code/send`）
- `qq_oauth`：QQ 扫码（另走 OAuth 回调，最终仍落到建 Session）

### 3.2 时序

```text
Client
  → AuthController.login
  → AuthService.login
       ├─ Redis 检查登录失败锁定（checkLoginAllowed）
       ├─ LoginHandlerFactory → 具体 Handler 校验凭证，得到 AuthUser
       │     失败：recordLoginFailure + 审计，返回 null → 401 业务码
       ├─ ensureDefaultUserRole、清失败计数、更新 lastLoginAt、写审计
       └─ createSessionAndResponse
              └─ createRotatedSession
                    ├─ 生成 refresh = jti + ":" + 随机串，hash=SHA-256 入库
                    ├─ 写 auth_session（access/refresh/absolute 过期时间）
                    ├─ JwtService.createAccessToken(userId, username, sessionId, roles)
                    └─ 返回 LoginResponse{ accessToken, refreshToken, expireIn, userInfo }
```

### 3.3 Access JWT 里有什么

`JwtService.createAccessToken` 写入的关键 claims：

| Claim | 含义 |
| --- | --- |
| `sub` | 用户 ID |
| `username` | 用户名 |
| `sid` | Session ID（Filter 查会话用） |
| `roles` | 角色列表 |
| `typ` | 固定 `access` |
| `jti`（JWT id） | Access 唯一 ID（黑名单用） |
| `iss` / `exp` / `iat` | 签发方与时间 |

### 3.4 Refresh 形态

- 明文：`{refresh_token_jti}:{随机 UUID}`  
- 库表：`auth_session.refresh_token_jti` + `refresh_token_hash`（只存 hash）  
- 校验时：按 jti 查 Session，再比对 `sha256(refreshToken)`

## 4. 请求鉴权流程（核心）

### 4.1 Security 配置

`SecurityConfig`：

- CSRF 关闭；Session 策略 `STATELESS`
- 公开：`/api/auth/login|refresh|code/send|logout`、QQ OAuth、`/api/ai/chat`、部分 Actuator
- `/api/admin/**` 等需 `ROLE_ADMIN`
- 其余 `/api/**` 需已认证
- `JwtAuthenticationFilter` 挂在 `UsernamePasswordAuthenticationFilter` 之前

### 4.2 Filter 做什么

`JwtAuthenticationFilter`：

1. 非 `/api/**` 或公开路径 → 跳过鉴权逻辑（`shouldNotFilter`）
2. 无 `Bearer` Token  
   - 普通接口 → 写 401 JSON 并 `return`（不进 Controller）  
   - `/api/ai/chat` → 匿名放行（可选鉴权）
3. `jwtService.parseAccessToken`：验签、issuer、`typ=access`、未过期
4. **Redis** `isAccessBlacklisted(jti)` → 已登出则 401
5. **Session** `findById(sid)`：不存在 / `revoked_at` 非空 / 超过 `absolute_expires_at` → 401  
   （注释里「校验 Refresh」不准确：这里查的是 **Session**，不是解析 Refresh）
6. 用户 `status == 1`
7. 构造 `AuthPrincipal`，写入 `SecurityContext` 与 request attribute，再 `chain.doFilter`

失败时 `response.getWriter().write(...)` + `flushBuffer()`，**不依赖 Controller return**。

### 4.3 Header 与 Session 的关系

| | Header（客户端带） | Session（服务端存） |
| --- | --- | --- |
| 内容 | Access JWT | `auth_session` 行（可缓存到 Redis） |
| 每次请求 | 必须带（受保护接口） | Filter 按 JWT 里的 `sid` 查询 |
| 角色等 | 多在 JWT claims 里 | 会话吊销、绝对过期、Refresh 绑定 |

客户端「存 Token」≠ 服务端「存 Session」：前者是出示的票，后者是票是否仍被承认的总开关。

## 5. 刷新 Token

`POST /api/auth/refresh`，Body 为纯文本 Refresh Token。

`AuthService.refresh`：

1. 拆出 jti，查 Session  
2. 已吊销 → 为防重放，可 `revokeAllByUserId`，返回失败  
3. 绝对过期 / refresh 过期 / hash 不匹配 → 失败  
4. **吊销当前 Session**，再 `createRotatedSession`：新 Access + 新 Refresh  
5. `absolute_expires_at` **继承旧会话**，不因反复 refresh 无限顺延  

这是 Refresh **轮换（rotation）**：旧 Refresh 立刻失效。

---

## 6. 登出

`POST /api/auth/logout`（公开，可带 Access Header + 可选 Refresh Body）。

`AuthService.logout`：

1. 若有 Access：解析成功则  
   - `blacklistAccessToken(jti, 剩余 TTL)`  
   - `revokeById(sessionId)`  
2. Access 已过期仍可尝试用 Refresh 的 jti 吊销 Session  

之后：

- 旧 Access：黑名单拦截（未过期窗口内）  
- 旧 Refresh：Session 已吊销，无法再 refresh  
- 同会话下未过期的 Access 也会因 Session 吊销被 Filter 拒绝

## 7. 存储分工

| 数据 | 存哪 | 说明 |
| --- | --- | --- |
| 用户 / 角色 / 标识 | MySQL `auth_user*` | 账号主数据 |
| 会话 | MySQL `auth_session`（+ Redis 缓存） | Refresh hash、吊销、绝对过期 |
| Access JWT | 客户端；服务端不存明文 | 只在黑名单里记 `jti` |
| Access 黑名单 | Redis | key 带 TTL，过期自动清 |
| 验证码 / 登录失败 / 发码限流 | Redis | 防刷、锁定 |
| 登录审计 | MySQL `auth_login_audit` | 成功失败记录 |

表结构见 Flyway：`src/main/resources/db/migration/V1__init_schema.sql`。

## 8. 端到端对照（按场景）

| 场景 | 客户端 | 服务端关键动作 |
| --- | --- | --- |
| 密码登录 | `POST /login` | Handler 验密 → 建 Session → 发双 Token |
| 验证码登录 | 先 `/code/send` 再 `/login` | Redis 限流 + 验码 → 同上 |
| 调业务 API | `Authorization: Bearer <access>` | Filter：JWT + 黑名单 + Session + 用户状态 |
| Access 过期 | `POST /refresh` + refresh 正文 | 校验 hash → 轮换 Session → 新双 Token |
| 登出 | `/logout` + Access（及可选 Refresh） | 黑名单 + 吊销 Session |
| AI 匿名聊 | 不带 Token 调 `/api/ai/chat` | 可选鉴权：无 Token 也放行 |

## 10. 小结

1. **登录**：校验身份 → 写 Session → 发短 Access + 长 Refresh  
2. **鉴权**：每个受保护请求验 JWT，并用 Redis 黑名单 + Session 做可吊销裁决  
3. **刷新**：只认 Refresh，轮换 Session，绝对过期不延长  
4. **登出**：黑名单堵 Access，吊销 Session 堵 Refresh 与同会话 Access  

不是「纯无状态 JWT」，也不是「单 Cookie Session」；而是 **JWT 跑请求 + Session/黑名单管吊销** 的组合实现。
