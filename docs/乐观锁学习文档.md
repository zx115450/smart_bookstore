## 导读
面试里「乐观锁 vs 悲观锁」经常被问，但很多人只会背定义：

- **悲观锁**：先锁住再改（`SELECT ... FOR UPDATE`）
- **乐观锁**：先改，改的时候校验「数据有没有被别人动过」

真正写代码时，乐观锁往往 **不是一个注解那么简单**。它可以是：

1. 显式 **`version` 字段** + `WHERE version = ?`
2. **状态字段 CAS**：`WHERE status = 'PENDING'`
3. **数值条件 CAS**：`WHERE stock >= ?`（本项目大量在用）

三种本质相同：**用一次原子 UPDATE 的 WHERE 条件，代替长时间占锁**。

---

## 一、乐观锁的核心思想

### 1.1 经典流程（带 version）

```text
1. SELECT id, stock, version FROM product WHERE id = 1;
   → 读到 stock=10, version=5

2. 业务计算：stock 应变为 9

3. UPDATE product
   SET stock = 9, version = version + 1
   WHERE id = 1 AND version = 5;

4. 若 affected rows = 0
   → 说明期间别人已更新（version 已不是 5）
   → 重试或返回「请刷新后重试」
```

**没有**在步骤 1～3 之间对行加长时间排他锁；冲突在步骤 3 由数据库一次性判定。

### 1.2 和悲观锁对比

| 维度 | 悲观锁 `FOR UPDATE` | 乐观锁 |
|------|---------------------|--------|
| 冲突时 | 等待（阻塞） | 直接失败 / 重试 |
| 读多写少 | 容易排队 | 通常更省锁 |
| 写冲突极高（秒杀） | 单行热点瓶颈 | 大量失败重试，不如 Redis |
| 实现复杂度 | 较低 | 需处理重试、失败提示 |
| 典型 SQL | 先 SELECT FOR UPDATE 再 UPDATE | 一条条件 UPDATE 或 version UPDATE |

### 1.3 三种常见实现形态

| 形态 | WHERE 条件 | 典型场景 |
|------|------------|----------|
| **A. version 列** | `AND version = ?` | 后台编辑同一条记录、通用实体更新 |
| **B. 状态 CAS** | `AND status = '旧状态'` | 订单状态机、券核销 |
| **C. 数值 CAS** | `AND stock >= ?` / `AND booked_count < capacity` | 库存、名额、余额 |

> B、C 有时不叫「乐观锁」，但和 version 乐观锁 **解决的是同一类问题**：避免基于过期读去做覆盖写。

## 二、案例 1：商品库存扣减（数值 CAS）

**场景**：购书支付时扣 `sale_stock`，不能扣成负数。

本项目 `BookMapper.deductSaleStock`：

```sql
UPDATE book
SET sale_stock = sale_stock - #{qty}, updated_at = NOW()
WHERE id = #{id} AND sale_stock >= #{qty};
```

```java
// 影响行数 = 0 → 库存不足或并发已被扣完
if (mapper.deductSaleStock(bookId, quantity) <= 0) {
    throw TradeException.outOfStock();
}
```

| 点 | 说明 |
|----|------|
| 是否 version | 无 version 列，靠 `sale_stock >= qty` 保证原子 |
| 为何够 | UPDATE 单行原子；条件不满足则 0 行 |
| 与悲观锁 | 本项目 pay 前还有 `FOR UPDATE` 读 book，属于 **悲观 + 条件 UPDATE** 双保险 |

**变体（带 version）**：

```sql
UPDATE book
SET sale_stock = sale_stock - 1, version = version + 1
WHERE id = 1001 AND sale_stock > 0 AND version = 7;
```

适合需要在应用层明确感知「版本冲突」、做自动重试的场景。

## 三、案例 2：用户余额扣款（数值 CAS）

**场景**：余额支付，不能透支。

```sql
UPDATE auth_user
SET balance = balance - #{amount}, updated_at = NOW()
WHERE id = #{id} AND balance >= #{amount};
```

| 并发 | 结果 |
|------|------|
| 两笔支付同时扣 80，余额 100 | 仅一笔成功，另一笔 affected=0 → 余额不足 |
| 无需 FOR UPDATE 长时间占行 | 适合冲突不算极高的支付场景 |

**注意**：转账（A 减 B 加）需 **同一事务** 内更新两行，并 **固定 id 顺序** 防死锁（见案例 8）。

## 四、案例 3：订单状态流转（状态 CAS）

**场景**：仅 `PENDING_PAY` 可支付，防止重复支付或已取消订单被支付。

本项目 `TradeOrderMapper.markPaid`：

```sql
UPDATE trade_order
SET status = 'PAID', paid_at = NOW(), updated_at = NOW()
WHERE id = #{id} AND status = 'PENDING_PAY' AND user_id = #{userId};
```

```java
if (orderMapper.markPaid(orderId, userId) <= 0) {
    throw TradeException.invalidStatus();
}
```

| 点 | 说明 |
|----|------|
| 本质 | **状态机乐观锁**，`status` 即「业务版本」 |
| vs 先查再改 | 少一次 SELECT，且 UPDATE 原子 |
| 幂等 | 已 PAID 时再调 pay → 0 行，可判无效状态 |

**其他状态流转示例**：

```sql
-- 取消：仅待支付可取消
UPDATE trade_order SET status = 'CANCELLED', cancelled_at = NOW()
WHERE id = ? AND status = 'PENDING_PAY';

-- 借阅确认：仅 APPLIED 可确认
UPDATE borrow_order SET status = 'CONFIRMED', borrow_at = NOW()
WHERE id = ? AND status = 'APPLIED';
```

## 五、案例 4：优惠券核销（状态 CAS）

**场景**：同一张券只能核销一次，防止重复下单重复使用。

```sql
UPDATE user_coupon
SET status = 'USED', used_at = NOW(), trade_order_id = ?, updated_at = NOW()
WHERE id = ? AND status = 'UNUSED' AND user_id = ?;
```

| 并发 | 结果 |
|------|------|
| 两笔订单同时用同一张券 | 仅一笔 UPDATE 成功 |
| 第二笔 | affected=0 → 券不可用 |

这是 **券维度的乐观锁**，比「先 SELECT 看 UNUSED 再 UPDATE」更安全。

## 六、案例 5：优惠券模板发放上限（数值 CAS）

**场景**：签到赠券 / 秒杀发券，模板 `total_count` 有限时不能超发。

```sql
UPDATE coupon_template
SET issued_count = issued_count + 1, updated_at = NOW()
WHERE id = #{id}
  AND status = 1
  AND (total_count = 0 OR issued_count < total_count);
```

| 点 | 说明 |
|----|------|
| `total_count = 0` | 表示不限量 |
| affected=0 | 已发完或模板下架 |

## 七、案例 6：预约时段名额（数值 CAS + version 递增）

**场景**：某时段 `capacity=30`，已约 `booked_count` 不能超过容量。

表结构（本项目 `reservation_time_slot`）含 `version` 字段：

```sql
UPDATE reservation_time_slot
SET booked_count = booked_count + 1,
    version = version + 1,
    updated_at = NOW()
WHERE id = #{id}
  AND booked_count < capacity;
```

释放名额：

```sql
UPDATE reservation_time_slot
SET booked_count = booked_count - 1,
    version = version + 1,
    updated_at = NOW()
WHERE id = #{id}
  AND booked_count > 0;
```

| 点 | 说明 |
|----|------|
| 主要防超卖 | `booked_count < capacity` |
| version | 每次变更 +1，便于审计、可扩展为严格 `AND version=?` |
| 与座位锁 | 座位级防超卖仍靠 `reservation_order` 唯一占用 + 行锁；时段名额是另一维度 |

## 八、案例 7：运营后台编辑冲突（经典 version）

**场景**：管理员 A、B 同时打开「图书编辑」页，后提交的不能悄悄覆盖先提交的。

### 8.1 表结构

```sql
ALTER TABLE book ADD COLUMN version INT NOT NULL DEFAULT 0;
```

### 8.2 读

```json
GET /api/admin/books/1
{ "id": 1, "title": "Java核心技术", "price": 119, "version": 12 }
```

### 8.3 写

```sql
UPDATE book
SET title = ?, price = ?, version = version + 1, updated_at = NOW()
WHERE id = 1 AND version = 12;
```

```java
if (bookMapper.updateWithVersion(book) == 0) {
    throw new BookstoreException(4008, "数据已被他人修改，请刷新后重试");
}
```

| 体验 | 前端收到 4008，提示刷新页面重新编辑 |
|------|-------------------------------------|

### 8.4 MyBatis-Plus `@Version`

```java
@TableName("book")
public class Book {
    @Version
    private Integer version;
}
```

`updateById(book)` 时 MP 自动：`WHERE id=? AND version=?`，并 `version+1`。

## 九、案例 8：转账（双账户 + 固定加锁顺序）

**场景**：A 转 100 给 B。可用悲观锁，也可用 **条件 UPDATE 乐观风格**：

```sql
START TRANSACTION;

-- 先扣款（条件 CAS）
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 100 AND balance >= 100 AND version = 5;

-- 影响行数=0则回滚
UPDATE account SET balance = balance + 100, version = version + 1
WHERE id = 200 AND version = 3;

INSERT INTO transfer_log (...) VALUES (...);
COMMIT;
```

| 注意 | 两行更新任一失败要 **整事务回滚** |
|------|----------------------------------|
| 悲观锁写法 | 按 id 排序 `FOR UPDATE` 两行再改，见 [MySQL锁与业务场景学习文档](./MySQL锁与业务场景学习文档.md) 场景 2 |

## 十、案例 9：文章点赞 / 阅读量（高并发计数）

**场景**：点赞数 +1，允许极少量误差时可 Redis INCR；要精确时用 DB：

```sql
UPDATE article
SET like_count = like_count + 1, version = version + 1
WHERE id = 100 AND version = 7;
```

高冲突时：

- **方案 A**：乐观锁 + 客户端重试 3 次
- **方案 B**：Redis 聚合，定时刷 DB
- **方案 C**：单独计数表 + 行锁（热点行仍痛）

乐观锁适合 **冲突不算极端** 的计数；秒杀级热点应 Redis。

## 十一、案例 10：工单抢单（状态 CAS + SKIP LOCKED 对比）

**场景**：多个客服抢同一待处理工单。

**乐观锁风格**：

```sql
UPDATE ticket
SET status = 'PROCESSING', assignee_id = 1001, updated_at = NOW()
WHERE id = 9001 AND status = 'OPEN';
-- 0 行 → 已被别人抢走
```

**悲观锁风格（MySQL 8.0+）**：

```sql
SELECT id FROM ticket WHERE status = 'OPEN' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
UPDATE ticket SET status = 'PROCESSING', assignee_id = ? WHERE id = ?;
```

| 选型 | 说明 |
|------|------|
| 乐观 UPDATE | 实现简单，抢不到就换下一条 |
| SKIP LOCKED | 批量拉取任务更高效 |

## 十二、案例 11：缓存写侧 version CAS（防旧值覆盖）

**场景**：慢线程读 DB 旧数据回填 Redis，覆盖管理员刚写入的新缓存。

见 [数据库与缓存高一致性业务场景实现方案](./数据库与缓存高一致性业务场景实现方案.md) 方案 D：

```json
// Redis 中存
{ "price": 100, "version": 13 }
```

Lua 仅当 `newVersion >= oldVersion` 才 SET。

| 点 | 说明 |
|----|------|
| version 在 DB | UPDATE 时 `version+1` |
| version 在缓存 | 写侧 CAS，不是每次读都对账 |
| 本质 | **跨存储的乐观并发控制** |

## 十三、案例 12：秒杀抢券（Redis 原子 + DB 唯一约束兜底）

**场景**：P4 秒杀（规划）。DB 乐观锁扛不住万级 QPS，但 **落库阶段** 仍可用乐观思想：

```sql
-- 消费者落库时
INSERT INTO seckill_order (user_id, activity_id, status, idempotency_key)
VALUES (1, 100, 'PROCESSING', 'uuid');
-- uk_seckill_user_activity (user_id, activity_id) 冲突 → 已参与
```

| 层次 | 手段 |
|------|------|
| 抢名额 | Redis Lua 原子 decr + sadd |
| 一人一单 | DB UNIQUE |
| 重试幂等 | idempotency_key UNIQUE |

这是 **分层乐观**：热点在 Redis，DB 用约束做最终一致性兜底。

## 十四、Java 层：重试与异常设计

### 14.1 通用重试模板

```java
public <T> T updateWithRetry(Supplier<Integer> update, int maxRetries) {
    for (int i = 0; i < maxRetries; i++) {
        int rows = update.get();
        if (rows > 0) {
            return ...;
        }
        // 重新 SELECT 最新 version 后再组装 UPDATE
    }
    throw new OptimisticLockException("更新冲突，请重试");
}
```

### 14.2 何时重试、何时直接失败

| 场景 | 建议 |
|------|------|
| 后台编辑 | 不重试，提示用户刷新 |
| 库存扣减 | 0 行 → 直接「库存不足」，不盲目重试 |
| 内部批处理 | 可重试 2～3 次 + 随机退避 |
| 支付 / 核销 | **不重试**，0 行即业务失败 |

### 14.3 错误码示例（智慧书城风格）

| code | 含义 |
|------|------|
| 4008 | 数据版本冲突，请刷新（后台编辑） |
| 4204 | 库存不足（购书） |
| 4102 | 券不可用（核销 CAS 失败） |

## 十五、常见错误

### 错误 1：有 version 但 UPDATE 不带 version 条件

```sql
-- ❌ 丢失版本校验
UPDATE book SET title = ?, version = version + 1 WHERE id = 1;

-- ✅
UPDATE book SET title = ?, version = version + 1 WHERE id = 1 AND version = 12;
```

### 错误 2：先 SELECT 再 UPDATE，不用条件 UPDATE

```java
// ❌ 两步之间可能被插队
Book b = mapper.selectById(id);
b.setSaleStock(b.getSaleStock() - 1);
mapper.updateById(b);

// ✅
mapper.deductSaleStock(id, 1);
```

### 错误 3：把「影响行数=0」都当成乐观锁冲突

| 原因 | 处理 |
|------|------|
| version 冲突 | 提示刷新 / 重试 |
| stock 不足 | 提示售罄 |
| status 不对 | 提示状态不允许 |

要区分 **业务失败** 与 **并发冲突**。

### 错误 4：高冲突场景硬用乐观锁 + 无限重试

秒杀 1000 人抢 10 个名额 → 990 次无效重试，打爆 DB。应 **Redis 前置过滤**。

### 错误 5：@Version 与手写 SQL 混用

MyBatis-Plus 的 `updateById` 带 version，自定义 `@Update` 若不写 version 条件，会 **绕过乐观锁**。

## 十六、本项目中的乐观锁实践地图

| 模块 | 实现方式 | 文件/表 |
|------|----------|---------|
| 购书扣库存 | 数值 CAS `sale_stock >= qty` | `BookMapper.deductSaleStock` |
| 余额支付 | 数值 CAS `balance >= amount` | `AuthUserMapper.deductBalance` |
| 订单支付 | 状态 CAS `PENDING_PAY` | `TradeOrderMapper.markPaid` |
| 券核销 | 状态 CAS `UNUSED` | `UserCouponMapper.markUsed` |
| 券模板限量 | 数值 CAS `issued_count < total_count` | `CouponTemplateMapper` |
| 时段名额 | 数值 CAS + version++ | `ReservationTimeSlotMapper.tryReserve` |
| 座位防超卖 | **悲观锁** `FOR UPDATE` | `ReservationService`（与乐观锁互补） |
| 缓存防覆盖 | version CAS（方案 D） | 高一致性文档 |

**结论**：本项目大量用的是 **条件 UPDATE（状态/数值 CAS）**，这是乐观锁思想在业务里最常用的形态；`reservation_time_slot.version` 为严格 version 乐观锁预留了扩展点。

## 十七、选型决策树

```text
需要更新一行数据，怕并发覆盖
    │
    ├─ 冲突频率极高（秒杀）？
    │     └─ 是 → Redis Lua / MQ，DB 唯一约束兜底
    │
    ├─ 是状态流转？
    │     └─ 是 → WHERE status = 旧状态（案例 3、4）
    │
    ├─ 是库存/余额/名额？
    │     └─ 是 → WHERE stock/balance/count 条件（案例 1、2、6）
    │
    ├─ 是后台同条记录编辑？
    │     └─ 是 → version 列 + MP @Version（案例 7）
    │
    └─ 冲突高且必须强一致顺序执行？
          └─ 是 → SELECT FOR UPDATE（悲观锁），见幂等与行级锁学习文档
```

## 十八、面试答法（30 秒 / 2 分钟）

**30 秒版**：

> 乐观锁假设冲突少，更新时通过 WHERE 条件判断数据是否被改过。常见三种：version 字段、状态 CAS、库存数值 CAS。冲突时 UPDATE 影响行数为 0，业务决定重试还是失败。秒杀级热点用 Redis，不用 DB 乐观锁硬扛。

**2 分钟版（结合项目）**：

> 我们购书支付用 `UPDATE book SET sale_stock = sale_stock - qty WHERE sale_stock >= qty` 做库存 CAS，订单改 PAID 用 `WHERE status = PENDING_PAY` 做状态 CAS，券核销用 `WHERE status = UNUSED`。预约座位级并发用 FOR UPDATE 行锁，时段名额用 booked_count 条件 UPDATE。后台编辑适合 version 乐观锁。乐观锁和悲观锁不是对立，而是按冲突强度分层使用。

## 二十、小结

| 要点 | 内容 |
|------|------|
| 本质 | 用原子 UPDATE 的 WHERE 条件，避免基于过期读覆盖写 |
| 三种形态 | version 列、状态 CAS、数值 CAS |
| 成功判定 | `affected rows > 0` |
| 失败处理 | 区分库存不足、状态不对、版本冲突 |
| 不适用 | 秒杀热点、必须阻塞等待的场景 |
| 本项目 | 支付链大量使用条件 UPDATE；座位用悲观锁；P4 秒杀用 Redis |

乐观锁不是「不用锁」，而是 **把冲突判定推迟到 UPDATE 那一瞬间**——写对了，一样能保证数据正确。
