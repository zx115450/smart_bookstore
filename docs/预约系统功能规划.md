# 预约系统功能规划（挂载统一认证平台）


> **项目**：smart_bookstore（智慧书城） · **文档类型**：学习文档  
> **关联**：`com.zx.reservation` — 预约能力规划  
> **索引**：[学习文档中心](./README.md)

> 适用场景：大二 Java 后端项目，在现有登录/RBAC 体系上扩展轻量业务模块  
> 业务示例：自习室座位、实验室机位、咨询时段、场馆场次  
> 状态主线：**可预约 → 已预约 → 已完成 / 已取消**  
> 最后更新：2026-07

---

## 一、写在前面

预约系统的价值不在于功能多，而在于能讲清：

1. **状态流转**（什么时候能约、能取消、能完成）
2. **并发控制**（同一时段名额不能超卖）
3. **权限边界**（普通用户 vs 管理员）
4. **与认证体系复用**（登录态、角色、审计）

建议采用 **MVP 先跑通 + 1～2 个技术亮点做深** 的策略，不要一开始就做复杂排班、支付、消息推送全家桶。

## 二、业务场景选型（选一个垂直场景）

先定一个具体场景，避免做成「什么都能约」的空壳：

| 场景 | 预约对象 | 时段粒度 | 说明 |
|------|----------|----------|------|
| **自习室座位** ⭐ 推荐 | 座位 + 日期时段 | 2h / 半天 | 名额清晰，并发好讲 |
| 实验室机位 | 设备 + 时段 | 1h | 偏校园 |
| 咨询预约 | 咨询师 + 时段 | 30min | 需「服务人员」维度 |
| 场馆场次 | 场地 + 场次 | 按场 | 容量字段自然 |

下文以 **「自习室座位预约」** 为例描述功能，其他场景可平移替换名词。

## 三、角色与权限

复用现有认证中心的用户与 JWT；业务侧建议至少两个角色：

| 角色 | 编码建议 | 能做什么 |
|------|----------|----------|
| 普通用户 | `USER`（已有） | 浏览资源、创建预约、取消自己的预约、查看自己的记录 |
| 管理员 | `ADMIN`（需新增） | 管理资源/时段、代取消、标记完成、查看全部预约 |

权限实现：Spring Security `@PreAuthorize("hasRole('ADMIN')")` 区分管理接口。

## 四、核心状态机

### 4.1 预约单状态

```text
                    ┌─────────────┐
                    │  已预约     │  BOOKED（创建成功）
                    └──────┬──────┘
           取消          │          到场/到期
              ┌──────────┴──────────┐
              ▼                     ▼
       ┌─────────────┐       ┌─────────────┐
       │  已取消     │       │  已完成     │
       └─────────────┘       └─────────────┘
         CANCELLED              COMPLETED
```

| 状态 | 含义 | 允许的操作 |
|------|------|------------|
| `BOOKED` | 已预约，占用名额 | 用户取消、管理员取消、管理员标记完成 |
| `CANCELLED` | 已取消，释放名额 | 只读 |
| `COMPLETED` | 已使用/已结束 | 只读 |

### 4.2 资源/时段状态（可选，MVP 可简化）

| 状态 | 含义 |
|------|------|
| `AVAILABLE` | 可预约（在开放时间内且未满） |
| `FULL` | 已满（剩余名额为 0） |
| `CLOSED` | 管理员关闭，不可新约 |

MVP 阶段可以不单独存资源状态，用 **容量 - 已约数量** 动态计算是否可约。

## 五、功能清单

### 5.1 MVP（必做，能演示完整流程）

#### 用户端

| # | 功能 | 说明 |
|---|------|------|
| 1 | 登录后访问 | 所有预约接口需 JWT，复用现有 `/api/auth/login` |
| 2 | 资源列表 | 分页展示自习室/区域（名称、位置、总座位数） |
| 3 | 可预约时段查询 | 按资源 + 日期查询时段列表，返回剩余名额 |
| 4 | 创建预约 | 选择资源 + 时段，提交预约 → 状态 `BOOKED` |
| 5 | 我的预约列表 | 分页，支持按状态筛选 |
| 6 | 预约详情 | 查看单条预约信息 |
| 7 | 取消预约 | 仅 `BOOKED` 可取消 → `CANCELLED`，释放名额 |
| 8 | 预约规则校验 | 同一用户同一时段不可重复预约；取消后名额回滚 |

#### 管理端

| # | 功能 | 说明 |
|---|------|------|
| 9 | 资源 CRUD | 新增/编辑/下架自习室（管理员） |
| 10 | 时段模板/生成 | 为资源配置开放时段（如 8:00–22:00，每 2 小时一段） |
| 11 | 全部预约查询 | 管理员分页查看所有预约 |
| 12 | 标记完成 | `BOOKED` → `COMPLETED`（到场核销或定时任务） |

#### 工程基础

| # | 功能 | 说明 |
|---|------|------|
| 13 | 统一响应格式 | 与认证模块一致 `{ code, message, data }` |
| 14 | 参数校验 | 日期、时段 ID、资源 ID 合法性 |
| 15 | 全局异常 | 业务异常转可读错误码（见第七节） |

### 5.2 进阶（选 1～2 个做深，面试加分）

| # | 功能 | 技术点 | 优先级 |
|---|------|--------|--------|
| A | **并发防超卖** | 同一时段剩余名额 > 0 才能约；Redis 预减或 DB 乐观锁 | ⭐⭐⭐ 最推荐 |
| B | **幂等创建** | 前端重复提交 / 网络重试，同一 `Idempotency-Key` 只创建一条 | ⭐⭐⭐ |
| C | 预约状态机封装 | 枚举 + 显式 `canTransitTo()`，拒绝非法跳转 | ⭐⭐ |
| D | 超时自动取消 | 预约开始前 N 分钟未到场自动 `CANCELLED`（定时任务） | ⭐⭐ |
| E | 操作日志 | 预约创建/取消/完成写 audit 表 | ⭐⭐ |
| F | 缓存热点资源 | Redis 缓存资源列表、当日剩余名额（短 TTL） | ⭐ |
| G | 每人每日预约上限 | 如每天最多 2 次 | ⭐ |

**大二阶段建议组合：A（防超卖）+ B（幂等）或 A + C（状态机）。**

---

### 5.3 暂不建议做（范围过大）

- 真实支付、押金、退款
- 短信/邮件提醒（可写进「后续规划」）
- 复杂排班（咨询师轮班、多门店）
- 地图选座、可视化拖拽
- 分布式事务、分库分表

## 六、数据库设计（建议表）

### 6.1 ER 关系概览

```text
auth_user（已有）
    │
    ├── reservation（预约单）──┬── resource（资源：自习室）
    │                            │
    └──                          └── time_slot（时段：某资源某日某段）
```

### 6.2 表结构草案

#### `reservation_resource` 资源表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | |
| name | VARCHAR(64) | 自习室名称 |
| location | VARCHAR(128) | 位置 |
| total_capacity | INT | 总座位/名额 |
| status | TINYINT | 1=启用 0=下架 |
| created_at / updated_at | DATETIME | |

#### `reservation_time_slot` 时段表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | |
| resource_id | BIGINT FK | 所属资源 |
| slot_date | DATE | 日期 |
| start_time | TIME | 开始 |
| end_time | TIME | 结束 |
| capacity | INT | 该时段名额（≤ 资源总容量） |
| booked_count | INT | 已预约数（冗余，便于并发控制） |
| version | INT | 乐观锁版本号（可选） |
| UNIQUE | (resource_id, slot_date, start_time) | 防重复时段 |

#### `reservation_order` 预约单表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | |
| order_no | VARCHAR(32) UNIQUE | 业务单号 |
| user_id | BIGINT FK | 预约人 |
| resource_id | BIGINT FK | |
| time_slot_id | BIGINT FK | |
| status | ENUM | BOOKED / CANCELLED / COMPLETED |
| cancel_reason | VARCHAR(255) NULL | |
| idempotency_key | VARCHAR(64) NULL UNIQUE | 幂等键（进阶） |
| booked_at | DATETIME | |
| cancelled_at / completed_at | DATETIME NULL | |
| created_at / updated_at | DATETIME | |

#### `reservation_audit_log` 操作日志（进阶）

| 字段 | 说明 |
|------|------|
| reservation_id | 预约单 ID |
| operator_id | 操作人 |
| action | CREATE / CANCEL / COMPLETE |
| from_status / to_status | |
| remark | |
| created_at | |

**最少 3 张业务表**（resource、time_slot、order），满足规划指南「表设计可讲」。

## 七、接口规划

Base path 建议：`/api/reservation`（需 JWT，管理员接口加 `ADMIN` 角色）

### 7.1 用户接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/resources` | 资源列表（分页） |
| GET | `/resources/{id}/slots` | 某资源某日可预约时段（query: `date`） |
| POST | `/orders` | 创建预约 |
| GET | `/orders/mine` | 我的预约（query: `status`, `page`） |
| GET | `/orders/{id}` | 预约详情 |
| POST | `/orders/{id}/cancel` | 取消预约 |

### 7.2 管理接口（ADMIN）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/admin/resources` | 创建资源 |
| PUT | `/admin/resources/{id}` | 更新资源 |
| DELETE | `/admin/resources/{id}` | 下架资源 |
| POST | `/admin/resources/{id}/slots/generate` | 批量生成某日/某周时段 |
| GET | `/admin/orders` | 全部预约列表 |
| POST | `/admin/orders/{id}/complete` | 标记完成 |

### 7.3 建议错误码

| code | 含义 |
|------|------|
| 3001 | 时段不存在或已关闭 |
| 3002 | 名额不足 |
| 3003 | 重复预约（同用户同时段） |
| 3004 | 状态不允许该操作 |
| 3005 | 无权操作他人预约 |
| 3006 | 超过每日预约上限 |

## 八、核心流程说明

### 8.1 创建预约（含防超卖思路）

```text
1. 校验 JWT，取 userId
2. 校验时段存在且 slot_date 未过期
3. 校验用户该时段是否已有 BOOKED 记录
4. 【并发】在事务内：
   - 方案 A：UPDATE time_slot SET booked_count = booked_count + 1
             WHERE id = ? AND booked_count < capacity
   - 方案 B：Redis DECR 剩余名额 key，成功后再写 DB
5. 插入 reservation_order，status = BOOKED
6. 失败则回滚名额
```

### 8.2 取消预约

```text
1. 校验预约归属（userId 或 ADMIN）
2. 校验 status == BOOKED
3. 事务：order → CANCELLED；time_slot.booked_count -= 1
4. 写操作日志（可选）
```

### 8.3 标记完成

```text
管理员或定时任务：BOOKED → COMPLETED（不释放名额，表示已消费）
```

## 九、与认证模块的衔接

| 点 | 做法 |
|----|------|
| 登录 | 前端先调 `/api/auth/login`，存 Access Token |
| 鉴权 | 预约 Controller 走现有 `JwtAuthenticationFilter` |
| 当前用户 | `@RequestAttribute(AuthAttributes.AUTH_USER) AuthPrincipal` |
| 角色 | 新增 `ADMIN` 角色 + `auth_user_role` 绑定 |
| 审计 | 可选：关键操作关联 `user_id`，风格对齐 `auth_login_audit` |

简历描述示例：**「基于 JWT + RBAC 的统一认证平台，扩展自习室预约模块，实现时段名额并发控制与预约状态机。」**

## 十二、一句话总结

**预约系统 MVP = 资源 + 时段 + 预约单 + 登录鉴权 + 取消/完成；做深一点就加「名额防超卖」和「状态机/幂等」。** 挂在现有认证项目上，比从零做一个孤立 CRUD 更有简历和面试价值。
