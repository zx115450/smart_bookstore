## 二、一句话结论

这个预约系统里，**最有价值的不是「能预约」本身**，而是：

1. **精确到座的库存占用**（不是粗粒度「还剩 3 个名额」）
2. **并发下不能重复卖同一座**（防超卖）
3. **业务规则 + 状态机 + 权限** 组成的完整闭环

普通列表、详情、CRUD 是配套能力；**防超卖、规则校验、状态流转、幂等** 才是值得写进简历和面试里讲的部分。

## 四、⭐⭐⭐ 核心亮点（面试可讲 5 分钟）

### 4.1 座位粒度防超卖

**问题**：多个用户同时点击「预约 A03 座」，系统不能卖出两次。

**实现**（`ReservationService.createOrder`）：

```text
1. SELECT ... FROM reservation_seat WHERE id = ? FOR UPDATE   ← 行级锁
2. 校验 (time_slot_id, seat_id) 是否已有 status=BOOKED 的订单
3. 事务内 INSERT reservation_order
4. 失败返回 3011「该座位在该时段已被预约」
```

**代码位置**：

- `ReservationSeatMapper.selectByIdForUpdate` — `FOR UPDATE` 锁座位
- `ReservationOrderRepository.existsBookedBySlotAndSeat` — 占用校验
- `ReservationException.seatAlreadyBooked()` — 错误码 3011

**为什么有价值**：

- 涉及 **库存模型**（时段 × 座位）和 **并发控制**，不是简单 INSERT
- 可演示：两个用户同时抢同一座，只有一个成功
- 面试可延伸：行锁 vs 乐观锁 vs Redis 预减库存

---

### 4.2 业务规则组合

创建预约前有一串 **按顺序执行的规则**，不是「参数合法就能插库」：

| 序号 | 规则 | 错误码 | 业务含义 |
|------|------|--------|----------|
| 1 | `timeSlotId`、`seatId` 必填 | 3001 | 基础参数 |
| 2 | 幂等键已存在 | — | 直接返回已有订单 |
| 3 | 时段存在 | 3001 | |
| 4 | 自习室启用 | 3007 | 下架不可约 |
| 5 | 座位存在、属于该自习室、status=1 | 3010 | |
| 6 | 时段开始时间 > 当前时间 | 3009 | 过期不可约 |
| 7 | 用户在该时段无其他 BOOKED 单 | 3003 | 同时段只能约 1 次 |
| 8 | 用户当日 BOOKED+COMPLETED < 2 | 3006 | 每日上限 |
| 9 | 该座位在该时段未被占用 | 3011 | 防超卖 |

常量：`DAILY_ORDER_LIMIT = 2`（`ReservationService`）

**为什么有价值**：

- 体现 **真实产品约束**，不是空壳 CRUD
- 每条规则对应明确错误码，前后端可联调、可测试
- 面试可问：「如果去掉某条规则会怎样？」

---

### 4.3 预约单状态机

**状态**：`BOOKED` → `CANCELLED` / `COMPLETED`

```text
                    ┌─────────────┐
                    │   BOOKED    │
                    └──────┬──────┘
           取消          │          管理员标记完成
              ┌──────────┴──────────┐
              ▼                     ▼
       ┌─────────────┐       ┌─────────────┐
       │  CANCELLED  │       │  COMPLETED  │
       └─────────────┘       └─────────────┘
         释放座位占用           座位视为已消费
         （终态，只读）         （终态，只读）
```

**实现**：`ReservationOrderStatus.canTransitTo()` 显式拒绝非法跳转 → 3004

| 操作 | 权限 | 前置状态 |
|------|------|----------|
| 取消 | 本人或 ADMIN | BOOKED |
| 标记完成 | ADMIN | BOOKED |

**为什么有价值**：

- 非法操作有明确拒绝，不是 silent fail
- 取消 vs 完成对 **座位占用** 的影响不同（释放 vs 消费）
- 可画状态图，答辩清晰

---

### 4.4 幂等创建（idempotencyKey）

**问题**：用户双击「确认预约」、网络超时重试，可能重复创建订单。

**实现**：

```text
请求带 idempotencyKey
→ 查 reservation_order.idempotency_key（UNIQUE）
→ 已存在：直接返回原订单，不重复 INSERT
→ 不存在：正常创建
```

**与 3003 的区别**：

| | idempotencyKey | 3003 重复预约 |
|--|----------------|---------------|
| 防什么 | 同一请求重复提交 | 用户在同一时段约两次 |
| 是否必填 | 可选 | 始终生效 |
| 典型场景 | 双击、网络重试 | 用户换座再约 |

**为什么有价值**：工程上常见、实现成本低、面试常问「如何保证接口幂等」。

## 五、⭐⭐ 业务完整度（补充讲）

### 5.1 三级资源模型

```text
自习室 (reservation_resource)  ← 位置：图书馆 A 区
  └── 座位 (reservation_seat)   ← A01，含 rowNum/colNum 布局
  └── 时段 (reservation_time_slot) ← 2026-07-05 08:00–10:00
        └── 预约单 (reservation_order) ← user + slot + seat
```

**两种「剩余」展示**：

| 接口 | 粒度 | 字段 |
|------|------|------|
| `GET /resources/{id}/slots?date=` | 时段级 | `remainingSeats` = 总座位 − BOOKED 数 |
| `GET /slots/{slotId}/seats` | 座位级 | `available` = 该座是否可约 |

前端可渲染 **座位 Grid 热力图**，比「只选时段」更接近真实自习室场景。

---

### 5.2 取消即释放库存

取消后 `status → CANCELLED`，该 `(time_slot_id, seat_id)` 不再计入 BOOKED：

- 无需手动改 `booked_count`
- `remainingSeats` / `available` 由 **订单状态实时推导**
- 设计简单、行为可解释

---

### 5.3 管理端闭环

| 能力 | 接口 | 说明 |
|------|------|------|
| 创建自习室 | `POST /admin/resources` | 自动按容量生成默认座位 |
| 批量生成座位 | `POST .../seats/generate` | A01–A30 等 |
| 批量生成时段 | `POST .../slots/generate` | 须先有座位 |
| 全部预约 | `GET /admin/orders` | 含 seatNo |
| 核销 | `POST .../orders/{id}/complete` | BOOKED → COMPLETED |

用户端 + 管理端可组成完整 demo / 答辩路径。

---

### 5.4 与统一认证复用

- 用户接口：`@PreAuthorize("hasRole('USER')")`
- 管理接口：`@PreAuthorize("hasRole('ADMIN')")`
- 当前用户：`AuthPrincipal`（userId、roles）
- 数据关联：`reservation_order.user_id → auth_user.id`

**简历表述**：在 JWT + RBAC 统一认证平台上扩展预约模块，而非孤立 CRUD 项目。

## 七、诚实说明：当前可加强的点

### 7.1 时段 `booked_count` 乐观锁未接入

`ReservationTimeSlotMapper` 已定义 `tryReserve` / `release`（`booked_count + 1` 且 `booked_count < capacity`），但 **当前 `createOrder` 未调用**。

现状：名额以 **订单表 BOOKED 记录** 为准，`toSlotResponse` 实时 `countBookedSeatsBySlot`。

**面试说法**：从「时段计数」演进到「座位级占用」；计数改为统计订单，粒度更细。

### 7.2 未使用 Redis 预减库存

当前：**MySQL 事务 + 行锁**，对 MVP / 大二项目够用。

**可扩展**：高并发下 Redis 预减 + DB 双检（写在「后续规划」即可）。

### 7.3 未实现的能力（可选扩展）

- 操作审计表（CREATE / CANCEL / COMPLETE）
- 超时未到场自动取消（定时任务）
- 短信/邮件提醒

## 八、简历 / 答辩提炼

### 8.1 推荐描述（一段话）

> 在统一认证平台（JWT + RBAC）上扩展自习室座位预约模块。采用 **资源 → 座位 → 时段 → 预约单** 四级模型；创建预约时在事务内通过 **行锁 + 占用校验** 防止同一座位超卖；**状态机** 管理 BOOKED / CANCELLED / COMPLETED；支持 **幂等键** 防重复提交；业务规则含 **每日预约上限、同时段唯一预约、过期时段拦截**；管理端支持座位/时段批量生成与核销。

### 8.2 只讲 2 个最深的技术点

1. **座位级防超卖**：`FOR UPDATE` + `(slot_id, seat_id)` 唯一占用 + 3011  
2. **业务规则 + 状态机**：不是裸 CRUD，每条规则有错误码、每个状态有合法跳转

### 8.3 答辩演示路径（3 分钟）

```text
1. admin 登录 → 自习室列表
2. 选日期 → 看 remainingSeats
3. 选时段 → 座位图，available 灰/绿
4. 预约 A03 → 成功，展示 orderNo + seatNo
5. （可选）并发抢座 → 3011
6. 取消 → 座位 available 恢复
7. ADMIN → 标记完成
```

## 九、与错误码对照

| code | 含义 | 价值点关联 |
|------|------|------------|
| 3003 | 您已预约该时段 | 业务规则 |
| 3004 | 当前状态不允许该操作 | 状态机 |
| 3005 | 无权操作他人预约 | 权限 |
| 3006 | 超过每日预约上限 | 业务规则 |
| 3009 | 时段已过期 | 业务规则 |
| 3010 | 座位不存在或已停用 | 数据校验 |
| 3011 | 该座位在该时段已被预约 | **防超卖** |
