## 第 1 章 认证与登录（`com.zx.auth`）

### 1.1 为什么用双 Token？Access 和 Refresh 各自职责？

**答**：
- **Access Token**：JWT，短期（默认 7200s），放在前端内存 / Authorization Header；每次业务请求都带；无状态可被验证。
- **Refresh Token**：服务端生成的 `jti:random` 形式随机串，长期（默认 7 天，Remember Me 30 天），存于 `auth_session` 表（含 `refresh_token_hash = SHA-256(refresh)`）；只在刷新时上送。
- **职责切分**：Access 短 → 即使泄露窗口小；Refresh 长 → 服务端可控可吊销；轮换 → 一次性使用，每次刷新作废旧 Session、签新 Session。

**追问：为什么 Refresh 不直接做成 JWT？**
答：JWT 无状态难以吊销；我们要支持「登出撤销」「绝对过期」「同账号互踢」，必须服务端有状态，所以 Refresh 走 DB Session 表 + Hash 比对，Access 才用 JWT。

### 1.2 登录全链路时序？

**答**（`AuthService.login`）：
1. `LoginRequest` 带 `loginType`（password / email_code / phone_code / qq_oauth）。
2. `resolveLoginKey` 决定限流键（密码 → account；OAuth → state；验证码 → target）。
3. `authRedisService.checkLoginAllowed`：查 Redis 失败计数，超 `login-fail-max=5` 锁 15 分钟。
4. `LoginHandlerFactory.getHandler(type)` 工厂分发到对应 `LoginHandler`：`PasswordLoginHandler` / `EmailCodeLoginHandler` / `PhoneCodeLoginHandler` / `QqOAuthLoginHandler`。
5. Handler 校验返回 `AuthUser`；失败则 `recordLoginFailure` + 审计；成功则 `clearLoginFailure`。
6. `ensureDefaultUserRole` 给默认 `USER` 角色。
7. `createSessionAndResponse` → `createRotatedSession`：生成 `jti = UUID`、`refresh = jti + ":" + UUID`；计算 `accessExp = now + 7200s`、`absoluteExp = now + 90d`、`slidingRefreshExp = now + 7d/30d`；`refreshExp = min(slidingRefreshExp, absoluteExp)`；存 `AuthSession`（`refreshTokenHash = SHA-256(refresh)`）；签 Access JWT（含 `userId / username / sid / roles / typ=access / jti`）。
8. 写 `AuthLoginAudit` 审计。

### 1.3 Refresh 轮换怎么做？为什么这样设计？

**答**（`AuthService.refresh`）：
1. 拆 `refresh = jti:random`，取 `jti`。
2. `sessionRepo.findByRefreshTokenJti(jti)` 找 Session。
3. 校验：`revokedAt == null`、`absoluteExpiresAt > now`、`refreshExpiresAt > now`、`refreshTokenHash == SHA-256(明文)`。
4. **作废旧 Session**：`s.setRevokedAt(now)` 并 save。
5. **签新 Session**：`createRotatedSession` 复用 `user / rememberMe / loginIp`，**继承 `absoluteExpiresAt`**（绝对过期不可延长），新 `slidingRefreshExp` 重新算。
6. 返回新 Access + 新 Refresh。

**设计点**：
- 一次性轮换：旧 Refresh 用一次即作废，防重放。
- 绝对过期继承：90 天硬上限，无论怎么刷新都不能突破。
- 滑动过期可延长：7 天内不操作即失效，活跃用户每次刷新续 7 天。
- 同账号多端：每个 Session 独立，互不影响；显式 `revokeAllByUserId` 才能互踢。

**追问：检测到旧 Refresh 被复用怎么办？**
答：`if (s.getRevokedAt() != null) sessionRepo.revokeAllByUserId(s.getUserId())` —— 一次性 Refresh 被复用说明可能泄露，直接吊销该用户全部 Session，强制重新登录。

### 1.4 登出怎么让 JWT 立即失效？

**答**（`AuthService.logout`）：
1. 解析 Access 取 `jti` 和 `exp`。
2. `authRedisService.blacklistAccessToken(jti, ttl=exp-now)`：把 jti 写入 Redis 黑名单，TTL 设为 Token 剩余有效期。
3. `sessionRepo.revokeById(sessionId)`：撤销 Session，使 Refresh 也失效。
4. 若有 Refresh，也撤销对应 Session。

**追问：为什么不让 JWT 本身可吊销？**
答：JWT 无状态、签名校验本地完成，无法主动吊销；只能用「黑名单 + 短 TTL」折中：Access 短到 2h，黑名单只存 2h，Redis 压力可控。

**追问：黑名单的 Key 怎么设计？**
答：`auth:blacklist:access:{jti}`，TTL = Token 剩余秒数；`JwtAuthenticationFilter` 每次请求 `isAccessBlacklisted(jti)` 查一次 Redis。

### 1.5 JwtAuthenticationFilter 怎么工作？

**答**（`JwtAuthenticationFilter extends OncePerRequestFilter`）：
1. `shouldNotFilter`：非 `/api/` 前缀或 `PUBLIC_PATHS`（登录、刷新、发码、登出、QQ OAuth、媒资回调）直接放行。
2. 取 `Authorization: Bearer <token>`；空 Token：`OPTIONAL_AUTH_PATHS`（`/api/ai/chat`）匿名放行；其他返回 401 `TOKEN_MISSING`。
3. `jwtService.parseAccessToken`：验签 + 验 Issuer + 验 `typ=access`，取 `userId / username / sessionId / roles / jti`。
4. `isAccessBlacklisted(jti)` → 401 `TOKEN_REVOKED`。
5. `sessionRepository.findById(sessionId)`：Session 不存在 / 已撤销 → 401 `SESSION_REVOKED`。
6. 校验 `absoluteExpiresAt` 与用户 `status=1`。
7. 构造 `AuthPrincipal(userId, username, sessionId, roles)`，写入 `request.setAttribute`。
8. 构造 `UsernamePasswordAuthenticationToken` + `ROLE_xxx` authorities，写入 `SecurityContextHolder`。
9. `finally` 清 `SecurityContextHolder.clearContext()`，避免线程池串号。

### 1.6 RBAC 怎么落地？

**答**：
- 表：`auth_user` / `auth_role` / `auth_user_role` / `auth_user_identity`。
- `RoleConstants.ADMIN = "ADMIN"`、`USER = "USER"`。
- `SecurityConfig.securityFilterChain`：`/api/admin/**`、`/api/reservation/admin/**`、`/api/ai/admin/**` 走 `hasRole("ADMIN")`，其余 `authenticated()`。
- 方法级：`@EnableMethodSecurity` + `@PreAuthorize("hasRole('ADMIN')")`。
- Filter 注入 `ROLE_ADMIN` / `ROLE_USER` authority，Spring Security 自动匹配 `hasRole`（自动加 `ROLE_` 前缀）。

### 1.7 登录限流怎么做的？

**答**（`AuthRedisService` + `AuthRateLimitProperties`）：
- **发码限流**：`send-code-per-target-seconds=60`（同目标 60s 一次）、`send-code-per-target-hourly=5`（同目标每小时 5 次）、`send-code-per-ip-hourly=10`（同 IP 每小时 10 次）。
- **登录失败锁定**：`login-fail-max=5`、`login-fail-lock-minutes=15`；用 Redis `INCR` + `EXPIRE`，超限直接抛 `AuthException`。
- **验证码 TTL**：`verification-code-ttl-seconds=300`，5 分钟内有效。

### 1.8 QQ 扫码登录流程？

**答**（`QqOAuthController` + `QqOAuthService` + `QqOAuthClient`）：
1. 前端调 `GET /api/auth/oauth/qq/state`：服务端生成 `state`，存 Redis（TTL 600s），返回 `authorizeUrl`。
2. 用户在 QQ 扫码授权，QQ 回调 `GET /api/auth/oauth/qq/callback?code=...&state=...`。
3. 服务端校验 `state`（防 CSRF），调 QQ 换 `access_token`，再调 QQ 取 `openid`。
4. `AuthUserIdentity` 表按 `openid` 查找：已绑定 → 直接登录；未绑定 → 创建新用户 + 写 `auth_user_identity`，或返回前端让用户绑定已有账号。
5. 走 `QqOAuthLoginHandler` 复用 `createSessionAndResponse`，返回 Token；前端跳 `frontend-success-url`。

### 1.9 工厂模式在登录里怎么用？

**答**：
- `LoginHandler` 接口 + `LoginHandlerFactory`：按 `loginType` 分发到 `PasswordLoginHandler` / `EmailCodeLoginHandler` / `PhoneCodeLoginHandler` / `QqOAuthLoginHandler`。
- `SendCodeHandler` + `SendCodeHandlerFactory`：按 `loginType` 分发到 `EmailSendCodeHandler` / `PhoneSendCodeHandler`。
- 新增登录方式只需新增 Handler 类 + 注册到 Factory，`AuthService` 不动，符合开闭原则。

## 第 2 章 自习室预约（`com.zx.reservation`）

### 2.1 怎么防超卖？

**答**（`ReservationService.createOrder`）：
1. **幂等查询**：先按 `idempotencyKey` 查 `reservation_order`，已存在直接返回。
2. **校验时段 / 资源 / 座位合法性**。
3. **行级锁**：`seatRepository.findByIdForUpdate(seatId)` → `SELECT ... FOR UPDATE`，锁住该座位行直到事务结束。
4. **业务校验（锁内）**：座位属于该资源、`status=1`、时段未过期、用户当日预约数 `<2`、用户未重复预约该时段、该座位该时段未被占。
5. **写订单**：`status=BOOKED`、`idempotencyKey`、`bookedAt=now`。

**追问：为什么用 `FOR UPDATE` 而不是乐观锁？**
答：座位预约是「时段 × 座位」强冲突场景，冲突率高，乐观锁会大量重试；行锁直接串行化，简单可靠。乐观锁更适合冲突低的库存场景。

**追问：锁粒度能不能更细？**
答：可以锁 `reservation_order` 表的 `(time_slot_id, seat_id)` 唯一索引，靠唯一约束兜底；但行锁更直观，且能做更多业务校验。

### 2.2 预约状态机？

**答**（`ReservationOrderStatus`）：`BOOKED → CANCELLED` / `COMPLETED`，`canTransitTo` 控制合法转移。
- `BOOKED`：已预约，未到时间。
- `CANCELLED`：用户取消或管理员取消。
- `COMPLETED`：到馆签到完成或时段结束自动完成。

### 2.3 幂等怎么保证？

**答**：
- 表 `reservation_order.idempotency_key` 加唯一索引。
- 创建订单前先 `findByIdempotencyKey`，命中直接返回。
- 即使两个请求同时进来，唯一索引会让其中一个抛 `DuplicateKeyException`。

### 2.4 当日预约数限制怎么做？

**答**：`orderRepository.countActiveOrdersByUserAndDate(userId, slotDate) >= DAILY_ORDER_LIMIT(=2)` 即拒绝。SQL 按 `user_id + slot_date + status in (BOOKED, COMPLETED)` 统计。

### 2.5 时段 / 座位 / 资源三级模型？

**答**：
- `ReservationResource`：场馆（名称、位置、总容量、状态）。
- `ReservationSeat`：座位（`seatNo`、`rowNum`、`colNum`、`status`），属于某 Resource。
- `ReservationTimeSlot`：时段（`slotDate`、`startTime`、`endTime`、`capacity`、`bookedCount`），属于某 Resource。
- 预约 = `Resource × TimeSlot × Seat` 三元组。

### 2.6 管理端怎么批量生成座位和时段？

**答**（`generateSeats` / `generateSlots`）：
- 座位：按 `rows × cols` 或 `count` 生成 `seatNo = prefix + 行列号`，`existsByResourceAndSeatNo` 去重。
- 时段：按 `date ~ endDate`、`startHour ~ endHour`、`durationHours` 循环生成，`existsByResourceDateStart` 去重。
- 生成后回写 `resource.totalCapacity = seatRepository.countEnabledByResource`。

## 第 3 章 图书目录与缓存（`com.zx.bookstore.catalog`）

### 3.1 图书详情缓存怎么设计的？

**答**：L1 Caffeine 本地缓存 + L2 Redis 分布式缓存 + 布隆过滤器防穿透 + 逻辑过期防击穿 + 热点探测长 TTL，由 `BookCacheFacade` 统一编排。

读路径（`BookCatalogService.getBookDetail`）：
1. `bookCacheMetrics.onRequest()` 计数。
2. **布隆过滤**：`bookBloomRedisService.mightContain(id)` 返回 `false` → 直接 404，不打 L1/L2/MySQL。
3. **L1 命中**：`bookCacheFacade.getLocal(id)` → 命中则 `onL1Hit` + `recordAccess` + 返回。
4. **L2 命中**：`bookCacheFacade.getRedis(id)` → 命中则 `fillLocal`（回填 L1）+ `onL2Hit` + `recordAccess` + 返回。
5. **DB 回源**：`bookRepository.findEnabledById` → 命中则 `loadAndCacheBook`（写 L2 + L1）+ `onMiss`；未命中则 `onBloomFalsePositive`（布隆假阳性）+ 404。

### 3.2 布隆过滤器怎么实现？为什么用？

**答**（`BookBloomRedisService`）：
- **目的**：拦截「不存在的 bookId」查询，防止缓存穿透打爆 MySQL。
- **存储**：Redis Bitmap，Key `book:bloom:ids`，全站共享一份。
- **参数**：`bloom-expected-elements=100000`、`bloom-false-positive-rate=0.01`，由 `BloomFilterSpec.of(n, p)` 算出 `m`（bit 数）和 `k`（哈希函数数）。
- **写入**：`add(bookId)` 对 k 个 offset `SETBIT 1`，新书创建后增量写入。
- **查询**：`mightContain(bookId)` 对 k 个 offset `GETBIT`，任一为 0 → 一定不存在；全为 1 → 可能存在。
- **预热**：`bloom-warmup-on-startup=true` 时启动加载所有 bookId 重建。
- **fail-open**：Redis 异常时返回 `true` 放行查 DB，保证可用性优先。

**追问：布隆能不能删？**
答：经典布隆不支持删除（bit 不能 0）；下架书的 id 仍占 bit，最坏多查一次 DB。要支持删除得用 Counting Bloom Filter。

**追问：假阳性怎么处理？**
答：`onBloomFalsePositive` 计数 + 抛 `bookNotFound`；不写空值缓存（布隆已经挡住大部分）。

### 3.3 逻辑过期防击穿怎么实现？

**答**（`LogicalExpireCacheClient`）：
- **载荷**：`RedisLogicalData { expireTime, data, absent }`，物理 TTL = 逻辑 TTL + 1h 缓冲，保证逻辑过期后 Key 仍在。
- **读**：
  1. miss → `loadOnMiss`：抢互斥锁（`SETNX lockKey TTL=30s`），抢到则查 DB + 写逻辑过期；没抢到则 `waitForCache` 轮询 3s 等他人写完；超时再抢一次，仍失败则降级直接查 DB 不写缓存。
  2. 命中且未逻辑过期 → 直接返回。
  3. 命中但逻辑过期 → 抢锁，抢到则**异步重建**（线程池 10 线程，重建完释放锁），当前线程**返回旧值**；没抢到则直接返回旧值。
- **空值**：`saveAbsent(key, ttl=2min)` 短物理 TTL 防穿透。
- **重建线程池**：`Executors.newFixedThreadPool(10, daemon=true)`，`@PreDestroy` 优雅关闭 60s。

**追问：为什么不用物理 TTL + 互斥锁？**
答：物理 TTL 到期 Key 立刻消失，大量请求同时回源；逻辑过期让 Key 永远在，只让一个线程异步重建，其他线程拿旧值，吞吐高但接受短暂脏读。

**追问：锁怎么释放？**
答：重建任务 `finally { unlock(lockKey) }`，`unlock = DEL`；锁 TTL 30s 防止重建线程崩溃死锁。

### 3.4 热点探测怎么做的？

**答**（`BookHotKeyService` + `bookstore.cache.hot-*`）：
- 分桶滑动窗口：`hot-window-seconds=60`、`hot-bucket-seconds=10`（6 个桶）。
- 每次访问 `recordAccess(bookId)`：当前桶计数 +1。
- 超 `hot-threshold=50` 判定为热点，Redis Key TTL 升级为 `hot-detail-ttl-seconds=7200`（+ 随机抖动 600s）。
- `hot-max-tracked-keys=5000` 防止冷 Key 占内存。

### 3.5 TTL 抖动防雪崩？

**答**：`detail-ttl-seconds=1800`、`detail-ttl-jitter-seconds=300`，写 Redis 时 `TTL = base + random(jitter)`，避免大量 Key 同时过期引发雪崩。

### 3.6 缓存一致性怎么保证？

**答**：Cache-Aside + 主动失效：
- 读：缓存 miss → DB → 写缓存。
- 写：先写 DB，事务提交后 `bookCacheFacade.evict(id)`（同时删 L2 Redis + L1 Caffeine）。
- 容忍短暂不一致：L1 是本机堆，多实例间有差异，靠短 TTL（60s）自然收敛。
- 强一致场景可加 Binlog（Canal/Debezium）监听 `book` 表变更删缓存，本仓库规划为可选演进。

### 3.7 库存变更日志？

**答**（`BookStockLogService` + `book_stock_log` 表）：
- `recordSaleOut`：售出扣 `sale_stock`。
- `recordBorrowOut` / `recordBorrowIn`：借出 / 归还 `borrow_stock`。
- `recordAdminAdjust`：管理员调整库存，记 `old → new` 备注。
- 字段：`bookId / delta / type / orderId / operatorId / remark / createdAt`，用于对账和审计。

## 第 4 章 图书借阅（`com.zx.bookstore.borrow`）

### 4.1 借阅状态机？

**答**（`BorrowOrderStatus`）：
- `APPLIED`（已申请待确认）→ `BORROWED`（已借出） / `CANCELLED`（拒绝/取消）。
- `BORROWED` → `OVERDUE`（逾期） / `RETURNED`（已归还）。
- `OVERDUE` → `RETURNED` / 续借回 `BORROWED`。
- `canTransitTo` 控制合法转移，非法转移抛 `BorrowException.invalidStatus`。

### 4.2 申请借书怎么校验库存？

**答**（`BorrowService.apply`）：
1. 用户不能有未处理的 `APPLIED` 单（`hasPendingApplyByUser`）。
2. 用户不能有未还的书（`hasActiveBorrowByUser`）。
3. `bookRepository.findByIdForUpdate(bookId)` 行锁锁住书。
4. 校验 `borrowStock > countAppliedByBookId(bookId)`：库存 > 已申请数（含未确认的）才允许申请。
5. 写 `BorrowOrder`，`status=APPLIED`。

**追问：为什么用 `countAppliedByBookId` 而不是直接看 `borrowStock`？**
答：申请单未确认时不扣库存，但占用「待确认名额」；如果只看 `borrowStock`，可能超额申请导致后续无法确认。

### 4.3 确认借出怎么扣库存？

**答**（`BorrowService.confirm`）：
1. 状态机校验 `APPLIED → BORROWED`。
2. `bookRepository.findByIdForUpdate(bookId)` 行锁。
3. `stock > 0` 校验。
4. `updateToBorrowed(orderId, now, dueAt=now+borrowDays)`：CAS 式 UPDATE，`rows==0` 则 reload 重判。
5. `book.setBorrowStock(stock - 1)` + `saveBorrowStock`。
6. `borrowDueRedisService.scheduleDue(orderId, dueAt)`：写 Redis ZSET，score = `dueAt` 的 Unix 秒。
7. `bookStockLogService.recordBorrowOut` 记日志。

### 4.4 续借怎么处理？为什么续借能恢复线上阅读？

**答**（`BorrowService.renew`）：
- 限制：每张借阅单最多续借 1 次（`MAX_RENEW=1`）。
- 状态：`BORROWED` 或 `OVERDUE` 都可续借。
- 应还日：未到期则从原 `dueAt` 顺延 `borrowDays`；已逾期则从 `now` 起算，状态恢复 `BORROWED`。
- `updateRenew(orderId, dueAt, MAX_RENEW)` CAS UPDATE，`rows==0` 则 reload 重判（防并发续借）。
- 重新 `scheduleDue` 到 ZSET。

**线上阅读联动**：电子书章节解锁依赖借阅状态，`OVERDUE` 时全文降级为试看；续借回 `BORROWED` 后恢复全文解锁。

### 4.5 逾期调度怎么做？

**答**（`BorrowDueRedisService` + `BorrowOverdueScheduler` + `lua/borrow_due_pop.lua`）：
- **写入**：`confirm` 时 `ZADD borrow:due:zset orderId score=dueAt.epoch`。
- **弹出**：调度器 `@Scheduled(fixedDelay=60s)`，调 `popDueOrderIds(nowEpoch, batchSize=100)`：
  ```lua
  local members = redis.call('ZRANGEBYSCORE', key, '-inf', maxScore, 'LIMIT', 0, limit)
  for i = 1, #members do redis.call('ZREM', key, members[i]) end
  return members
  ```
  原子取出 score ≤ now 的 orderId 并删除。
- **DB 更新**：对每个 orderId `updateToOverdue`，`rows>0` 才计数。
- **归还移除**：`returnBook` 时 `removeDue(orderId)` 从 ZSET 移除（幂等）。
- **兜底**：`reconcileOverdueBatch` 直接 SQL `UPDATE ... WHERE status='BORROWED' AND due_at < now LIMIT batchSize`，防止 Redis ZADD 失败或历史数据漏入 ZSET。

**追问：为什么用 ZSET 不用延迟队列？**
答：ZSET 简单、可范围查、可移除（归还即删）；延迟队列要为每单发一条消息、归还时还得取消，成本高。ZSET 适合「到期批量扫描」类调度。

**追问：调度器多实例会不会重复处理？**
答：`updateToOverdue` 是 CAS UPDATE（`WHERE status='BORROWED'`），`rows>0` 才标记成功；多实例并发跑也只有一条实例能改成功，天然幂等。

### 4.6 借阅四种逾期实现思路对比？

**答**（见 `借阅逾期四种实现思路对比.md`）：
1. **定时全表扫描**：简单，但扫描成本高、延迟大、DB 压力大。
2. **延迟队列**：精准，但归还取消消息复杂、消息体大。
3. **Redis ZSET + Lua**：精准、可移除、批量扫描，本仓库选型。
4. **时间轮**：单机精准，分布式需 Redisson，复杂度高。

### 4.7 行锁 + CAS UPDATE 的双层并发保护？

**答**：
- 行锁：`findByIdForUpdate` 锁住 Book 行，串行化扣库存操作。
- CAS UPDATE：`updateToBorrowed(orderId, now, dueAt) WHERE status='APPLIED'`，`rows==0` 说明状态已被改，reload 重判。
- 双层保护：行锁防并发扣超库存，CAS 防并发改状态。

## 第 5 章 到馆签到（`com.zx.marketing.checkin`）

### 5.1 BitMap 连续签到怎么实现？

**答**（`CheckinRedisService`）：
- **月历 BitMap**：Key `sign:user:{userId}:{yyyyMM}`，offset = `dayOfMonth - 1`，`setBit` 1 表示签到。
- **TTL**：40 天，跨月自动新建。
- **月历查询**：`getMonthlyCalendar` 循环 `getBit` 返回 0/1 数组。
- **今日是否签到**：`hasCheckedInToday` = `getBit(monthKey, today.dayOfMonth - 1)`。

### 5.2 连续天数 streak 怎么算？

**答**（`updateStreak`）：
- Key `sign:last:{userId}` 存上次签到日期（`yyyy-MM-dd`）。
- Key `sign:streak:{userId}` 存连续天数。
- 逻辑：若 `last == yesterday` → `INCR streak`（连续 +1）；否则 → `SET streak = 1`（断签重置）。最后写 `last = today`。

**追问：跨月怎么算连续？**
答：只看 `last == yesterday`，与月份无关；只要昨天签了今天就连续。

### 5.3 满 7 天赠券怎么做？

**答**（`CheckinService` + `CouponService`）：
- `streak-reward-days=7`：连签满 7 天触发。
- 触发后调 `couponService.issueCheckinCoupon(userId, templateId)`，写 `user_coupon` 表，`obtain_way=CHECKIN`。
- 防重复：`user_coupon` 加唯一索引 `(user_id, checkin_cycle)`，每个 7 天周期只能领一次。

### 5.4 场馆码怎么生成？

**答**（`getOrCreateDailyVenueCode`）：
- Key `venue:checkin:code:{venueId}:{date}`。
- 首次访问随机生成 6 位字符（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，去掉易混淆字符），TTL 到当天结束 + 1h。
- 后续访问直接返回已有码。
- 校验：`validateDailyVenueCode` 比对 Redis 中的码（忽略大小写）。

### 5.5 签到时间窗？

**答**：`window-minutes-before=15`、`window-minutes-after=15`，预约时段开始前 15 分钟到结束后 15 分钟内可签到，超窗拒绝。

### 5.6 签到与预约怎么联动？

**答**：签到时校验用户当天是否有该场馆的有效预约（`BOOKED` 状态），无预约不允许签到；签到后预约单写 `checkinAt`。

## 第 6 章 优惠券（`com.zx.bookstore.coupon`）

### 6.1 优惠券模板与用户券模型？

**答**：
- `CouponTemplate`：券模板（类型、面额、门槛、有效期、发行量）。
- `UserCoupon`：用户持有的券（`userId / templateId / status / obtainWay / orderId / usedAt`）。
- `CouponObtainWay`：`CHECKIN`（连签赠）、`SECKILL`（秒杀抢）、`ADMIN_GRANT`（管理员发放）。
- `CouponType`：`FIXED_AMOUNT`（满减）、`PERCENT_DISCOUNT`（折扣）。
- `UserCouponStatus`：`UNUSED / USED / EXPIRED`。

### 6.2 策略模式怎么用？

**答**（`CouponDiscountCalculatorFactory` + `CouponDiscountCalculator`）：
- 接口 `CouponDiscountCalculator`：`calculate(totalAmount, template) → discountAmount`。
- 实现：`FixedAmountCalculator`（满减）、`PercentDiscountCalculator`（折扣）。
- 工厂 `CouponDiscountCalculatorFactory.getCalculator(type)` 按 `CouponType` 分发。
- 新增券类型只需新增 Calculator + 枚举，`CouponService` 不动。

### 6.3 下单算价流程？

**答**（`TradeService.createOrder` → `CouponService.calculateDiscount`）：
1. 算 `totalAmount = sum(price * quantity)`。
2. `couponService.calculateDiscount(userId, userCouponId, totalAmount)`：
   - 校验券属于用户、状态 `UNUSED`、未过期、满足门槛。
   - 调对应 Calculator 算 `discountAmount`。
3. `payAmount = totalAmount - discountAmount`（≥0）。
4. 支付成功后 `couponService.markUsed(userId, couponId, orderId)`：状态 `USED` + 写 `orderId / usedAt`。

### 6.4 优惠券退款怎么回退？

**答**：当前流程支付成功即核销券；若后续支持退款，需 `markUnused` 把券状态回 `UNUSED`、清空 `orderId`。本仓库规划为可选演进。

## 第 7 章 购书交易（`com.zx.bookstore.trade`）

### 7.1 下单流程？

**答**（`TradeService.createOrder`）：
1. **幂等**：`findByIdempotencyKey` 命中直接返回。
2. **解析订单行**：从购物车 `cartItemIds` 或直接 `bookId + quantity`。
3. **算价**：`totalAmount = sum(price * qty)`；`discountAmount = couponService.calculateDiscount`；`payAmount = max(0, total - discount)`。
4. **写订单**：`TradeOrder`（`status=PENDING_PAY`）+ `TradeOrderItem` 列表。
5. **清购物车**：若来自购物车，删对应 `CartItem`。
6. **延迟关单**：`scheduleOrderTimeoutCancel` —— 事务提交后（`TransactionSynchronization.afterCommit`）发 MQ 延迟消息，`unpaid-cancel-delay-minutes=15`。

**追问：为什么 afterCommit 才发 MQ？**
答：避免事务回滚后消息已发出导致「无订单却触发关单」；保证消息一定对应已提交的订单。

### 7.2 支付怎么扣库存 + 扣余额？

**答**（`TradeService.pay`）：
1. 校验订单属于用户、状态 `PENDING_PAY`。
2. 遍历 `TradeOrderItem`：
   - `bookRepository.findByIdForUpdate(bookId)` 行锁。
   - `deductSaleStock(bookId, quantity)` CAS 扣 `sale_stock`，`rows==0` 抛 `outOfStock`。
   - `bookStockLogService.recordSaleOut` 记日志。
3. `authUserRepository.findByIdForUpdate(userId)` 行锁用户。
4. `deductBalance(userId, payAmount)` CAS 扣余额，`rows==0` 抛 `insufficientBalance`。
5. `markPaid(orderId, userId)` CAS 改状态，`rows==0` 抛 `invalidStatus`。
6. `couponService.markUsed` 核销券。
7. 写 `paidAt = now`。

**追问：为什么下单时不扣库存、支付时才扣？**
答：超时未支付占库存会浪费；支付时才扣，配合延迟关单释放名额，库存利用率高。代价是支付时可能 `outOfStock`，需前端提示重试。

### 7.3 延迟关单怎么实现？

**答**（`TradeMqProducer` + `TradeOrderTimeoutConsumer` + `TradeMqConfig`）：
- 拓扑：`bookstore.topic` 交换机 → `trade.order.timeout` 队列（无消费者，靠消息 TTL + DLX 回到主队列）→ `trade.order.timeout.consume` 消费队列。
- 发送：`publishOrderTimeout(message)`，消息 `expiration = unpaid-cancel-delay-minutes * 60 * 1000`。
- 到期：消息从 `trade.order.timeout` 经 DLX 回到 `trade.order.timeout.consume`。
- 消费：`TradeOrderTimeoutConsumer` 调 `TradeService.cancelOnTimeout`。

### 7.4 cancelOnTimeout 怎么保证幂等？

**答**：
1. 查订单不存在 → 跳过。
2. 状态非 `PENDING_PAY` → 跳过（已支付/已取消不重复处理）。
3. `markCancelledByTimeout(orderId)` CAS UPDATE（`WHERE status='PENDING_PAY'`），`rows==0` 说明被其他实例先处理，跳过。

### 7.5 死信兜底？

**答**（`TradeOrderTimeoutDeadLetterConsumer`）：
- 主消费队列 `trade.order.timeout.consume` 配 `x-dead-letter-exchange` → `trade.dlx`。
- 消费失败 Nack(requeue=false) → 进 `trade.order.timeout.dlq`。
- 死信消费者记录失败原因，人工对账；不重投主队列避免死循环。

### 7.6 用户取消订单？

**答**（`TradeService.cancel`）：状态 `PENDING_PAY` 才能取消，`markCancelled` CAS UPDATE。支付后不能取消，需走退款流程。

## 第 8 章 优惠券秒杀（`com.zx.bookstore.seckill`）

### 8.1 秒杀全链路？

**答**（`SeckillService.grab`）：
1. **幂等查询**：`findOrderByIdempotencyKey` 命中直接返回已有订单状态。
2. **用户维度查重**：`findOrderByUserAndActivity` 命中且 `PROCESSING` 直接返回；命中非 `PROCESSING` 抛 `alreadyParticipated`。
3. **活动校验**：`findEnabledActivity` + `validateActivityWindow`（活动进行中）。
4. **双维度令牌桶限流**：`seckillRateLimitService.assertAllowed(activityId, userId)`。
5. **Redis Lua 原子抢券**：`seckillRedisService.grab(activityId, userId)` 返回 0/1/2。
6. **发 MQ**：`seckillMqProducer.publishSeckillOrder(message)`；失败则 `rollbackGrab` 回滚 Redis + 抛 `systemBusy`。
7. **返回**：`status=PROCESSING`，前端轮询结果。

### 8.2 Lua 脚本怎么保证原子性？

**答**（`lua/seckill_grab.lua`）：
```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then return 0 end
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return 2 end
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return 1
```
- `KEYS[1] = seckill:stock:{activityId}`、`KEYS[2] = seckill:users:{activityId}`、`ARGV[1] = userId`。
- 返回：0=售罄、1=抢中待发 MQ、2=已参与。
- Redis 单线程执行 Lua，整个「判库存 + 判重复 + 扣库存 + 记用户」原子完成，无需加锁。

**追问：为什么不用 `WATCH/MULTI/EXEC`？**
答：WATCH 乐观锁在高并发下冲突率高、重试成本大；Lua 脚本天然原子，一次往返完成，性能远超事务。

### 8.3 双维度令牌桶限流？

**答**（`SeckillRateLimitService` + `lua/seckill_token_bucket.lua`）：
- **活动维度**：`activity-capacity=2000`、`activity-refill-per-second=2000`，防活动整体被打爆。
- **用户维度**：`user-capacity=2`、`user-refill-per-second=1`，防单用户狂点。
- Lua 实现：`HMGET key tokens last_ms` → 按 `elapsed * rate / 1000` 补令牌 → `filled = min(filled, capacity)` → `filled >= acquire` 则 `filled -= acquire` 返回 1，否则返回 0。
- Key TTL `key-ttl-seconds=7200`，冷活动自动清理。

**追问：为什么先限流再 Lua 抢券？**
答：限流在「真正尝试占库存」之前；未拿到令牌不消耗库存、不进 Set，避免无效请求压 Redis。

### 8.4 MQ 异步落库？

**答**（`SeckillService.processSeckillOrder` + `SeckillOrderConsumer`）：
1. 消费 MQ 消息。
2. 幂等检查：`findOrderByIdempotencyKey` / `findOrderByUserAndActivity` 命中直接返回。
3. 校验活动存在。
4. 写 `SeckillOrder`（`status=PROCESSING`），靠 `uk_seckill_user_activity` / `uk_seckill_idempotency` 兜底并发。
5. `couponService.issueSeckillCoupon` 发券：
   - 成功 → `status=SUCCESS` + 写 `userCouponId`。
   - 失败 → `status=FAILED` + 写 `failReason` + `rollbackGrab` 回滚 Redis；**不抛异常**，让主消费 ACK，死信只兜早期失败。

### 8.5 死信对账怎么做？

**答**（`SeckillService.reconcileDeadLetter` + `SeckillDeadLetterConsumer`）：
- 主队列 Nack(requeue=false) → `seckill.dlx` → `seckill.order.dlq`。
- 对账逻辑：
  1. 已 `SUCCESS` → 忽略。
  2. 已 `FAILED` 但 Redis 仍占名额 → 补 `rollbackGrab`。
  3. 卡在 `PROCESSING` → 标 `FAILED` + 回滚 Redis。
  4. 无订单但 Redis 占名额 → `rollbackGrab`。
  5. 无订单无 Redis → 无需处理。
- **不重投主队列**，避免死循环。

### 8.6 库存预热与回滚？

**答**（`SeckillRedisService`）：
- **预热**：`warmUpStock(activityId, stock, endTime)` —— `SET stockKey stock` + `DEL usersKey` + `EXPIRE` 到活动结束 + 1 天。
- **回滚**：`rollbackGrab(activityId, userId)` —— `INCR stockKey` + `SREM usersKey userId`。
- **轮询**：`getResult` 时若 DB 无订单但 `hasGrabbedUser` 返回 true，说明 Lua 成功但 Consumer 未落库，返回 `PROCESSING`。

### 8.7 一人一单三层保障？

**答**：
1. Redis Set `sismember` 判重（Lua 内）。
2. DB 唯一索引 `uk_seckill_user_activity (user_id, activity_id)`。
3. DB 唯一索引 `uk_seckill_idempotency (idempotency_key)`。
- Redis 挡大部分请求，DB 兜底并发竞态。

### 8.8 MQ 重试策略？

**答**（`bookstore.mq.retry`）：
- 默认 `strategy=queue`：失败投 `seckill.order.retry`（TTL）后 Ack，到期 DLX 回主队列；超次 Nack 进 DLQ。
- 可选 `strategy=local`：消费线程内 `RetryTemplate` 重试。
- `max-attempts=3`、`initial-interval-ms=1000`、`multiplier=2.0`、`max-interval-ms=10000`。
- 业务异常 / `IllegalArgumentException` 不进重试，直接 DLQ。

### 8.9 RabbitMQ 拓扑结构？

**答**（`RabbitMqConfig`）：
```
bookstore.topic ──seckill.order──► seckill.order
      │ 失败未超次：发到 seckill.order.retry（TTL）后 Ack
      │                 │ 到期 DLX
      │                 └──seckill.order──► seckill.order（回主队列）
      │ 超次/不可重试：Nack(requeue=false)
      ▼
seckill.dlx ──► seckill.order.dlq
```
- `bookstore.topic`：Topic 交换机，业务消息路由。
- `seckill.dlx`：Direct 交换机，死信路由。
- 队列均 `durable=true`，重启不丢消息。

## 第 9 章 AI 客服（`com.zx.ai`）

### 9.1 Spring AI 怎么集成？

**答**：
- 依赖：`spring-ai-starter-model-openai`（OpenAI 兼容协议）+ `spring-ai-starter-vector-store-milvus`。
- 配置：`spring.ai.openai.chat.api-key=DeepSeek`、`spring.ai.openai.embedding.api-key=DashScope`（千问）。
- 自动装配：`MilvusVectorStoreAutoConfiguration` 默认 exclude，由 `AiVectorConfig` 在 `ai.rag.enabled=true` 时 `@Import` 显式导入。

### 9.2 ChatClient 怎么编排？

**答**（`AiChatConfig`）：
```java
ChatClient aiChatClient = builder
    .defaultSystem(SYSTEM_PROMPT)
    .defaultAdvisors(MessageChatMemoryAdvisor.builder(aiChatMemory).build())
    .defaultTools(bookSearchTool, bookDetailTool, faqTool, borrowTool,
                 bookRecommendTool, userReadingProfileTool)
    .build();
```
- **System Prompt**：强约束「查书类必须先调 searchBooks/getBookDetail」「规则类必须先调 searchFaq」「个人借阅类必须先调 getMyBorrowOrders」「推荐类必须先调 recommendBooks」「禁止编造业务数据」。
- **ChatMemory Advisor**：`MessageWindowChatMemory` 滑动窗口，`maxMessages = maxHistoryTurns * 2`（一轮含 user + assistant 两条）。
- **Tool Calling**：Spring AI 2.0 默认 `ToolCallingAdvisor` 自动循环调工具直到模型不再请求。

### 9.3 ChatMemory 怎么持久化？

**答**（`RedisStringChatMemoryRepository` + `MessageWindowChatMemory`）：
- 自定义 `ChatMemoryRepository` 实现，存 Redis String，Key `ai:chat:memory:{conversationId}`。
- `conversationId` 构造：登录 `user:{userId}:{sessionId}`，匿名 `anon:{sessionId}`。
- `MessageWindowChatMemory` 滑动窗口：超过 `maxMessages` 自动裁剪旧消息，保留最近 N 轮。
- TTL `ai.session.ttl-minutes=30`，超时会话自动清理。

**追问：为什么不用 InMemory？**
答：多实例部署时内存不共享；Redis 持久化 + 共享，会话跨实例可恢复。

### 9.4 业务 Tool 有哪些？

**答**（`com.zx.ai.tool`）：
1. `BookSearchTool.searchBooks(keyword, limit)`：关键词搜书，返回架位、库存、是否有电子书。
2. `BookDetailTool.getBookDetail(bookId)`：图书详情。
3. `FaqTool.searchFaq(topic)`：FAQ 规则查询，先语义召回（RAG）再关键词匹配兜底。
4. `BorrowTool.getMyBorrowOrders(status)`：当前用户借阅单（从 `AiUserContext` 取 userId）。
5. `BookRecommendTool.recommendBooks(intent, seedBookId)`：推荐（EXPLORE/LEARN/SIMILAR/RELAX/PERSONALIZED）。
6. `UserReadingProfileTool.getUserReadingProfile()`：用户阅读画像（基于借阅历史）。

### 9.5 怎么防止模型编造？

**答**：
1. **System Prompt 强约束**：明确「禁止编造书名、架位、库存、规则细节、接口路径、时间数值」。
2. **Tool description 互补**：每个 `@Tool` 的 `description` 写明「必须先调用本工具」「只能根据工具返回回答」。
3. **Tool 返回 `found=false` 时引导**：明确告知用户「暂无该规则/书」，不假装查到。
4. **个人类 Tool 取 userId 从 ThreadLocal**：禁止让模型传 userId，防止越权。
5. **`AiUserContext` finally 清理**：避免线程池串号。

### 9.6 RAG 怎么实现？

**答**（`SemanticFaqRecaller` + `FaqEmbeddingIndexer` + Milvus）：
- **索引阶段**：`FaqEmbeddingIndexer` 把 FAQ 条目用千问 `text-embedding-v3`（1024 维）向量化，写入 Milvus collection `bookstore_book`，`metadata.type='faq'`。
- **召回阶段**：`SemanticFaqRecaller.recall(query, topK)` 调 `vectorStore.similaritySearch(SearchRequest.query().topK(8).similarityThreshold(0.6).filterExpression("type == 'faq'"))`。
- **降级**：Milvus 不可用时 `FaqTool` 通过 `ObjectProvider` 容忍缺失，降级为关键词匹配。
- **共用 collection**：FAQ 与图书向量同存 `bookstore_book`，靠 `type` filter 区分。

### 9.7 ChatCard 是什么？

**答**（`ChatCardCollector` + `ChatCard`）：
- Tool 内部 `ChatCardCollector.offerBooks(books)` 把结构化卡片塞 ThreadLocal。
- AI Service `chat` 后 `ChatCardCollector.drain()` 取出卡片，随 `ChatResponse` 返回前端。
- 前端除展示模型文本回复外，还能渲染卡片（图书列表、借阅单等），提升 UX。

### 9.8 限流？

**答**：`ai.rate-limit.per-user-hourly=30`，按 userId 限流；匿名按 IP 限流。超限抛 `AiException.rateLimited`。

### 9.9 异常处理？

**答**（`AiExceptionHandler` + `AiException`）：
- `AiException.badRequest / unavailable / rateLimited` 等工厂方法。
- `@RestControllerAdvice` 统一捕获，返回 `{ code, message, data: null }`。
- 模型调用异常统一包装为「AI 服务暂时不可用，请稍后重试」，不暴露底层细节。

## 第 10 章 数字阅读与笔记 Agent（`com.zx.reader`）

### 10.1 试看与解锁机制？

**答**（`ChapterAccessService` + `reader.preview.default-chapters=2`）：
- 默认前 2 章免费试看。
- 第 3 章起需「借阅中 `BORROWED`」或「已购买 `PAID`」才能解锁。
- `OVERDUE` / `RETURNED` / `APPLIED` 状态降级为试看，不能解锁全文。
- 解锁后电子书全文 + 完整视频可读；降级时只能试看前 2 章 + 视频前 5 分钟。

### 10.2 BFF 读章怎么做？

**答**（`EbookReaderController` + `EbookReaderService`）：
- 前端调 `GET /api/reader/ebooks/{ebookId}/chapters/{chapterNo}`。
- BFF 服务端校验权限后返回章节正文（Markdown）。
- 不把电子书原文直接暴露给前端，防止绕过权限抓取。
- `ChapterTextCache` 缓存章节正文，减少 DB 查询。

### 10.3 阅读进度合并落库？

**答**（`ReadingProgressService` + `ProgressRedisStore` + `ReaderProgressMqProducer` + `ProgressFlushConsumer`）：
- **Redis 热写**：每次 `updateProgress` 写 `ProgressHotState { chapterId, charOffset, lastActiveMs, dirty }` 到 Redis。
- **延迟合并**：同章偏移只写 Redis，不发 MQ；首次或换章才即时写 MySQL。
- **MQ 延迟消息**：`scheduleFlush(userId, ebookId)` 发延迟消息 `delay-ms=10000`。
- **到期处理**（`onFlushDue`）：
  - `dirty=false` → `markClean` 退出。
  - `now - lastActiveMs < idle-ms=5000` → 仍在阅读，再延后（滑动窗口）。
  - 否则 → `persist` 写 MySQL + `markClean`。
- **换章即时写库**：`previousChapterId != newChapterId` 时立即 `persist`，避免换章丢失进度。
- **afterCommit 标记**：`markCleanAfterCommit` 在事务提交后才清 dirty，避免回滚后状态不一致。

**追问：为什么用 Redis + MQ 而不是直接写 DB？**
答：阅读进度高频更新（每秒可能多次），直接写 DB 压力大；Redis 热写 + MQ 延迟合并，把多次写合并成一次 DB 写，DB 压力降一个数量级。

**追问：换章为什么即时写库？**
答：换章是「关键节点」，用户切换章节后立即关闭 App，若延迟写库可能丢失「已读到第 N 章」的事实；同章偏移丢失影响小（重读几行），换章丢失影响大。

### 10.4 Study Agent 是什么？

**答**（`StudyAgentService` + `StudyAgentTools` + `StudyAgentConfig`）：
- 独立 ChatClient `studyChatClient`，挂载学习专用 Tool：`getChapterContent / getMyNotes / saveNote / summarizeChapter / rewriteNote / mergeNotes`。
- 会话键 `study:user:{userId}:{sessionId}`，与客服会话隔离。
- 限流 `reader.agent.rate-limit-per-user-hourly=20`、`max-input-chars=12000`、`max-history-turns=8`。
- `StudyAgentContext` ThreadLocal 存 `userId / ebookId / roles`，Tool 内部取，禁止模型传 userId。

### 10.5 Study Agent 工具设计原则？

**答**：
- **不覆盖原文**：`rewriteNote` / `mergeNotes` 另存为 `AI_REWRITE` / `AI_MERGE`，原笔记保留。
- **不编造**：`summarizeChapter` 必须先 `getChapterContent` 取正文，无权限返回 `ok=false`，禁止编造。
- **总结缓存**：`StudySummaryCacheService` 按 `(ebookId, chapterNo)` 缓存总结，命中直接用，未命中调模型生成 + 写缓存。
- **划线摘录限制**：`reader.notes.max-quote-on-locked=80`，锁定章节划线最多 80 字。

### 10.6 媒资集成？

**答**（`MediaAccessService` + `BookMediaRef` + `Lite VOD`）：
- `BookMediaRef` 关联 `bookId ↔ ebookId ↔ mediaId`。
- 调媒资平台（Lite VOD）获取播放地址与对象签名。
- `bookstore.media.lite-vod.mock=true` 时走 Mock，不连 8080；生产改 `false` + 配 `internal-token`。
- 媒资回调 `MediaCallbackController` 校验 `X-Internal-Token`，无 JWT。

### 10.7 阅读板块错误码？

**答**：阅读板块用 `51xx` 段，如 `5101` 电子书不存在、`5103` 章节未解锁、`5105` 笔记不存在等，与认证 `1xxx`、预约 `3xxx`、书城 `4xxx` 区分。

## 第 11 章 中间件深度

### 11.1 Redis 拓扑怎么动态切换？

**答**（`RedisDeployConfiguration` + `BookstoreRedisProperties` + `bookstore.redis.mode`）：
- `mode=standalone`：单节点。
- `mode=master-replica`：主从，`read-from=REPLICA_PREFERRED` 优先读从。
- `mode=sentinel`：哨兵，`master=mymaster`、`nodes=host:26379`。
- `mode=cluster`：分片集群，`nodes` 种子节点、`max-redirects=5`。
- `RedisDeployConfiguration` 按 mode 注入对应 `LettConnectionFactory`，`read-from` 控制读写策略。
- 环境变量 `REDIS_MODE` 切换，无需改代码。

**追问：Cluster 模式为什么 `database` 必须为 0？**
答：Redis Cluster 不支持 `SELECT` 切库，所有 Key 共享 0 库。

### 11.2 Redisson 怎么用？

**答**：
- 依赖 `redisson-spring-boot-starter` 4.6.1（Spring Boot 4.x 需 4.0+）。
- 提供分布式锁 `RLock`、布隆过滤器 `RBloomFilter`、限流器 `RRateLimiter` 等高级数据结构。
- 本仓库主要用 StringRedisTemplate + Lua 脚本手写，Redisson 作为兜底方案。

### 11.3 RabbitMQ 怎么保证不丢消息？

**答**：
- **生产端**：`spring.rabbitmq.publisher-confirm-type=correlated` + `publisher-returns=true`，确认消息到达 Exchange 与 Queue。
- **Broker**：队列 `durable=true`、消息 `deliveryMode=2`（持久化）、镜像队列（可选）。
- **消费端**：`acknowledge-mode=manual`，业务成功才 `basicAck`；失败 `basicNack(requeue=false)` 进 DLQ。
- **TTL 重试**：失败消息投 retry 队列（无消费者，靠消息 TTL + DLX 回主队列），实现延迟重试。

### 11.4 MySQL 索引设计？

**答**：
- 唯一索引：`uk_seckill_user_activity`、`uk_seckill_idempotency`、`uk_reservation_order_idempotency`、`uk_user_coupon_checkin_cycle`。
- 联合索引：`(user_id, status, created_at)` 支持用户订单分页查询；`(book_id, status)` 支持图书借阅查询。
- 覆盖索引：列表查询尽量走覆盖索引避免回表。

### 11.5 Flyway 怎么管理 schema？

**答**（`db/migration`）：
- `V1__init_schema.sql`：基线 schema（auth + reservation + bookstore + checkin）。
- `V2__reader_schema.sql`：阅读板块（ebook + chapter + note + progress）。
- `V3__borrow_renew_count.sql`：借阅单加 `renew_count` 字段。
- 配置：`baseline-on-migrate=true`、`baseline-version=1`、`validate-on-migrate=true`。
- 空库直接执行 V1；已有库无历史表记 baseline=1 跳过 V1。

**追问：为什么不用 JPA 自动建表？**
答：JPA 自动建表不可控、不可追溯；Flyway 版本化 SQL 显式可审查、可回滚、可对账。

### 11.6 Milvus 向量库怎么用？

**答**：
- 依赖 `spring-ai-starter-vector-store-milvus`，配置 `host/port=19530`、`collection-name=bookstore_book`、`embedding-dimension=1024`（千问 v3）。
- 索引 `IVF_FLAT` + `COSINE` 距离。
- `initialize-schema=false`：Spring AI 2.0 + Milvus 2.6 用空 indexName 调 describeIndex 会报错，集合需预先建好并建索引。
- 启动时 `BookIndexPrewarmer` 可选预热（`ai.rag.prewarm-on-startup=false` 默认关）。

## 第 12 章 工程与规范

### 12.1 四层架构？

**答**：
- **Controller**：`@RestController`，参数校验、调用 Service、组装响应。
- **Service**：`@Service`，业务编排、事务边界、调用 Repository。
- **Repository**：`@Repository`（MyBatis-Plus Mapper），数据访问，复杂 SQL 在 XML 或注解。
- **Entity**：POJO，对应表结构，`@TableName` 注解。

**追问：为什么不用 DDD？**
答：项目规模适中，四层够用；DDD 过度设计增加复杂度。Repository 层已隔离数据访问，未来可平滑演进到 DDD。

### 12.2 统一响应体？

**答**：`{ code, message, data }`，`code=0` 成功，非 0 错误码。
- 1xxx 认证、3xxx 预约、4xxx 书城、5xxx 阅读（51xx）、6xxx AI。
- `@RestControllerAdvice` + `ExceptionHandler` 统一捕获业务异常返回该格式。
- Filter 层（如 `JwtAuthenticationFilter`）直接写 JSON，不走 Controller，手动构造响应体。

### 12.3 异常体系？

**答**：
- `ErrorCode` 枚举：定义所有错误码与消息。
- `BookstoreException` / `BorrowException` / `ReservationException` / `TradeException` / `SeckillException` / `CheckinException` / `AiException` / `ReaderException` 各模块异常基类。
- 各模块 `ExceptionHandler` 捕获本模块异常，转统一响应体。
- `IllegalArgumentException` 等通用异常由全局 handler 处理。

### 12.4 工厂模式有哪些应用？

**答**：
- `LoginHandlerFactory`：登录方式分发。
- `SendCodeHandlerFactory`：发码渠道分发。
- `CouponDiscountCalculatorFactory`：优惠券计算策略分发。
- `LoginHandler` / `SendCodeHandler` / `CouponDiscountCalculator` 都是接口 + 多实现 + 工厂分发，符合开闭原则。

### 12.5 可观测性？

**答**（`spring-boot-starter-actuator` + `micrometer-registry-prometheus`）：
- 暴露 `/actuator/health,info,prometheus,metrics`。
- `BookCacheMetrics` 自定义计数：`onRequest / onL1Hit / onL2Hit / onMiss / onBloomReject / onBloomFalsePositive`。
- `management.metrics.tags.application=smart_bookstore` 全局标签。
- Prometheus 抓取 → Grafana 看板，监控缓存命中率、QPS、错误率。

### 12.6 测试策略？

**答**（`src/test` + Testcontainers）：
- **单元测试**：Service 层用 Mockito mock Repository。
- **集成测试**：Testcontainers 拉真实 MySQL / Redis / RabbitMQ，测端到端流程。
- **Lua 脚本测试**：`bookstore.cache.logical` 等包测逻辑过期、布隆、令牌桶。
- **AI 测试**：`ai.faq` / `ai.rag` / `ai.recommend` / `ai.tool` 测语义召回与 Tool 行为。

### 12.7 配置敏感信息管理？

**答**：
- `application.yaml` 放公开配置，占位符 `${DB_URL:}`。
- `application-local.yaml`（gitignore）放本地敏感配置（DB 密码、JWT secret、API key）。
- 生产用环境变量覆盖：`DB_URL / DB_USERNAME / DB_PASSWORD / JWT_SECRET / DEEPSEEK_API_KEY / DASHSCOPE_API_KEY / QQ_APP_ID`。
- `auth.jwt.secret` 必须 ≥256 bit 随机串。

### 12.8 Nginx 前端部署？

**答**（`nginx-smart-bookstore/`）：
- 便携 Nginx + 前端静态包，端口 `8088`。
- `/api` 反代到后端 `8081`。
- 启动：`nginx-smart-bookstore\start.bat`（Windows）。
- 生产用独立 Nginx + 域名 + HTTPS。

## 第 13 章 高频追问与对比题

### 13.1 JWT vs Session

| 维度 | JWT | Session |
| --- | --- | --- |
| 状态 | 无状态 | 服务端有状态 |
| 扩展 | 天然分布式 | 需 Redis 共享 |
| 吊销 | 难（需黑名单） | 易（删 Session） |
| 大小 | 较大（含 claims） | 小（仅 sessionId） |
| 本仓库 | Access 用 JWT | Refresh 用 Session 表 |

### 13.2 Cache-Aside vs Write-Through vs Write-Behind

| 模式 | 读 | 写 | 一致性 | 本仓库 |
| --- | --- | --- | --- | --- |
| Cache-Aside | miss 回源写缓存 | 先写 DB 再删缓存 | 最终一致 | ✓ |
| Write-Through | 同步读缓存 | 同步写缓存 + DB | 强 | ✗ |
| Write-Behind | 同步读缓存 | 异步写 DB | 弱 | ✗ |

### 13.3 布隆过滤器 vs Counting Bloom

| 维度 | 布隆 | Counting Bloom |
| --- | --- | --- |
| 删除 | 不支持 | 支持（计数位） |
| 空间 | 紧凑 | 略大（计数） |
| 假阳性 | 有 | 有 |
| 假阴性 | 无 | 无 |
| 本仓库 | Bitmap 布隆 | ✗ |

### 13.4 逻辑过期 vs 物理过期 + 互斥锁

| 维度 | 逻辑过期 | 物理过期 + 互斥锁 |
| --- | --- | --- |
| Key 存在 | 永在 | 到期消失 |
| 击穿 | 不击穿（拿旧值） | 可能击穿（锁前 miss） |
| 脏读 | 短暂容忍 | 无 |
| 吞吐 | 高 | 锁竞争时低 |
| 本仓库 | 超级热点 Key | 普通详情 Cache-Aside |

### 13.5 ZSET 延迟调度 vs 延迟队列 vs 时间轮

| 方案 | 精度 | 可移除 | 分布式 | 复杂度 | 本仓库 |
| --- | --- | --- | --- | --- | --- |
| ZSET + Lua | 秒级 | ✓ | ✓ | 低 | ✓ 借阅逾期 |
| RabbitMQ TTL | 秒级 | ✗ | ✓ | 中 | 订单超时 |
| 时间轮 | 槽位级 | ✓ | 需 Redisson | 高 | ✗ |

### 13.6 乐观锁 vs 悲观锁

| 维度 | 乐观锁 | 悲观锁 |
| --- | --- | --- |
| 实现 | version 字段 + CAS | `FOR UPDATE` |
| 冲突低 | 优 | 浪费 |
| 冲突高 | 重试多 | 优 |
| 本仓库 | 借阅 `updateRenew` CAS | 预约 `findByIdForUpdate` |

### 13.7 MQ 重试：队列 TTL vs 本地 RetryTemplate

| 方式 | 优点 | 缺点 | 本仓库 |
| --- | --- | --- | --- |
| 队列 TTL | Broker 等待不占消费线程 | 多一次网络往返 | 默认 |
| 本地 RetryTemplate | 无网络开销 | 占消费线程 | 可选 |

### 13.8 Spring AI Tool Calling vs 手写 Function Calling

| 维度 | Spring AI Tool | 手写 |
| --- | --- | --- |
| 注册 | `@Tool` 注解自动 | 手动 JSON Schema |
| 调用 | 框架自动循环 | 手动解析 + 调用 |
| 上下文 | ThreadLocal + Advisor | 手动传 |
| 本仓库 | ✓ | ✗ |

## 第 14 章 简历话术与答辩要点

### 14.1 项目亮点话术（30 秒口述）

> 我做的智慧书城是一个综合业务平台，覆盖认证、预约、借阅、交易、秒杀、AI 客服、数字阅读 Agent 七大板块。技术上有三个亮点：第一，多级缓存防穿透防击穿防雪崩，用布隆过滤器挡不存在查询、逻辑过期互斥重建挡热点 Key、TTL 抖动防雪崩；第二，秒杀全链路用双维度令牌桶限流 + Redis Lua 原子扣库存 + RabbitMQ 异步落库 + 死信对账补偿，保证高并发下不超卖不漏单；第三，AI 客服用 Spring AI Tool Calling，System Prompt 强约束模型「事实走 Tool、禁止编造」，6 个业务 Tool + ChatMemory 多轮 + Milvus RAG 语义召回 FAQ。

### 14.2 难点话术

> 最难的是秒杀的一致性。Lua 脚本能原子扣库存，但 MQ 发送失败、Consumer 处理失败、Consumer 卡在 PROCESSING 都会导致 Redis 与 DB 不一致。我的解法是分三层兜底：第一层 MQ 发送失败立即 `rollbackGrab` 回滚 Redis；第二层 Consumer 发券失败标 FAILED + 回滚 Redis，不抛异常让主 Consumer ACK，避免事务回滚冲掉 FAILED 状态；第三层死信队列对账，对 SUCCESS 忽略、FAILED 补回滚、PROCESSING 标 FAILED + 回滚、无订单但 Redis 占名额的也回滚，覆盖所有不一致场景。

### 14.3 量化指标话术

- 缓存命中率：L1 + L2 命中率 > 95%，DB QPS 降一个数量级。
- 秒杀峰值：单活动 2000 QPS 令牌桶限流，Lua 抢券 < 1ms，MQ 异步落库削峰填谷。
- 借阅逾期：ZSET + Lua 调度延迟 < 60s，SQL 兜底保证不漏。
- AI 客服：Tool Calling 平均 2-3 轮收敛，RAG 召回 top-8 相似度阈值 0.6。

### 14.4 答辩高频问题

**Q：为什么不用 Redisson 分布式锁做秒杀？**
A：Redisson 锁是「先到先得」串行化，QPS 受限于锁持有时间；Lua 脚本一次往返完成判库存+扣库存+判重，无锁竞争，吞吐高一个数量级。

**Q：布隆过滤器假阳性怎么处理？**
A：假阳性率配置 0.01，命中后继续查 L1/L2/MySQL，最坏多一次 DB 查询；`onBloomFalsePositive` 计数监控，假阳性率超阈值时重建过滤器。

**Q：JWT 黑名单 Redis 挂了怎么办？**
A：Redis 挂时 `isAccessBlacklisted` fail-open 返回 false（放行），保证可用性；Access TTL 仅 2h，窗口可控；Redis 恢复后黑名单继续生效。

**Q：MQ 消费顺序怎么保证？**
A：秒杀不要求严格顺序，单活动单队列 FIFO 即可；若需严格顺序，可按 `activityId` 路由到同一队列，单消费者串行消费。

**Q：阅读进度合并落库会不会丢数据？**
A：Redis 持久化（AOF + RDB）+ MQ 持久化（durable + persistent）双重保护；最坏 Redis 宕机丢失 5s 内进度，用户重读几行可接受；换章即时写库保证关键节点不丢。

**Q：AI 客服怎么防止模型乱调 Tool？**
A：System Prompt 明确每个 Tool 的触发场景与禁止项；Tool description 写明「必须先调用」「禁止编造」；Tool 返回 `ok=false` 时引导模型如实转达；`AiUserContext` ThreadLocal 防止模型伪造 userId 越权。

**Q：项目里你最有成就感的设计？**
A：阅读进度合并落库。借鉴视频进度落库思路，Redis 热写 + MQ 延迟消息滑动窗口 + 换章即时写库 + afterCommit 标记，把高频写合并成低频 DB 写，DB 压力降一个数量级，同时保证关键节点不丢。

### 14.5 项目演进方向

1. **搜索**：MySQL `LIKE` → Elasticsearch 全文检索 + Binlog（Canal/Debezium）同步。
2. **限流**：单机令牌桶 → Sentinel 集群限流。
3. **调度**：`@Scheduled` → XXL-JOB 分布式调度。
4. **网关**：Nginx → Spring Cloud Gateway 统一鉴权。
5. **监控**：Prometheus → + SkyWalking 链路追踪。
6. **AI**：单模型 → 多模型路由（DeepSeek 通用 + GPT-4 复杂推理）。

## 第 15 章 Java / Spring 八股结合项目

### 15.1 Spring Bean 生命周期

**答**：实例化 → 属性注入 → `BeanNameAware`/`BeanFactoryAware` → `ApplicationContextAware` → `BeanPostProcessor.postProcessBeforeInitialization` → `@PostConstruct` → `InitializingBean.afterPropertiesSet` → `@Bean(initMethod)` → `BeanPostProcessor.postProcessAfterInitialization` → 使用 → `@PreDestroy` → `DisposableBean.destroyBean` → `@Bean(destroyMethod)`。

**项目应用**：`SeckillRedisService.@PostConstruct` 加载 Lua 脚本；`LogicalExpireCacheClient.@PreDestroy` 关闭线程池；`BookBloomRedisService.@PostConstruct` 计算 `BloomFilterSpec`。

### 15.2 Spring 事务传播行为

| 传播 | 含义 | 本仓库 |
| --- | --- | --- |
| REQUIRED（默认） | 有则加入，无则新建 | 大部分 Service |
| REQUIRES_NEW | 总是新建 | 审计日志（独立提交） |
| NESTED | 嵌套事务（保存点） | ✗ |
| SUPPORTS | 有则加入，无则非事务 | ✗ |

**追问：自调用为什么事务失效？**
答：同类内方法调用走 `this`，不经代理；需注入自己或 `AopContext.currentProxy()`。本仓库 `ReadingProgressService.onFlushDue` 标 `@Transactional` 避免自调 `persist` 失效。

### 15.3 @Transactional 失效场景

1. 方法非 public。
2. 自调用（同类内 `this.method()`）。
3. 异常被 catch 不抛出。
4. 抛 checked 异常未配 `rollbackFor`。
5. 类非 Spring Bean（new 出来的）。
6. `final`/`static` 方法。

**项目规避**：Service 方法全 public；自调用方法单独标 `@Transactional`；异常统一抛 `XxxException`（RuntimeException 子类）。

### 15.4 ThreadLocal 原理与内存泄漏

**答**：每个 Thread 持有 `ThreadLocalMap`，key 是 `ThreadLocal` 弱引用，value 是强引用。key 被 GC 后 value 仍强引用 → 内存泄漏。需 `remove()` 清理。

**项目应用**：`AiUserContext` / `StudyAgentContext` / `ChatCardCollector` 都用 ThreadLocal，`finally` 中 `clear()`。

### 15.5 Redis 为什么单线程还快？

**答**：
- 纯内存操作，无磁盘 IO。
- IO 多路复用（epoll）单线程处理大量连接。
- 单线程无锁竞争、无上下文切换。
- 6.0 后 IO 多线程（写 socket），命令执行仍单线程。

**项目应用**：Lua 脚本原子执行秒杀扣库存，无需分布式锁。

### 15.6 MySQL InnoDB 锁

| 锁 | 粒度 | 模式 | 本仓库 |
| --- | --- | --- | --- |
| 行锁 | 行 | 共享/排他 | `FOR UPDATE` 预约座位 |
| 间隙锁 | 区间 | 排他 | 唯一索引防幻读 |
| 临键锁 | 行+间隙 | 排他 | 范围查询 |
| 意向锁 | 表 | IS/IX | 加行锁前自动 |

**追问：`FOR UPDATE` 走什么锁？**
答：等值命中唯一索引 → 行锁；等值未命中 → 间隙锁；范围查询 → 临键锁。本仓库预约按 `seatId` 主键等值查询，命中行锁。

### 15.7 MySQL 事务隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 本仓库 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | ✓ | ✓ | ✓ | ✗ |
| READ COMMITTED | ✗ | ✓ | ✓ | ✗ |
| REPEATABLE READ（默认） | ✗ | ✗ | ✓(MVCC) | ✓ |
| SERIALIZABLE | ✗ | ✗ | ✗ | ✗ |

**追问：RR 怎么解决幻读？**
答：MVCC（快照读）+ 临键锁（当前读）。`FOR UPDATE` 是当前读，加临键锁防幻读。

| Broker → 消费 | manual ACK | ✓ |
| 消费失败 | Nack + DLQ | ✓ |

## 第 16 章 场景题与系统设计

### 16.1 如果 QPS 涨 10 倍怎么扩容？

**答**：
1. **应用层**：无状态，直接水平扩容，K8s HPA 按 CPU 自动扩。
2. **MySQL**：读写分离（主写从读）+ 分库分表（按 user_id 分片）。
3. **Redis**：主从 → 哨兵 → 分片集群，`bookstore.redis.mode` 切换。
4. **RabbitMQ`：镜像队列 → 联邦 → 分片。
5. **限流**：单机令牌桶 → Sentinel 集群限流。
6. **缓存**：本地缓存扩容 + Redis 集群 + 多级降级。

### 16.2 缓存与 DB 不一致怎么排查？

**答**：
1. 看 `BookCacheMetrics`：命中率突降 → 缓存失效异常。
2. 看 `book_stock_log`：库存变更日志对账。
3. 看 Redis Monitor：是否有异常 DEL。
4. 看 Binlog：DB 是否被外部直接改。
5. 解法：先修数据，再排查根因（evict 顺序、TTL、并发写）。

### 16.3 秒杀活动开始前 5 分钟发现库存配错了怎么办？

**答**：
1. 管理端 `updateActivity` 改 `seckillStock`，但活动进行中不允许改（`ongoing` 校验）。
2. 先 `disableActivity` 下架活动（`status=0`），Redis Key 仍在但 `findEnabledActivity` 拒绝。
3. 修正 `seckillStock` 后重新启用，`warmUpStock` 重置 Redis 库存与用户 Set。
4. 已抢用户（Set 内）需手动补偿或公告重新抢。

### 16.4 借阅逾期调度器挂了怎么办？

**答**：
1. ZSET 数据不丢（Redis 持久化）。
2. 调度器重启后 `popDueOrderIds` 继续弹出过期单。
3. `reconcileOverdueBatch` SQL 兜底，直接 `UPDATE ... WHERE status='BORROWED' AND due_at < now`，不依赖 ZSET。
4. 双保险：即使 ZSET 全丢，SQL 兜底也能标记逾期。

### 16.5 AI 客服模型返回慢（10s+）怎么办？

**答**：
1. 前端流式输出（SSE），首 token < 1s 即可感知。
2. 设置超时 `spring.ai.openai.chat.options.timeout`，超时返回「AI 服务繁忙」。
3. 降级：简单 FAQ 直接走关键词匹配，不调模型。
4. 限流：`per-user-hourly=30` 防滥用。
5. 异步：复杂问题转工单，后台处理。

### 16.6 MQ 消费堆积怎么办？

**答**：
1. 看消费 TPS：`rabbitmqctl list_queues name messages consumers`。
2. 临时扩消费者：`concurrency` 调大，多实例消费。
3. prefetch 调小（`spring.rabbitmq.listener.simple.prefetch=10`）避免一个消费者囤太多。
4. 业务降级：跳过非关键步骤（如审计日志），快速 ACK。
5. 死信兜底：超时未消费转 DLQ 人工处理。

### 16.7 Redis 大 Key / 热 Key 怎么处理？

**答**：
- **大 Key**：拆分（如 `user:{id}` 拆 `user:{id}:base` / `user:{id}:profile`）；`UNLINK` 异步删。
- **热 Key**：本地缓存（Caffeine L1）挡；多副本（主从读分散）；`read-from=REPLICA_PREFERRED`。
- **本仓库**：图书详情走 L1+L2，热点探测自动升级 TTL；秒杀库存 Key 拆 `stock` + `users` 两个 Key。

### 16.8 分布式锁怎么实现？

**答**：
- **Redis SETNX + TTL**：`SET key value NX PX 30000`；value 用 UUID 防误删；释放用 Lua 校验 value。
- **Redisson RLock**：可重入、看门狗续期、公平锁。
- **本仓库**：逻辑过期重建用 `SETNX lockKey TTL=30s`；秒杀用 Lua 脚本无需锁。

## 第 17 章 代码细节追问

### 17.1 `SeckillService.grab` 为什么先查 idempotencyKey 再查 user+activity？

**答**：idempotencyKey 是前端重试时唯一标识，命中直接返回已有结果，不消耗令牌、不进 Lua；user+activity 查重是兜底（用户换 key 重试同活动）。先查 idempotencyKey 性能最优，重试请求快速返回。

### 17.2 `SeckillService.processSeckillOrder` 发券失败为什么不抛异常？

**答**：抛异常会让事务回滚，`SeckillOrder` 的 `FAILED` 状态也回滚，下次重试又重新发券；不抛则 `FAILED` 落库提交，主 Consumer ACK，死信队列兜底对账。保证 FAILED 状态不丢。

### 17.3 `BorrowService.confirm` 为什么先 `updateToBorrowed` 再 `setBorrowStock`？

**答**：`updateToBorrowed` 是 CAS UPDATE（`WHERE status='APPLIED'`），`rows==0` 说明状态已变，reload 重判；只有 CAS 成功才扣库存，避免并发确认扣超。先 CAS 改状态再扣库存，状态机保证不超扣。

### 17.4 `LogicalExpireCacheClient` 重建线程池为什么 10 线程？

**答**：重建是 IO 密集（查 DB + 写 Redis），10 线程足够应对突发热点；过多会压 DB；过少会排队。`daemon=true` 避免阻止 JVM 退出。

### 17.5 `JwtAuthenticationFilter` 为什么 `finally` 清 SecurityContext？

**答**：Tomcat 线程池复用线程，不清会导致下一个请求继承前一个用户身份（串号）。`finally` 确保异常时也清。

### 17.6 `ReadingProgressService.updateProgress` 为什么 `afterCommit` 才 `markClean`？

**答**：若事务回滚，进度未落库，`markClean` 会让下次延迟消息跳过写库，丢进度。`afterCommit` 保证只有提交后才清 dirty。

### 17.7 `AiChatConfig` 为什么 `@ConditionalOnProperty`？

**答**：`ai.enabled=false` 时不创建 ChatClient 与 ChatMemory，避免无 API key 时启动失败；`AiChatService` 同样条件注解，不创建 Bean。

### 17.8 `BookBloomRedisService.mightContain` 为什么 fail-open？

**答**：Redis 异常时返回 `true` 放行查 DB，保证可用性优先；若 fail-close 返回 `false`，Redis 抖动会导致所有详情 404，业务不可用。

### 17.9 `SeckillRateLimitService` 为什么活动维度 + 用户维度双限流？

**答**：活动维度防整体被打爆（容量 2000）；用户维度防单用户狂点（容量 2）。单维度不够：只限活动，单用户可能刷爆；只限用户，多用户并发仍可能压垮。

### 17.10 `TradeService.scheduleOrderTimeoutCancel` 为什么用 `TransactionSynchronization`？

**答**：避免事务回滚后消息已发出导致「无订单却触发关单」；`afterCommit` 保证消息一定对应已提交订单。无事务时直接发。

### A.2 令牌桶限流（`seckill_token_bucket.lua`）

```lua
local data = redis.call('HMGET', key, 'tokens', 'last_ms')
local tokens, last = tonumber(data[1]), tonumber(data[2])
if tokens == nil then tokens = capacity; last = now end
local filled = math.min(capacity, tokens + (now - last) * rate / 1000.0)
if filled < acquire then return 0 end

```

## 附录 C：面试速记 30 题

1. 双 Token 为什么？→ Access 短防泄露，Refresh 长可吊销，轮换防重放。
2. JWT 怎么吊销？→ Redis jti 黑名单 + 短 TTL。
3. 登录限流？→ Redis INCR 失败计数 + 锁 15 分钟。
4. 预约防超卖？→ `FOR UPDATE` 行锁 + 幂等键。
5. 签到 BitMap？→ `sign:user:{id}:{yyyyMM}` offset=day-1。
6. 连签 streak？→ `last == yesterday` 则 INCR 否则重置 1。
7. 缓存穿透？→ 布隆过滤器挡不存在 ID。
8. 缓存击穿？→ 逻辑过期 + 互斥重建 + 异步刷新。
9. 缓存雪崩？→ TTL 随机抖动。
10. 热点探测？→ 分桶滑动窗口 + 超 50 升级 TTL。
11. 借阅逾期？→ ZSET score=dueAt + Lua 弹出 + SQL 兜底。
12. 续借规则？→ 最多 1 次，未到期顺延，已逾期从 now 起算。
13. 优惠券策略？→ 工厂 + Calculator 接口 + 满减/折扣实现。
14. 下单算价？→ total - discount = pay，支付时才扣库存。
15. MQ 延迟关单？→ TTL 队列 + DLX 回主队列 + CAS 幂等。
16. 秒杀 Lua？→ 判库存 + 判重复 + 扣 + 记用户原子完成。
17. 令牌桶？→ 活动 2000 + 用户 2，Lua 补令牌 + try-acquire。
18. 一人一单？→ Redis Set + DB 唯一索引双层。
19. MQ 死信？→ Nack(requeue=false) → DLX → DLQ 对账。
20. AI 防编造？→ System Prompt 强约束 + Tool description 互补。
21. ChatMemory？→ Redis 持久化 + 滑动窗口 maxMessages。
22. RAG？→ Milvus + 千问 Embedding + filter type='faq'。
23. 阅读进度合并？→ Redis 热写 + MQ 延迟 + 换章即时写。
24. Study Agent？→ 独立 ChatClient + 5 个学习 Tool + ThreadLocal 上下文。
25. 四层架构？→ Controller → Service → Repository → Mapper。
26. 工厂模式？→ Login/SendCode/Coupon 三处。
27. Flyway？→ V1 基线 + baseline-on-migrate + 版本化 SQL。
28. Redis 拓扑？→ standalone/master-replica/sentinel/cluster 配置切换。
29. 可观测？→ Actuator + Micrometer + Prometheus + 自定义缓存指标。
30. 演进方向？→ ES 搜索 + Sentinel 限流 + XXL-JOB 调度 + SkyWalking 链路。
